# HTTP and HTTPS

Everything in this course comes together when you load a page. The browser [looks up the name](/courses/computer-networks/dns), opens a [TCP connection](/courses/computer-networks/tcp-reliable-delivery) or a QUIC one, sets up encryption, and then speaks HTTP: a simple, text-based conversation of requests and responses. This lesson covers that conversation and the encryption that protects it.

## Requests and responses

HTTP is a **request-response** protocol. The client sends a request:

```text
GET /courses?level=intro HTTP/1.1
Host: decoded.stack42.tech
Accept: text/html
```

and the server sends back a response:

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 5120

<!doctype html>…
```

A request has a **method**, a **path**, **headers** and sometimes a **body**. A response has a **status code**, headers and usually a body. Because [TCP is a byte stream](/courses/computer-networks/tcp-reliable-delivery#a-reliable-byte-stream), HTTP/1.1 marks where each message ends with a blank line after the headers and a `Content-Length` (or chunked encoding) for the body.

| Method | Meaning | Safe to repeat? |
|---|---|---|
| GET | fetch a resource | yes |
| POST | submit data, create something | no |
| PUT | replace a resource | yes (same result each time) |
| DELETE | remove a resource | yes |

| Status | Meaning |
|---|---|
| 2xx | success: **200** OK, **201** Created, **204** No Content |
| 3xx | go elsewhere: **301** moved permanently, **304** not modified (use your cache) |
| 4xx | the client got it wrong: **400** bad request, **401** not signed in, **403** forbidden, **404** not found, **429** too many requests |
| 5xx | the server failed: **500** internal error, **502** bad gateway, **503** unavailable |

Here's a real exchange with a tiny server on your own machine:

```python
import http.client, http.server, threading

class Hello(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        body = f"you asked for {self.path}".encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, *args):             # keep the output quiet
        pass

server = http.server.HTTPServer(("127.0.0.1", 0), Hello)
threading.Thread(target=server.serve_forever, daemon=True).start()

conn = http.client.HTTPConnection("127.0.0.1", server.server_port)
conn.request("GET", "/courses?level=intro")
resp = conn.getresponse()
print(resp.status, resp.reason)  # 200 OK
print(resp.getheader("Content-Type"))  # text/plain
print(resp.read().decode())  # you asked for /courses?level=intro

conn.close()
server.shutdown()
```

## Stateless, with cookies

Each HTTP request stands alone: the server isn't required to remember anything between them. That makes servers easy to scale, since any machine can answer any request. To keep you signed in, the server sends a **cookie** (`Set-Cookie: session=…`), and the browser sends it back with every later request to that site (`Cookie: session=…`).

## Three versions

- **HTTP/1.1** (1997) is text, one request at a time per TCP connection. Browsers open about six connections per site to fetch things in parallel.
- **HTTP/2** (2015) is binary and **multiplexes** many requests over one TCP connection. But one lost TCP segment stalls all of them: [head-of-line blocking](/courses/computer-networks/tcp-reliable-delivery#where-youll-meet-this).
- **HTTP/3** (2022) runs over **QUIC** on [UDP](/courses/computer-networks/udp-and-ports#why-use-an-unreliable-protocol), which keeps streams independent and combines the connection and encryption handshakes into one round trip.

The requests and responses mean the same in all three. Only how they're carried changed.

## HTTPS and TLS

Plain HTTP crosses every router on the path readable and changeable. **HTTPS** is HTTP inside **TLS** (Transport Layer Security), which gives three guarantees:

1. **Confidentiality**: the content is encrypted.
2. **Integrity**: any change in transit is detected.
3. **Authentication**: you're really talking to `decoded.stack42.tech`, not an impostor.

The handshake does two things before any HTTP is sent:

- **Key exchange.** Client and server agree on a shared secret key over the open network using **Diffie-Hellman key exchange**, whose security rests on [discrete logarithms](/courses/computational-mathematics/discrete-logarithms#a-one-way-street) being hard to compute (modern TLS uses an elliptic-curve version of the same idea). Everything after that is encrypted with fast symmetric ciphers such as AES.
- **Certificate check.** The server sends a **certificate**: its public key and name, signed by a **certificate authority** the browser already trusts. The browser checks the signature, the name and the expiry date. That's what the padlock means.

TLS 1.3 needs one round trip for this on a new connection, so a fresh HTTPS request over TCP costs DNS + TCP handshake + TLS handshake before the first byte of the page: why reusing connections, and HTTP/3's combined handshake, matter so much.

<Callout tone="orange" label="The padlock doesn't mean the site is safe">
HTTPS proves you're connected to the domain in the address bar, privately. It says nothing about whether that domain is honest. Phishing sites have valid certificates too: check the name, not just the padlock.
</Callout>
