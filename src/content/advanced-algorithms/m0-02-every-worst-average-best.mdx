# Counting the Basic Operation

To analyze an algorithm without a stopwatch, we pick its **basic operation** (the instruction that does the real work, like a comparison) and count how many times it runs for an input of size $n$. In this lesson we do that for a handful of classic algorithms, then see that the count isn't always a single number.

## Five small algorithms

**Sequential search.** Is the key `x` in the array `S` of `n` keys? Return its position, or 0 if it isn't there.

```cpp
void seqsearch(int n, const keytype S[], keytype x, index& location) {
    location = 1;
    while (location <= n && S[location] != x)
        location++;
    if (location > n)
        location = 0;
}
```

**Add the array members.** Add all the numbers in `S`.

```cpp
number sum(int n, const number S[]) {
    number result = 0;
    for (index i = 1; i <= n; i++)
        result = result + S[i];
    return result;
}
```

**Exchange sort.** Sort `n` keys into nondecreasing order: compare each position with every position after it and swap if they're out of order.

```cpp
void exchangesort(int n, keytype S[]) {
    for (index i = 1; i <= n; i++)
        for (index j = i + 1; j <= n; j++)
            if (S[j] < S[i])
                swap(S[i], S[j]);
}
```

**Matrix multiplication.** Multiply two $n \times n$ matrices.

```cpp
void matrixmult(int n, const number A[][N], const number B[][N], number C[][N]) {
    for (index i = 1; i <= n; i++)
        for (index j = 1; j <= n; j++) {
            C[i][j] = 0;
            for (index k = 1; k <= n; k++)
                C[i][j] = C[i][j] + A[i][k] * B[k][j];
        }
}
```

**Binary search.** If the array is *sorted*, look at the middle. If `x` is smaller, throw away the right half, and if it's bigger, throw away the left half. Repeat.

```cpp
void binsearch(int n, const keytype S[], keytype x, index& location) {
    index low = 1, high = n, mid;
    location = 0;
    while (low <= high && location == 0) {
        mid = (low + high) / 2;           // integer division = floor
        if (x == S[mid])     location = mid;
        else if (x < S[mid]) high = mid - 1;
        else                 low = mid + 1;
    }
}
```

## Sequential vs. binary search

Both answer the same question, but look at the comparisons they need in the worst case:

| Array size | Sequential search | Binary search |
| ---: | ---: | ---: |
| 128 | 128 | 8 |
| 1,024 | 1,024 | 11 |
| 1,048,576 | 1,048,576 | 21 |
| 4,294,967,296 | 4,294,967,296 | 33 |

Every time the array doubles, sequential search does twice the work, but binary search does only **one more** comparison. That's the difference between $n$ and $\lg n$.

## Every-case time complexity

For some algorithms, the basic operation runs the **same number of times for every input of size $n$**. Then we write $T(n)$ and call it the **every-case** time complexity.

| Algorithm | Basic operation | $T(n)$ |
| --- | --- | --- |
| Add array members | addition | $n$ |
| Exchange sort | comparison of `S[j]` with `S[i]` | $(n-1) + (n-2) + \dots + 1 = \dfrac{(n-1)n}{2}$ |
| Matrix multiplication | multiplication in the inner loop | $n \times n \times n = n^3$ |

The contents of the input don't matter. Exchange sort compares every pair even if the array is already sorted.

## When there is no every-case

Sequential search is different. If `x` is in the first slot, it stops after one comparison. If `x` is missing, it checks all $n$. So we look at three separate numbers.

**Worst case $W(n)$.** The basic operation runs at most $n$ times, when `x` is the last item or isn't in the array at all:

$$
W(n) = n
$$

The worst case tells you the **absolute maximum** time the algorithm can take.

**Average case $A(n)$.** This is the *expected* number of comparisons. Assume `x` is in the array and is equally likely to be in any of the $n$ slots, so each slot has probability $1/n$. If `x` is in slot $k$, finding it takes $k$ comparisons:

$$
A(n) = \sum_{k=1}^{n} k \cdot \frac{1}{n} = \frac{1}{n} \cdot \frac{n(n+1)}{2} = \frac{n+1}{2}
$$

On average you look through about half the array. (If `x` might be missing, say it's present with probability $p$ and absent with probability $1-p$, you add $n \cdot (1-p)$ for the misses.)

**Best case $B(n)$.** The loop runs at least once, since $n \ge 1$. If `x = S[1]`, there is exactly one pass whatever $n$ is:

$$
B(n) = 1
$$

## Fibonacci: the same problem, two very different algorithms

The Fibonacci sequence is $F_0 = 0$, $F_1 = 1$ and $F_n = F_{n-1} + F_{n-2}$ for $n > 1$. Translating the definition straight into code gives a recursive function:

```cpp
int fib(int n) {
    if (n <= 1)
        return n;
    else
        return fib(n - 1) + fib(n - 2);
}
```

It looks perfect, but count the calls it makes:

| $n$ | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| calls | 1 | 1 | 3 | 5 | 9 | 15 | 25 |

If you draw the call tree, `fib(n-2)` is computed inside `fib(n-1)` *and again* on its own. The number of calls $T(n)$ more than doubles every time $n$ grows by 2:

$$
T(n) > 2\,T(n-2) > 2 \cdot 2\,T(n-4) > \dots > \underbrace{2 \cdot 2 \cdots 2}_{n/2 \text{ times}}\, T(0)
$$

Since $T(0) = 1$, this gives $T(n) > 2^{n/2}$ (you can prove it properly by induction). That's **exponential**.

The fix is to keep each term in an array, so every term is computed exactly once:

```cpp
int fib2(int n) {
    int f[n + 1];
    f[0] = 0;
    if (n > 0) {
        f[1] = 1;
        for (index i = 2; i <= n; i++)
            f[i] = f[i - 1] + f[i - 2];
    }
    return f[n];
}
```

## Applying the theory

Suppose two algorithms solve the same problem: the first takes $n$ steps and the second takes $n^2$. The first looks better. But say the first algorithm's basic operation is **1,000 times slower** on our computer: it takes $1000t$ per step, while the second takes $t$.

| | Time for input size $n$ |
| --- | --- |
| Algorithm 1 | $n \times 1000t$ |
| Algorithm 2 | $n^2 \times t$ |

The first one is faster when

$$
n^2 t > 1000\,n\,t \quad\Longrightarrow\quad n > 1000.
$$

So for inputs under 1,000 the "worse" algorithm wins, but for anything bigger the linear one wins, and the gap keeps growing. The same happens with $100n$ against $0.01n^2$: the linear one wins once $0.01n^2 > 100n$, which means $n > 10{,}000$.

<Callout tone="violet" label="The fundamental principle">
**Any linear-time algorithm is eventually more efficient than any quadratic-time algorithm.** Constants only change *where* the crossover happens, not *whether* it happens.
</Callout>

## Order

That principle lets us group functions by how they behave **eventually**.

- $5n^2$ and $5n^2 + 100$ are **pure quadratic** functions: they have no linear term.
- $0.1n^2 + n + 100$ is a **complete quadratic** function: it has a linear term too.

Watch what happens as $n$ grows:

| $n$ | $0.1n^2$ | $0.1n^2 + n + 100$ |
| ---: | ---: | ---: |
| 10 | 10 | 120 |
| 20 | 40 | 160 |
| 50 | 250 | 400 |
| 100 | 1,000 | 1,200 |
| 1,000 | 100,000 | 101,100 |

Eventually the $n^2$ term dominates, and the other terms become insignificant. So even though $0.1n^2 + n + 100$ isn't pure quadratic, we put it in the same group.

The set of all complexity functions that can be grouped with the pure quadratic functions is called $\Theta(n^2)$. If a function is in $\Theta(n^2)$, we say it is **order $n^2$**. For example, since we can throw away low-order terms:

$$
g(n) = 5n^2 + 100n + 20 \in \Theta(n^2)
$$

The most common groups, from slowest-growing to fastest-growing:

$$
\Theta(\lg n) \quad \Theta(n) \quad \Theta(n \lg n) \quad \Theta(n^2) \quad \Theta(n^3) \quad \Theta(2^n)
$$
