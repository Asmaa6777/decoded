# Red-Black Trees: Insertion and Deletion

Searching a [red-black tree](/courses/advanced-algorithms/balanced-search-trees) is just a BST search. Inserting and deleting are harder, because they can break the four properties. This lesson shows how to repair them using only **recoloring** and **rotations**, in $O(\lg n)$ time.

## The problem with insertion

Imagine adding keys to a red-black tree one at a time.

- **Insert 8.** Where does it go? Wherever the BST rules say. What color should it be? If we make it **red**, every path keeps the same number of black nodes, so property 4 is safe.
- **Insert 11**, below a red node. What color? It **can't be red**, because a red child of a red parent breaks property 3. It **can't be black** either: that adds a black node to only some paths, which breaks property 4. **Solution:** make it red and **recolor the tree** around it.
- **Insert 10**, so that the path bends. Now **no coloring works**. The tree is too unbalanced. We must **change the structure** of the tree so that recoloring becomes possible, and do it in $O(\lg n)$ time. The tool for this is the **rotation** from the last lesson.

## Insertion: the idea

<Callout tone="violet" label="RB-INSERT">
Insert $x$ into the tree as in an ordinary BST, and **color it red**. Only red-black property 3 might now be violated, if $x$'s parent is red. If so, **move the violation up the tree** by recoloring, until it can be fixed with rotations and recoloring.
</Callout>

```text
RB-INSERT(T, x)
    TREE-INSERT(T, x)
    color[x] ← RED              ⊳ only RB property 3 can be violated
    while x ≠ root[T] and color[p[x]] = RED
        do if p[x] = left[p[p[x]]]
            then y ← right[p[p[x]]]       ⊳ y = aunt/uncle of x
                 if color[y] = RED
                     then ⟨Case 1⟩
                     else if x = right[p[x]]
                              then ⟨Case 2⟩     ⊳ Case 2 falls into Case 3
                          ⟨Case 3⟩
            else ⟨"then" clause with "left" and "right" swapped⟩
    color[root[T]] ← BLACK
```

In the pictures below, $\Delta$ means a subtree with a black root, and all the $\Delta$'s have the **same black-height**.

### Case 1: the uncle $y$ is red

**Recolor.** Make $x$'s parent and uncle black, and the grandparent red:

```cpp
x->p->color = BLACK;
y->color = BLACK;
x->p->p->color = RED;
x = x->p->p;
```

This "pushes" the grandparent's black down onto its two children. Every downward path still has the same black-height, so property 4 holds. But the grandparent is now red, and *its* parent might be red too. So **recurse**: the loop continues with the grandparent as the new $x$. Case 1 does the same thing whether $x$ is a left or a right child.

<Callout tone="orange" label="Two usual slips">
- **Coloring the new node black.** It seems safer, but a black node adds one to the black count on just one path. That breaks property 4 everywhere above it, which is much harder to fix. A red node can only break property 3, and only locally.
- **Looking at the wrong relative.** Cases 1 to 3 depend on the **uncle** (the parent's sibling), not on $x$'s sibling. Find the grandparent first, then take its other child.
</Callout>

### Case 2: the uncle $y$ is black, and $x$ is an *inner* child

Here $x$ is a right child whose parent is a left child (or the mirror image). The path from the grandparent to $x$ **bends**.

```cpp
x = x->p;
leftRotate(x);
// continue with the Case 3 code
```

A rotation at the parent **straightens** the bend, turning this into Case 3. It keeps property 4: every downward path still has the same number of black nodes.

### Case 3: the uncle $y$ is black, and $x$ is an *outer* child

```cpp
x->p->color = BLACK;
x->p->p->color = RED;
rightRotate(x->p->p);
```

Recolor, then rotate at the grandparent. **Done!** The parent, now black, sits where the grandparent was, so no more violations of property 3 are possible.

## Example: insert 15

This is the lecture's example. Step through it and watch the case label:

1. Insert $x = 15$ under 11. Both 15 and 11 are red.
2. The uncle 8 is red, so **Case 1**: recolor, moving the violation up the tree to 10.
3. Now 10 and its parent 18 are both red, and the uncle 3 is black. 10 is an inner child, so **Case 2**: RIGHT-ROTATE(18).
4. **Case 3:** LEFT-ROTATE(7) and recolor. 10 becomes the new root.

## Analysis of insertion

- Go **up** the tree performing Case 1, which only **recolors** nodes. Each time, $x$ moves up two levels, so this happens at most $O(\lg n)$ times.
- If Case 2 or Case 3 happens, perform **1 or 2 rotations**, and **stop**.

**Running time: $O(\lg n)$, with $O(1)$ rotations.**

## Deletion

RB-DELETE has the **same asymptotic running time**, $O(\lg n)$, and uses a constant number of rotations too (at most 3).

**Step 1: ordinary BST deletion.**

- If the node to delete has **two children**, replace its data with its **predecessor's** data (the largest key in its left subtree) or its successor's. Its color stays the same. Then delete the predecessor's node instead.
- So the node $y$ that's actually removed always has **at most one** real (non-NIL) child.

**Step 2: did we break anything?**

- If the removed node $y$ was **red**, no property can be violated. Just remove it.
- If $y$ was **black**, every path that went through $y$ now has one black node too few, which breaks property 4. Let $x$ be the child that takes $y$'s place. It may be a black NIL "pretend" node. Call the **tree-fix** algorithm on $x$.

```text
RB-DELETE(T, z)
    if z has two children
        y ← PREDECESSOR(z)       ⊳ or successor
        key[z] ← key[y]          ⊳ move y's data into z
    else y ← z
    x ← the only child of y (a pretend NIL if it has none)
    splice y out, attaching x to y's parent
    if color[y] = BLACK
        RB-TREE-FIX(T, x)
```

### Fixing the tree: the black token

The tree-fix algorithm treats $x$ as carrying an **extra black token**. That makes up for the black node that was removed, so property 4 holds again. But it means $x$ might now be "doubly black", which breaks property 1 (every node is *either* red or black).

The token is **pushed up the tree** until:

- it reaches a **red** node, which is then colored black, or
- it reaches the **root**, where it can just be dropped, or
- it can be removed by **rotating and recoloring**.

Let $w$ be $x$'s **sibling**. The **nephews** are $w$'s children.

| Case | Situation | What to do |
| --- | --- | --- |
| (1) | $x$ is **red** | Color it black. **Done!** |
| (2) | $x$'s sibling $w$ is **red** | Swap the colors of $w$ and the parent, then rotate at the parent. Now $x$ has a black sibling, so go on to case (3) or (4). |
| (3) | $w$ is black and **both nephews are black** | Color $w$ red. That takes one black from both sides, so pass the token **one level up** to the parent and repeat. |
| (4) | $w$ is black and **a nephew is red** | Rotate (once or twice) and recolor, so that the red nephew becomes black and fills the gap. **Done!** |

In cases (2) and (4), the second picture is the mirror image: when $x$ is a right child, swap left and right.

### The lecture's three deletion examples

All three start from the tree built in [Another insertion example](#another-insertion-example). It has 47 at the root and 32 on the left. On the right is the red 71, with 65, 87, 82 and 93 below it.

**Example 1: delete 87.** 87 has two children, so its key is replaced by its predecessor, 82, and 82's old node is removed instead. That node was **red**, so nothing breaks. No fix-up at all.

<RBTreeVisualizer start={[47, 32, 71, 65, 82, 87, 93]} ops={[{ op: "delete", key: 87 }]} />

**Example 2: delete 71**, from the same tree with 51 added (a red left child of 65). 71 has two children, so its key is replaced by its predecessor, 65. 65's old node was **black**, and its child 51 takes its place. 51 is **red**, so case (1): color 51 black. Done.

<RBTreeVisualizer start={[47, 32, 71, 65, 82, 87, 93, 51]} ops={[{ op: "delete", key: 71 }]} />

**Example 3: delete 32.** 32 is black and has no children, so its place is taken by a NIL "pretend" node $x$ that carries the extra black token.

1. $x$'s sibling is the red 71: **case (2)**. Make 71 black and the parent 47 red, then left-rotate at 47. 71 is now the root.
2. $x$'s new sibling is 65, which is black with two black (NIL) children: **case (3)**. Color 65 red and pass the token up to the parent, 47.
3. 47 is **red**, so **case (1)**: color it black. Done.

The result is 71 at the root, with 47 (and its red right child 65) on the left and 87 (with red 82 and 93) on the right.

### Part 1: Midterm questions

**1.** *(Midterm 2023)* Insert 5, then 9, into this red-black tree: root 2 (black), with children 1 and 4 (both red).

<ModelAnswer>
**Insert 5.** It goes to the right of 4 and is coloured red. Its parent 4 is red, and its uncle 1 is red too: **Case 1**. Recolour: 4 and 1 become black, and 2 becomes red. 2 is the root, so it is coloured black again. The tree is now 2 (black) with children 1 and 4 (black), and 5 (red) under 4.

**Insert 9.** It goes to the right of 5 and is red. Its parent 5 is red, and its uncle (4's left child) is NIL, which is black. 9 is an **outer** child (right of a right child): **Case 3**. Rotate left at 4, then swap the colours of 5 and 4.

**Result:** 2 (black) at the root, with 1 (black) on the left and 5 (black) on the right; 5 has children 4 and 9, both red.
