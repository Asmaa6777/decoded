# The Abstraction Gap

Most computer science curricula teach you the **mathematical scaffolding** that practitioners use without knowing they're using it. Theory of Computation is a clear example. It was built in the 1930s to 1950s by people like Turing, Church and Kleene, who were trying to answer one question: *what can a machine compute, and what can't it?*

They weren't building apps. Still, that question produced:

- **[Finite Automata](/courses/theory-of-computation/how-to-read-a-machine)** → regex engines (grep, sed, almost every search bar)
- **[Pushdown Automata](/courses/theory-of-computation/pushdown-automata)** → parsers (every compiler, every browser rendering HTML)
- **Turing Machines** → the conceptual model for every CPU
- **Decidability** → why no antivirus can perfectly detect all malware
- **[Complexity Classes (P vs NP)](/courses/advanced-algorithms/p-and-np#p-vs-np)** → why cryptography works at all

<Callout tone="orange" label="The reverse-engineering question">
For each course topic, ask: *"What breaks if this theory didn't exist?"* That question gets through the abstraction faster than most textbook chapters.
</Callout>

Making those connections has a name in cognitive science: **transfer learning**, taking a principle from one domain and recognizing it in another. It's a big part of what separates senior engineers from juniors.

This course is built around that skill. Every module pairs the formal idea with the modern tool, the job, and the failure you've probably already seen in the wild.
