# States, Symbols, and Transitions

In Module 0 you learned to read machines by looking at them. You could trace a string through a diagram and tell whether it gets **accepted** or **rejected**. That's a useful skill, but it isn't mathematics yet: two people looking at two different diagrams have no shared language for comparing them, proving things about them, or building on them.

The formal definition fixes that. It's a precise notation that lets you reason about machines the way you reason about equations.

## Deterministic Finite Automaton Definition

A **Deterministic Finite Automaton** is defined as a five-tuple:

$$
M = (Q,\ \Sigma,\ \delta,\ q_0,\ F)
$$

Each of the five components maps directly to something you've seen in the diagrams.

**$Q$** is the finite set of all states: every circle in the diagram.

$$
Q = \{q_0,\ q_1,\ q_2\}
$$

**$\Sigma$** is the alphabet, the set of symbols the machine is allowed to read. A symbol outside $\Sigma$ never appears in its input.

$$
\Sigma = \{a,\ b\}
$$

**$\delta$** is the transition function, meaning the arrows. It takes a state and a symbol and returns the next state:

$$
\delta : Q \times \Sigma \rightarrow Q
$$

Read that as: given any state in $Q$ and any symbol in $\Sigma$, $\delta$ tells you exactly which state to move to. One input, one output, no ambiguity. That's what *deterministic* means.

**$q_0$** is the initial state, where computation always begins. $q_0 \in Q$.

**$F$** is the set of accept states, the double circles. $F \subseteq Q$. If the machine runs out of input while its current state is in $F$, it accepts the input.

<Callout tone="violet" label="Why a five-tuple">
  Five components are the minimum needed to fully specify a DFA. Give someone these five and they can reconstruct the diagram exactly, and they can also reason about the machine mathematically without drawing it.
</Callout>

Written as a five-tuple:

$$
Q = \{q_0,\ q_1,\ q_2\}
$$

$$
\Sigma = \{a,\ b\}
$$

$$
q_0 = q_0 \qquad F = \{q_2\}
$$

And the transition function $\delta$ as a table, with one entry for every state and symbol:

$$
\begin{array}{c|cc}
\delta & a & b \\
\hline
q_0 & q_1 & q_0 \\
q_1 & q_1 & q_2 \\
q_2 & q_1 & q_0 \\
\end{array}
$$

Each row is a state, each column a symbol, and each cell is where $\delta$ sends you. The table and the diagram hold identical information; they're two representations of the same machine.

<Callout tone="orange" label="The transition table must be complete">
  Every cell in the table must be filled, because every state needs a transition for every symbol in $\Sigma$. A machine with a missing transition is no longer a DFA. This is one of the differences between a DFA and an NFA, which you'll meet in the next lesson.
</Callout>

## The Extended Transition Function: $\hat{\delta}$

$\delta$ handles one symbol at a time, but what you care about is what happens after reading a whole string. For that, mathematicians define $\hat{\delta}$ (delta-hat), the extended transition function, which works on strings instead of single symbols.

$$
\hat{\delta}(q,\ \varepsilon) = q
$$

Reading the empty string from any state leaves you in that state.

$$
\hat{\delta}(q,\ wa) = \delta(\hat{\delta}(q,\ w),\ a)
$$

Reading a string $wa$ means: first process the string $w$ to get some intermediate state, then read the final symbol $a$ from there.

The definition is recursive: it builds up the computation one symbol at a time, exactly as you did by hand in lesson 03. $\hat{\delta}$ is the formal name for that process.

To see $\hat{\delta}$ in action, run it on the string $ab$ for the machine above. Apply the recursive rule, peeling off one symbol at a time from the right:

$$
\hat{\delta}(q_0,\ ab) = \delta(\hat{\delta}(q_0,\ a),\ b)
$$

$$
\hat{\delta}(q_0,\ a) = \delta(\hat{\delta}(q_0,\ \varepsilon),\ a) = \delta(q_0,\ a) = q_1
$$

$$
\hat{\delta}(q_0,\ ab) = \delta(q_1,\ b) = q_2
$$

The language a DFA $M$ accepts is then defined as:

$$
L(M) = \{w \in \Sigma^* \mid \hat{\delta}(q_0,\ w) \in F\}
$$

That's all strings that, fed to the machine from $q_0$, end in an accept state. The trace above ends at $q_2 \in F$, so $ab \in L(M)$. You reached the same conclusion by hand in lesson 03; this time it comes straight from the definition, with no diagram involved.

## What "Deterministic" Buys You

Lesson 03 unpacked the word: at every state, every symbol has exactly one transition arrow. Formally, that rule lives in the type of $\delta$ itself:

$$
\delta : Q \times \Sigma \rightarrow Q
$$

The codomain is $Q$, not the power set of $Q$, so one input pair always returns one state. All of determinism is in that function type.

Two consequences follow. First, a DFA simulator is a tight loop: read one character, do one table lookup, never backtrack. That's why regex engines built on DFAs run in time linear in the length of the input. Second, this single-arrow rule is exactly what the next lesson relaxes. An NFA's transition function returns a *set* of states, and the machine explores all of them at once. The diagrams look the same, but the signature differs and the runtime behaves very differently.

<Callout tone="sky" label="Historical note">
  The DFA was formally defined by Warren McCulloch and Walter Pitts in 1943, originally as a mathematical model of how neurons fire rather than as a computing model. Kleene then connected it to regular expressions in 1951. The parking meter, the regex engine, and the original neuron model are all instances of the same five-tuple.
</Callout>

## Building Your First DFA

Knowing the definition isn't enough; you also need to build machines. The process always follows the same steps:

**Step 1: Identify the conditions.** What does the machine need to remember to make the right decision at the end? Each distinct condition becomes a state. Track only the conditions that affect the final answer, not the full history of what it has seen.

**Step 2: Name the states.** One state per condition. Add a dead state if the machine can reach a point where acceptance is impossible regardless of what follows.

**Step 3: Fill the transition table.** For every state, for every symbol, decide: if I am in this condition and I read this symbol, what condition am I in now?

**Step 4: Mark the initial and accept states.** Which condition am I in before reading anything? Which conditions represent strings I want to accept?

As a worked example, build a DFA over $\Sigma = \{a, b\}$ that accepts exactly the strings containing at least one $a$.

The conditions that matter:
- $q_0$: haven't seen any $a$ yet, so can't accept yet
- $q_1$: have seen at least one $a$, so accept from here on

$$
\begin{array}{c|cc}
\delta & a & b \\
\hline
q_0 & q_1 & q_0 \\
q_1 & q_1 & q_1 \\
\end{array}
$$

$q_0$ is initial. $q_1$ is the only accept state. Once you reach $q_1$, no symbol can take you back, because "seen at least one $a$" stays true forever.

<Callout tone="mint" label="What you now have">
  A DFA is now a mathematical object with a precise definition, as well as a picture you can trace. You can write one as a five-tuple, read its transition table, apply $\hat{\delta}$ to compute what any string does, and build one from scratch by identifying the conditions your language needs to track. The next lesson introduces NFAs, machines where $\delta$ returns a set of states, and the surprising theorem that they recognize exactly the same languages as DFAs.
</Callout>
