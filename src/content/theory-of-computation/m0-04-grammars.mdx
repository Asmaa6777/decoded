# Grammars: Rules That Generate a Language

The last lesson described languages as sets: either you list the strings, or you write a rule in set notation like $\{w \in \Sigma^* \mid w \text{ starts with } a\}$. Set notation is precise, but it only tells you how to *check* a string. It doesn't tell you how to *produce* one.

In 1956 the linguist Noam Chomsky proposed a different way to pin down a language: give a finite set of rewriting rules that generate exactly its strings, and nothing else. He called this a **grammar**. His paper was about English, but the idea became the standard way to define programming languages, file formats and network protocols.

## The four parts of a grammar

A grammar is a four-tuple:

$$
G = (V,\ T,\ P,\ S)
$$

- $V$ is a finite set of **variables** (also called non-terminals). We write them as uppercase letters: $S$, $A$, $B$.
- $T$ is the set of **terminals**, the symbols that end up in the finished string. It's the alphabet $\Sigma$ from the last lesson, written in lowercase: $a$, $b$, $0$, $1$.
- $P$ is a finite set of **productions** (rules) of the form $\alpha \rightarrow \beta$, read "$\alpha$ can be rewritten as $\beta$".
- $S \in V$ is the **start variable**.

Some textbooks write the same thing as $(N, \Sigma, P, S)$, with $N$ for non-terminals. The parts are identical; only the letters change.

When several rules share a left-hand side, they're written on one line with a bar. $S \rightarrow aS \mid b$ is shorthand for the two rules $S \rightarrow aS$ and $S \rightarrow b$.

## Derivations

You use a grammar by starting from $S$ and repeatedly replacing a variable with the right-hand side of one of its rules. Each replacement is one **derivation step**, written $\Rightarrow$. Take the grammar

$$
S \rightarrow aS \mid b
$$

and derive $aab$:

$$
S \Rightarrow aS \Rightarrow aaS \Rightarrow aab
$$

Three steps: $S \rightarrow aS$ twice, then $S \rightarrow b$ to finish. The intermediate strings like $aaS$, which still contain variables, are called **sentential forms**. A derivation is finished when no variables are left.

$\Rightarrow^*$ means "in zero or more steps", so $S \Rightarrow^* aab$. The **language of the grammar** is every string of terminals you can reach from $S$:

$$
L(G) = \{w \in T^* \mid S \Rightarrow^* w\}
$$

For $S \rightarrow aS \mid b$, every string is some number of $a$'s followed by one $b$, so $L(G) = \{b,\ ab,\ aab,\ aaab,\ \ldots\}$, which is the regular expression $a^*b$.

## Try it: deriving $a^nb^n$

Here is the grammar for a language that Module 2 proves no finite automaton can recognize:

$$
S \rightarrow aSb \mid \varepsilon
$$

Each use of $S \rightarrow aSb$ adds one $a$ on the left and one $b$ on the right, so the two counts always match. $S \rightarrow \varepsilon$ removes the variable and ends the derivation. Step through it, then change the target string or the rules themselves.

## The Chomsky hierarchy

Chomsky's other contribution was to sort grammars by how much freedom their rules have. The more restricted the rules, the simpler the machine needed to recognize the language.

| Type | Name | Rules look like | Recognized by | Example language |
| --- | --- | --- | --- | --- |
| 3 | Regular | $A \rightarrow aB$ or $A \rightarrow a$ | Finite automaton | $a^*b$ |
| 2 | Context-free | $A \rightarrow \beta$ (one variable on the left) | Pushdown automaton | $a^nb^n$ |
| 1 | Context-sensitive | $\alpha \rightarrow \beta$ with $\lvert\alpha\rvert \le \lvert\beta\rvert$ | Linear-bounded automaton | $a^nb^nc^n$ |
| 0 | Unrestricted | $\alpha \rightarrow \beta$, anything | Turing machine | Anything a program can enumerate |

Each type contains the ones below it. Every regular language is context-free, every context-free language is context-sensitive, and so on. The examples in the last column sit exactly one level up: $a^nb^n$ is context-free but not regular, and $a^nb^nc^n$ is context-sensitive but not context-free.

This table is also a map of this course. Module 1 covers type 3 and Module 2 covers type 2. Types 1 and 0, and the Turing machine, are where later courses pick up.

<Callout tone="orange" label="Why the left-hand side matters">
  "Context-free" means a rule like $A \rightarrow \beta$ can be applied wherever $A$ appears, whatever surrounds it. A context-sensitive rule such as $aAb \rightarrow aab$ only fires when $A$ sits between an $a$ and a $b$. That dependence on the neighbours is the "context".
</Callout>

## A regular grammar is a finite automaton

Type 3 rules have a shape you've already seen. In $A \rightarrow aB$, read $A$ and $B$ as states and the rule as an arrow from $A$ to $B$ labelled $a$. A rule $A \rightarrow a$ is an arrow from $A$ to an accept state. Here is $S \rightarrow aS \mid b$ drawn that way:

Run `aab` through it and compare the states it visits with the derivation $S \Rightarrow aS \Rightarrow aaS \Rightarrow aab$ above. Each derivation step is one transition. That correspondence works for every right-linear grammar, which is why regular grammars, finite automata and regular expressions all describe the same family of languages.

## Two exam questions you'll meet

**"What language does this grammar generate?"** Derive the three or four shortest strings, look for the pattern, then check that every rule preserves it. For $S \rightarrow aSb \mid \varepsilon$: $\varepsilon$, $ab$, $aabb$, $aaabbb$. The pattern is $a^nb^n$, and $S \rightarrow aSb$ keeps the counts equal, so $L(G) = \{a^nb^n \mid n \ge 0\}$.

**"Write a grammar for this language."** Work out what has to stay balanced or ordered, and let one variable carry that job. For "strings over $\{a, b\}$ with an even number of symbols", one variable can add two symbols at a time: $S \rightarrow aaS \mid abS \mid baS \mid bbS \mid \varepsilon$. Test your answer by deriving a few strings and by trying to derive one that shouldn't be there.

## Where this shows up today

<ApplicationsGrid>
  <PracticalApplication title="Language specifications" tool="SPECS">
    Programming languages are defined by grammars. CPython's parser is generated from a grammar file in its repository (`Grammar/python.gram`), and the JSON format on json.org is specified the same way.
  </PracticalApplication>
  <PracticalApplication title="Internet standards" tool="RFCs">
    The syntax of URLs, email addresses and HTTP headers is written in ABNF, a grammar notation defined in RFC 5234. When a library validates a URL, it is checking membership in that grammar's language.
  </PracticalApplication>
  <PracticalApplication title="Parser generators" tool="COMPILERS">
    Tools like yacc, Bison and ANTLR take a grammar as input and output a parser. You write the rules; the tool builds the machine that recognizes them.
  </PracticalApplication>
  <PracticalApplication title="Syntax highlighting" tool="EDITORS">
    Editors such as Neovim, Zed and GitHub's code view use tree-sitter, which builds a parser from a grammar for each language so highlighting follows the real structure of the code.
  </PracticalApplication>
</ApplicationsGrid>
