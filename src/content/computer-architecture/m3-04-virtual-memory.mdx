# Virtual Memory

A multitasking operating system runs dozens or hundreds of programs at once. Each program is compiled as if it has all of memory to itself, starting at address 0. At the same time, programs like databases and browsers often need more memory than the motherboard physically holds.

**Virtual memory** solves both problems. It separates the addresses software uses from the physical addresses wired into RAM chips. Every address the CPU emits is a **virtual address**. Before an access can reach memory, dedicated hardware translates it into a **physical address**.

Virtual memory provides three core benefits:

1. **Larger apparent memory**: The operating system treats physical RAM as a cache for disk or solid-state storage. Programs larger than physical RAM run without changes.
2. **Process protection and isolation**: Each process receives its own address mapping. One process cannot read or corrupt memory belonging to another process or the kernel.
3. **Simpler memory layout**: Compilers and linkers place code, heap data, and the stack at standard addresses without needing to know which physical RAM locations are free.

The Operating Systems course covers the software policies that support this hardware: [demand paging](/courses/operating-systems/virtual-memory#demand-paging) and [page replacement](/courses/operating-systems/page-replacement-and-thrashing#page-replacement).

## Pages, Frames, and Address Decomposition

Virtual memory partitions both virtual and physical address spaces into fixed-size contiguous blocks of memory:

- A block in virtual memory is called a **virtual page** (or simply a page).
- A block in physical memory is called a **page frame** (or physical frame).
- Virtual pages and physical page frames have the exact same size, standardized at **4 KB** ($2^{12}$ bytes) in most general-purpose architectures, with support for larger "huge pages" (2 MB or 1 GB) for performance-critical workloads.

When a program generates an $n$-bit virtual address, the hardware divides it into two fields:

| Field | Virtual Page Number ($VPN$) | Page Offset ($p$ bits) |
|---|---|---|
| **Bit Position** | $A_{n-1} \dots A_p$ | $A_{p-1} \dots A_0$ |
| **Hardware Function** | Selects virtual page in page table | Selects exact byte within page |

1. **Page Offset ($p$ bits)**: Selects the specific byte within a page. A page size of $P$ bytes requires $p = \log_2(P)$ offset bits. For 4 KB pages, $p = \log_2(4096) = 12$ bits.
2. **Virtual Page Number ($VPN$)**: Identifies which page in the virtual address space is being referenced:

$$
VPN = \lfloor \text{Virtual Address} / \text{Page Size} \rfloor
$$

### The Translation Process

During memory access, the offset never changes. The byte offset within a virtual page is identical to the byte offset within the destination physical frame:

$$
\text{Physical Offset} = \text{Virtual Offset}
$$

The **Memory Management Unit** (MMU), a hardware block located inside the processor die, translates the $VPN$ into a **Physical Frame Number** ($PFN$):

$$
\text{Physical Address} = (PFN \times \text{Page Size}) + \text{Page Offset}
$$

The translation proceeds along two concurrent paths:
1. **Offset pass-through**: The lower $p$ bits ($A_{p-1} \dots A_0$) pass directly through untranslated, preserving the byte position within the physical frame.
2. **Frame lookup**: The upper $VPN$ bits feed the MMU, which queries the page table (or TLB) to output the matching $PFN$.
3. **Address concatenation**: The physical address is constructed by placing the $PFN$ in the high-order bits and appending the untouched page offset.

<Callout tone="orange" label="Attempting to translate the page offset">
A frequent beginner mistake is attempting to pass the offset bits through the page table or MMU translation logic. The page offset never changes during address translation. Because virtual pages and physical frames are the same size (typically 4 KB), byte 120 within a virtual page is physically stored at byte 120 within the assigned physical frame. Translation applies strictly to the Virtual Page Number ($VPN$).
</Callout>

## The Page Table and Page Table Entries (PTE)

The translation from $VPN$ to $PFN$ is stored in a lookup data structure called the **page table**. The operating system maintains an independent page table for every running process. When the operating system schedules a process, it loads the base physical address of that process's page table into a dedicated processor control register, such as the **Page Table Base Register** (PTBR), known as `CR3` on x86 architectures.

Each entry in a page table is called a **Page Table Entry** (PTE), typically 4 or 8 bytes wide, containing both the target frame address and control flags:

| Field | Valid ($V$) | Referenced ($R$) | Write ($W$) | Execute ($X$) | User ($U/S$) | Dirty ($D$) | Physical Frame Number ($PFN$) |
|---|---|---|---|---|---|---|---|
| **Width** | 1 bit | 1 bit | 1 bit | 1 bit | 1 bit | 1 bit | High-order address bits |
| **Purpose** | Resident in RAM | Page accessed | Writable | Machine code | User vs Kernel | Modified by store | Base frame address in RAM |

1. **Valid bit ($V$)**: Indicates whether the virtual page is currently resident in physical RAM ($V = 1$) or resides out on secondary disk swap storage ($V = 0$).
2. **Physical Frame Number ($PFN$)**: The base address bits of the physical RAM frame holding the page.
3. **Protection bits ($R, W, X$)**: Hardware access permissions specifying whether the page can be read, written, or executed as CPU machine code. Attempting to write to a read-only page or execute data on a non-executable page triggers a hardware protection fault (such as a segmentation fault).
4. **User / Supervisor bit ($U/S$)**: Enforces privilege rings, ensuring unprivileged user-mode applications cannot read or alter operating system kernel memory.
5. **Dirty bit ($D$)**: Set to 1 by the hardware MMU whenever a processor store instruction modifies data within the page frame. When the page is eventually evicted from RAM, the operating system checks the dirty bit: if $D = 1$, the page must be written back to disk; if $D = 0$, it can be overwritten immediately.
6. **Referenced bit ($R$ or Accessed bit $A$)**: Set to 1 by hardware whenever any byte in the page is read or written. Operating system page replacement algorithms (such as the Clock algorithm) inspect this bit to identify actively used pages.

<Callout tone="orange" label="Confusing virtual address space with physical memory">
Students often confuse the size of the virtual address space with the amount of installed physical RAM. On a 32-bit CPU, every process receives a full $2^{32} = 4\text{ GB}$ virtual address space, even if the computer physically contains only 512 MB of RAM. The 4 GB address space is dictated by the pointer bit width, not by the motherboard DRAM chips.
</Callout>

## Multi-Level (Hierarchical) Page Tables

In a naive design, a single linear array stores the page table. On a 32-bit architecture with 4 KB pages:

- Virtual address space = $2^{32}\text{ bytes} = 4\text{ GB}$.
- Number of pages = $2^{32} / 2^{12} = 2^{20} = 1{,}048{,}576$ pages.
- At 4 bytes per PTE, a single linear page table requires:
  $$1{,}048{,}576 \times 4\text{ bytes} = 4\text{ MB of contiguous physical RAM per process.}$$

If a system runs 250 active processes, 1 GB of physical memory would be consumed by page tables alone, even though most processes only use a few megabytes of actual code and data. On 64-bit architectures with 48-bit virtual addresses, a linear page table would require an impossible 512 gigabytes of storage per process.

### Two-Level Page Tables

To solve this scaling problem, architectures implement **multi-level page tables**. In a two-level paging system (such as 32-bit x86), the 20-bit $VPN$ is partitioned into two 10-bit indices:

| Field | Page Directory Index ($PDI$) | Page Table Index ($PTI$) | Page Offset ($p$) |
|---|---|---|---|
| **Bit Position** | $A_{31} \dots A_{22}$ (10 bits) | $A_{21} \dots A_{12}$ (10 bits) | $A_{11} \dots A_0$ (12 bits) |
| **Indexed Table** | Page Directory | Secondary Page Table | Byte within 4 KB frame |

1. **Page Directory Index (10 bits)**: Indexes into the **Page Directory** (a single 4 KB table containing 1,024 **Page Directory Entries** (PDEs), pointed to by the PTBR/`CR3` register). Each valid PDE contains the physical base address of a secondary page table.
2. **Page Table Index (10 bits)**: Indexes into that secondary **Page Table** (each also 4 KB in size, holding 1,024 PTEs).
3. **Offset (12 bits)**: Indexes the byte within the 4 KB page frame.

The primary benefit is **sparse allocation**. If a program uses only 2 MB of code at address `0x00400000` and 1 MB of stack at address `0xBFFFF000`, the operating system allocates only the top-level Page Directory (4 KB) and two secondary Page Tables (8 KB). The remaining 1,022 entries in the Page Directory are marked invalid ($V = 0$) and require no secondary page tables. Storage drops from 4 MB down to 12 KB per process.

In 64-bit processors, this hierarchy extends to four levels:
- **PML4** (Page Map Level 4)
- **PDPT** (Page Directory Pointer Table)
- **PD** (Page Directory)
- **PT** (Page Table)

## Making it fast: the TLB

Multi-level page tables save memory, but they introduce a severe performance penalty. On a two-level page table, every processor memory reference requires:
1. One memory read to fetch the Page Directory Entry.
2. A second memory read to fetch the Page Table Entry.
3. A third memory access to finally read or write the actual program data operand.

Translating every address would triple memory latency, reducing computer speed by over 60%.

To accelerate **virtual memory** translation and eliminate this overhead, the MMU includes a dedicated hardware cache called the **Translation Lookaside Buffer** (TLB).

The TLB is a small, highly associative hardware cache (typically 64 to 512 entries) containing recently translated $(VPN \to PFN)$ mappings:
1. When the CPU emits a virtual address, the MMU queries the TLB tag array using the $VPN$.
2. **TLB Hit**: If the translation is present and valid, the TLB outputs the $PFN$ in less than 1 clock cycle. The physical address is assembled immediately with zero main memory overhead.
3. **TLB Miss**: If the translation is absent from the TLB, the hardware must perform a **page table walk**:
   - **Hardware Page Table Walker** (x86, ARM): Dedicated finite-state machines in the MMU traverse the hierarchical page tables in memory, load the missing PTE into the TLB, and retry the memory access.
   - **Software-Managed TLB** (MIPS, SPARC): The MMU generates a TLB Miss trap exception. The operating system kernel executes a short, optimized trap handler that fetches the PTE and inserts it into the TLB using privileged instructions.

<Callout tone="orange" label="Confusing TLB misses with page faults">
Do not confuse a TLB miss with a page fault. A **TLB miss** merely means the address translation is not currently cached in the processor's high-speed TLB; the page is almost always already resident in physical RAM, requiring only a quick hardware page table walk (tens of nanoseconds). A **page fault** occurs when the page is completely absent from physical RAM ($V = 0$ in the PTE), requiring an operating system trap and slow secondary storage disk I/O (millions of nanoseconds).
</Callout>

### Process Context and the TLB

Because each process has its own unique virtual address mapping, virtual address `0x00400000` in Process A maps to a completely different physical frame than `0x00400000` in Process B.

When the operating system performs a context switch between processes, older architectures flushed the entire TLB (invalidating all entries). Flushing causes severe performance slowdowns because the new process immediately incurs dozens of compulsory TLB misses.

Modern architectures tag each TLB entry with an **Address Space Identifier** (ASID, on ARM/MIPS) or **Process Context Identifier** (PCID, on x86). The hardware compares both the $VPN$ and the currently active process ASID. This allows translations belonging to multiple different processes to coexist safely inside the TLB across context switches without flushing.

## Page Faults and Thrashing

When a program accesses a virtual page whose PTE has its valid bit cleared ($V = 0$), the MMU cannot produce a physical address. The hardware halts instruction execution and raises a **page fault exception** (a synchronous [hardware trap/interrupt](/courses/microprocessors/interrupts)).

The operating system kernel handles the page fault through several steps:

1. **Verify reference**: The kernel checks whether the virtual address falls within a valid memory segment defined by the process. If invalid (such as dereferencing a NULL pointer), the OS terminates the process with a segmentation violation.
2. **Locate backing store**: The OS locates the requested page block on secondary storage (the disk swap space or mapped executable file).
3. **Select physical frame**: The OS finds an empty page frame in physical RAM. If RAM is full, it invokes a page replacement algorithm (such as [LRU or Clock replacement](/courses/operating-systems/page-replacement-and-thrashing#least-recently-used-lru)) to evict an existing resident page. If the evicted page has its dirty bit set ($D = 1$), it writes the page back to disk.
4. **Disk I/O transfer**: The OS reads the requested page from disk into the allocated frame. Secondary storage is magnetic or flash-based: reading a 4 KB page takes between 10 microseconds (NVMe SSD) and 10 milliseconds (mechanical disk). The OS switches the CPU to another runnable thread while the disk transfer proceeds.
5. **Update PTE**: When the I/O transfer finishes, the OS records the new $PFN$ in the page table, sets the valid bit to 1 ($V = 1$), and clears the dirty bit ($D = 0$).
6. **Restart instruction**: The OS restores process state and restarts the exact machine instruction that triggered the page fault. This time, the translation hits in the page table, loads into the TLB, and completes normally.

<Callout tone="orange" label="Thrashing">
Because disk access latency ($10\text{ ms}$) is approximately $100{,}000$ to $1{,}000{,}000$ times slower than DRAM access latency ($50\text{ ns}$), page faults are exceptionally expensive. If the combined working sets of active processes exceed physical RAM capacity, the system spends virtually 100% of its execution time swapping pages to and from disk. This condition is called **thrashing**. In thrashing, CPU utilization drops toward zero while disk queues stay saturated.
</Callout>

## Interaction Between Caches and Virtual Memory

When an architecture contains both a cache and virtual memory, hardware must decide in what order translation and cache lookup occur:

| Architecture | Index Derivation | Tag Comparison | Advantages | Drawbacks |
|---|---|---|---|---|
| **PIPT** | Physical Address Bits | Physical Address Bits | Zero aliasing | TLB on critical path before cache lookup |
| **VIVT** | Virtual Address Bits | Virtual Address Bits | Fast (no TLB delay) | Aliasing and context switch flushes |
| **VIPT** | Virtual Address Bits | Physical Address Bits | Parallel TLB and cache lookup | Way size constrained by page size |

1. **Physically Indexed, Physically Tagged (PIPT)**: The virtual address is translated by the TLB first. The resulting physical address is then used to index the cache and compare tags. PIPT is completely free of aliasing problems, but it places the TLB latency directly on the critical path before the cache can even begin line lookup.
2. **Virtually Indexed, Virtually Tagged (VIVT)**: Both index and tag come from the virtual address. Caching occurs with zero TLB delay. However, VIVT suffers from cache coherency pitfalls:
   - **Homonyms (Aliasing)**: The same virtual address in two different processes refers to two distinct physical frames. Without flushing the cache or tracking process IDs, Process B could read stale data belonging to Process A.
   - **Synonyms**: Two different virtual addresses refer to the same physical frame. The same memory byte could be cached in two different lines, causing inconsistency if one is modified.
3. **Virtually Indexed, Physically Tagged (VIPT)**: The high-performance compromise used in modern L1 caches.

### Why VIPT Dominates Modern L1 Caches

Recall that a 4 KB page has 12 offset bits ($A_{11} \dots A_0$). Because the page offset is never modified during address translation, the lower 12 bits of a virtual address are **identical** to the lower 12 bits of the physical address.

In a VIPT cache, the cache controller extracts the set index bits directly from these lower offset bits. The cache array can look up the set in parallel while the TLB translates the $VPN$ into the $PFN$. When the cache line tags are read out from the cache SRAM, the physical frame number arrives from the TLB just in time to compare tags.

<Callout tone="orange" label="VIPT aliasing when cache way exceeds page size">
If the size of a single cache way exceeds the page size ($\text{Way Size} > \text{Page Size}$), the cache index requires bits from the Virtual Page Number ($VPN$). Because the operating system can map multiple virtual pages to the same physical frame with different high-order address bits, the exact same physical byte can map to two distinct cache sets simultaneously. This creates cache synonyms, where a write to one cache line does not update the other, corrupting program data.
</Callout>

<Callout tone="sky" label="The VIPT aliasing limit">
To guarantee that a VIPT cache never suffers from aliasing, the set index bits ($s$) plus the block offset bits ($b$) must fit entirely within the page offset bits ($p$):
$$
s + b \le p \iff \frac{\text{Total Cache Capacity}}{k} \le \text{Page Size}
$$
In words: **The size of each cache way must not exceed the page size.** For a 4 KB page size, an 8-way set-associative L1 cache can be up to $8 \times 4\text{ KB} = 32\text{ KB}$ without any aliasing risk.
</Callout>

<Callout tone="violet" label="Comparing cache and virtual memory">
Caches and virtual memory solve the same problem at two different scales:
- A cache block corresponds to a virtual memory page.
- A cache miss corresponds to a page fault.
- Cache mapping corresponds to address translation.
- A cache write buffer corresponds to operating system dirty page writeback daemons.
A cache is managed 100% by hardware because a miss costs nanoseconds. Virtual memory page faults are managed by operating system software because a disk transfer takes milliseconds, leaving plenty of time for software routines to execute.
</Callout>

<Callout tone="mint" label="Key takeaway">
Virtual memory provides isolation, protection, and a large address space by translating virtual pages to physical frames via page tables. The TLB caches active translations to preserve memory performance. VIPT organization allows L1 caches to index in parallel with TLB translation, delivering single-cycle access while maintaining system-wide memory protection.
</Callout>

<ModelAnswer title="Problem 1: Two-level hierarchical page table address decoding and memory overhead">
A 32-bit byte-addressed computer architecture features a two-level hierarchical page table system with 4 KB pages ($2^{12}$ bytes).
The 32-bit virtual address is partitioned as follows:
- Bits $A_{31} \dots A_{22}$ (10 bits): Page Directory Index
- Bits $A_{21} \dots A_{12}$ (10 bits): Page Table Index
- Bits $A_{11} \dots A_0$ (12 bits): Page Offset

Each Page Directory Entry (PDE) and Page Table Entry (PTE) is 4 bytes wide.
The Page Table Base Register (PTBR) contains physical address `0x00200000`.

1. Decode the virtual address `0x20803456`:
   - Determine the Page Directory Index (in decimal and hexadecimal).
   - Determine the Page Table Index (in decimal and hexadecimal).
   - Determine the Page Offset (in hexadecimal).
   - Calculate the exact byte physical address of the PDE within the Page Directory.
2. Consider a process whose active address space consists of:
   - Code: 8 MB starting at virtual address `0x00000000`.
   - Stack: 4 MB starting at virtual address `0xFFC00000` (growing downward).
   Calculate the total memory (in bytes and kilobytes) required to store the page tables for this process under:
   - A single-level (linear) page table.
   - The two-level hierarchical page table.

---

**Solution:**

**Part 1: Address decoding for `0x20803456`:**
Convert `0x20803456` into 32-bit binary:
$$
\text{0x20803456} = 0010\ 0000\ 1000\ 0000\ 0011\ 0100\ 0101\ 0110_2
$$
Partition the bit fields:
- Directory bits ($A_{31} \dots A_{22}$): `0010 0000 10` = `0x082` = 130 in decimal.
- Page Table bits ($A_{21} \dots A_{12}$): `00 0000 0011` = `0x003` = 3 in decimal.
- Offset bits ($A_{11} \dots A_0$): `0100 0101 0110` = `0x456`.

Physical address of the PDE:
Each PDE is 4 bytes wide. The Page Directory starts at base address `0x00200000`.
$$
\text{PDE Address} = \text{PTBR} + (\text{Directory Index} \times 4\text{ bytes}) = \text{0x00200000} + (130 \times 4) = \text{0x00200000} + 520 = \text{0x00200208}
$$

**Part 2: Page table memory overhead comparison:**

*Single-level page table:*
A linear table must contain an entry for every virtual page in the entire 4 GB address space, regardless of whether the page is allocated:
$$
\text{Total pages} = \frac{4\text{ GB}}{4\text{ KB}} = 2^{20} = 1{,}048{,}576\text{ entries}
$$
$$
\text{Storage} = 1{,}048{,}576 \times 4\text{ bytes} = 4{,}194{,}304\text{ bytes} = 4\text{ MB}
$$

*Two-level page table:*
- The top-level Page Directory is always allocated:
  1 Page Directory = 1,024 entries $\times 4\text{ bytes} = 4\text{ KB}$ (1 page frame).
- Code segment: 8 MB.
  Each secondary Page Table maps $1{,}024\text{ pages} \times 4\text{ KB per page} = 4\text{ MB}$ of virtual address space.
  Therefore, an 8 MB code segment requires:
  $$8\text{ MB} / 4\text{ MB per table} = 2\text{ secondary Page Tables}$$
- Stack segment: 4 MB.
  The 4 MB stack segment requires:
  $$4\text{ MB} / 4\text{ MB per table} = 1\text{ secondary Page Table}$$
- Total secondary tables allocated = $2 + 1 = 3$ Page Tables.
  Each secondary Page Table occupies $1{,}024 \times 4\text{ bytes} = 4\text{ KB}$.
  Storage for secondary tables = $3 \times 4\text{ KB} = 12\text{ KB}$.

Total page table memory consumed:
$$
\text{Total Memory}_{\text{two-level}} = 4\text{ KB (Directory)} + 12\text{ KB (Tables)} = 16\text{ KB}
$$
The two-level hierarchical organization reduces page table memory footprint from 4,096 KB down to 16 KB (a 99.6% reduction in memory overhead).
</ModelAnswer>

<ModelAnswer title="Problem 2: Effective Memory Access Time (EMAT) with TLB and page faults">
A computer system employs a two-level page table and an on-chip Translation Lookaside Buffer (TLB).
The system timing and probability parameters are:
- TLB lookup time ($t_{\text{TLB}}$): 2 ns
- Main memory access time ($t_{\text{mem}}$): 50 ns
- Disk page fault service time ($t_{\text{disk}}$): 8 ms ($8{,}000{,}000\text{ ns}$)
- TLB hit rate ($\alpha$): 98% (0.98)
- When a TLB miss occurs, the page is resident in memory (no page fault) 99.99% of the time. A page fault occurs on only 0.01% ($p = 0.0001$) of TLB misses.

1. Derive the expression for Effective Memory Access Time (EMAT) and calculate EMAT in nanoseconds.
2. What would the effective memory access time be if the system had no TLB (every translation walked the two-level page table in memory, assuming zero page faults)?
3. What is the maximum allowable page fault rate $p_{\max}$ (relative to all memory references) if the average access time must not exceed 65 ns?

---

**Solution:**

**Part 1: EMAT Calculation:**
An access proceeds through three possible paths:
1. **TLB Hit (probability $\alpha = 0.98$)**:
   The physical address is produced in $t_{\text{TLB}} = 2\text{ ns}$. Then 1 memory access fetches the data operand ($t_{\text{mem}} = 50\text{ ns}$).
   $$t_1 = t_{\text{TLB}} + t_{\text{mem}} = 2 + 50 = 52\text{ ns}$$
2. **TLB Miss, Memory Hit (probability $(1 - \alpha)(1 - p) = 0.02 \times 0.9999 \approx 0.019998$)**:
   The TLB lookup fails ($2\text{ ns}$). The MMU accesses the Page Directory ($50\text{ ns}$), then the Page Table ($50\text{ ns}$), and finally fetches the data operand ($50\text{ ns}$).
   $$t_2 = t_{\text{TLB}} + 2 \times t_{\text{mem}} + t_{\text{mem}} = 2 + 100 + 50 = 152\text{ ns}$$
3. **TLB Miss, Page Fault (probability $(1 - \alpha) \times p = 0.02 \times 0.0001 = 2 \times 10^{-6}$)**:
   The page must be fetched from disk ($t_{\text{disk}} = 8{,}000{,}000\text{ ns}$) before accessing data:
   $$t_3 \approx 8{,}000{,}000\text{ ns}$$

Calculating EMAT:
$$
\text{EMAT} = \alpha \times t_1 + (1 - \alpha)(1 - p) \times t_2 + (1 - \alpha)p \times t_3
$$
$$
\text{EMAT} = (0.98 \times 52) + (0.019998 \times 152) + (2 \times 10^{-6} \times 8{,}000{,}000)
$$
$$
\text{EMAT} = 50.96 + 3.0397 + 16.0 = 70.00\text{ ns}
$$
Notice that even a tiny page fault probability of 1 in 500,000 accesses ($2 \times 10^{-6}$) adds 16 ns (nearly 23%) to the entire system's average access latency.

**Part 2: Access time without TLB (zero page faults):**
Without a TLB, every reference requires walking the two-level page table (2 memory accesses) followed by the actual data access:
$$
T_{\text{no TLB}} = 3 \times t_{\text{mem}} = 3 \times 50\text{ ns} = 150\text{ ns}
$$
The TLB speeds up average memory access from 150 ns down to 70 ns (even with page faults included).

**Part 3: Maximum allowable page fault rate for $\text{EMAT} \le 65\text{ ns}$:**
Let $P_f$ be the global page fault probability across all memory references:
$$
\text{EMAT} \approx (1 - P_f) \times (\alpha \times 52 + (1 - \alpha) \times 152) + P_f \times 8{,}000{,}000 \le 65
$$
With $\alpha = 0.98$, the fault-free access time is:
$$
T_{\text{fault-free}} = 0.98(52) + 0.02(152) = 50.96 + 3.04 = 54\text{ ns}
$$
Now substitute into the equation:
$$
54 + P_f \times (8{,}000{,}000 - 54) \le 65
$$
$$
P_f \times 8{,}000{,}000 \le 65 - 54 = 11\text{ ns}
$$
$$
P_f \le \frac{11}{8{,}000{,}000} \approx 1.375 \times 10^{-6}
$$
To maintain an average memory access time below 65 ns, no more than 1 out of every 727,000 memory references may trigger a page fault.
</ModelAnswer>
