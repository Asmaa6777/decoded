# Cache Policies: Replacement, Writes and Block Size

[Cache mapping](/courses/computer-architecture/cache-mapping) decides where in a cache an address can go. But mapping is only half the design. Hardware engineers must also choose three policies: which block to evict when a set is full, how to handle memory writes so data stays consistent, and how large each block should be.

The goal is to keep **average memory access time** (AMAT) as low as possible while keeping data consistent across the system.

## The 3Cs Miss Taxonomy

To diagnose why cache misses occur, Mark Hill and David Patterson developed the **3Cs model**, which categorizes every cache miss into three primary causes:

1. **Compulsory misses (Cold misses)**: The very first access to a memory block. The block has never been in the cache, so the miss is unavoidable unless hardware or software prefetching predicts the access beforehand.
2. **Capacity misses**: The cache cannot contain all the blocks needed during program execution. If a program repeatedly accesses a working set of 128 KB on a 64 KB cache, blocks will be repeatedly evicted and re-fetched even if the cache has infinite associativity.
3. **Conflict misses (Collision misses)**: Multiple distinct memory blocks map to the same set in a direct-mapped or set-associative cache. These misses occur because of non-uniform placement and would vanish if the cache were fully associative with the same capacity.
4. **Coherence misses (The 4th C)**: In multiprocessor and multicore systems, a cache miss triggered when another processor core writes to a shared cache block, causing the local copy to be invalidated.

## What gets thrown out?

When a cache set is completely full and a miss brings in a new block, hardware must pick an existing line to throw out. A cache **replacement policy** governs this decision. A direct-mapped cache has no choice because each address maps to only one line. Set-associative and fully associative caches need an eviction rule, such as **LRU** (Least Recently Used), FIFO, or random replacement.

### Least Recently Used (LRU)

The **Least Recently Used** (LRU) policy evicts the block that has remained unreferenced for the longest period of time.

- **Rationale**: Exploits temporal locality. A block accessed recently is likely to be accessed again; a block untouched for thousands of cycles is the least likely to be needed soon.
- **Hardware implementation**:
  - In a 2-way set-associative cache, LRU requires exactly 1 bit per set. Setting the bit to 0 or 1 indicates which of the two ways was accessed most recently.
  - In a 4-way set-associative cache, tracking true LRU order among 4 ways requires $\log_2(4!) = \log_2(24) \approx 5$ or 6 bits per set, or a $4 \times 4$ triangular bit matrix.
  - For 8-way and 16-way caches, exact LRU becomes too complex and consumes too much power and silicon area.
- **Pseudo-LRU (Tree-PLRU)**: Modern high-associativity caches approximate LRU using a binary decision tree. For an 8-way cache, each set stores 7 tracking bits ($B_0 \dots B_6$) organized as a 3-level binary tree:
  - Root bit $B_0$ points to the left half (Ways 0 to 3) or right half (Ways 4 to 7).
  - Level-1 bits $B_1, B_2$ point to pairs of ways (Ways 0-1 vs 2-3, and Ways 4-5 vs 6-7).
  - Level-2 bits $B_3 \dots B_6$ point to individual ways.
  When an access hits Way 2, the hardware flips all bits along the path to Way 2 so they point *away* from Way 2. When an eviction occurs, hardware follows the arrows to find an unreferenced **victim block**.

### First-In, First-Out (FIFO)

The **First-In, First-Out** (FIFO) policy evicts the block that has been resident in the set for the longest time, regardless of how frequently or recently it was accessed.

- **Hardware implementation**: Simple circular counter per set pointing to the next victim way.
- **Drawback**: FIFO frequently evicts critical loop variables, lookup tables, and OS kernel routines simply because they were loaded early during program startup.

### Random Replacement

The **Random** policy selects a victim line uniformly at random using a pseudorandom number generator or clock-driven counter.

- **Hardware implementation**: Requires zero tracking bits in the cache tag array.
- **Performance**: In large caches with high associativity ($\ge 8$-way), random replacement performs surprisingly close to LRU (within 1 to 2% miss rate) because the probability of accidentally picking the most critical active line is small.

### Optimal Replacement (MIN / Belady's Algorithm)

The **Optimal** (or MIN) algorithm evicts the block whose next access will occur furthest in the future.

- **Theoretical bound**: Belady proved that MIN achieves the lowest possible miss rate for any fixed-size cache.
- **Why it cannot be built**: Hardware cannot look into the future. MIN serves as an offline theoretical benchmark to measure how close practical policies come to perfection.

## What happens on a write?

Reads leave cache contents alone. Writes modify data. When the CPU writes a word to the cache, cache and main memory temporarily disagree. Maintaining **cache coherency** and data consistency across main memory and other processor cores requires clear write policies. Architecture defines two choices for write hits and two for write misses.

### Write Hit Policies

#### 1. Write-Through

In a **write-through** cache, every write to the cache simultaneously updates main memory.

- **Advantage**: Main memory always holds a clean, up-to-date copy of data. Simplifies cache coherence in multicore systems and makes recovery after power loss or fault straightforward.
- **Disadvantage**: Main memory takes 50 to 100 ns to complete a write. If roughly 15% of all instructions are stores, waiting for DRAM on every store would stall the CPU pipeline continuously.
- **Write Buffer**: To avoid processor stalls, write-through caches place a **write buffer** (a small FIFO queue, typically 4 to 16 entries) between the cache and memory bus. The processor writes the data to both the cache and the write buffer in 1 cycle and continues execution immediately. The memory controller drains the buffer to DRAM in the background.

<Callout tone="orange" label="Write buffer saturation">
A write buffer hides memory latency only if writes arrive in bursts followed by gaps. If a tight loop performs continuous stores faster than DRAM can absorb them, the write buffer fills to capacity. Subsequent stores stall the execution pipeline until the buffer drains.
</Callout>

#### 2. Write-Back (Copy-Back)

In a **write-back** cache, writes update only the cache line. Main memory is not updated immediately.

- **Dirty Bit ($D$)**: Each cache line includes a 1-bit **dirty flag** (or modified bit). When the processor writes to a line, the hardware marks its dirty bit as 1.
- **Memory Update**: Main memory is updated only when a dirty line is evicted to make room for a new block. If a clean line (dirty bit 0) is evicted, it is discarded immediately with zero bus writes.
- **Advantage**: It cuts memory bus traffic. A loop modifying an array element 10,000 times generates 10,000 cache writes, but only one write to main memory when the block is eventually replaced.
- **Disadvantage**: More complex hardware. Evicting a dirty block requires two distinct memory operations: writing back the dirty victim to DRAM, and reading the incoming block into the cache.
- **Write-Back Buffer**: When an eviction forces out a dirty block, waiting for it to write all the way to DRAM before fetching the new block would double the miss penalty. Fast caches copy the dirty block into a temporary **write-back buffer** (or victim buffer). The CPU fetches the requested block from DRAM right away and resumes execution. The memory controller writes the dirty block from the buffer to DRAM in the background.

### Write Miss Policies

When the processor attempts to write to an address that is not in the cache, two approaches exist:

1. **Write-Allocate (Fetch-on-Write)**: The missed block is fetched from main memory into the cache, and the write is executed in the cache line. This is the natural pairing for **write-back** caches, because subsequent writes to that block will hit in the cache.
2. **No-Write-Allocate (Write-Around)**: The data is written directly to main memory without loading the block into the cache. This is the standard pairing for **write-through** caches, preventing non-repeated writes from evicting useful cached blocks.

<Callout tone="orange" label="Assuming write-back always generates less bus traffic">
Write-back cuts bus traffic when a program repeatedly updates the same cached block. But when write misses dominate, it can create more bus traffic than write-through. Under write-allocate, a write miss loads an entire 64-byte block from DRAM, even if the program wrote only a single 4-byte integer. In contrast, write-through with no-write-allocate sends only the 4-byte store across the bus without fetching the surrounding block.
</Callout>

<Callout tone="violet" label="Multicore cache coherence">
On modern multi-core chips, each core contains a private L1 and L2 cache. If Core 0 writes to address $X$ in its private write-back cache, Core 1 reading address $X$ from its own cache could read stale data. Hardware **cache coherence protocols** (such as MESI: Modified, Exclusive, Shared, Invalid) monitor the system bus and invalidate or update private cache lines whenever another core writes to a shared memory address.
</Callout>

## Block Size Trade-Offs

Block size represents a trade-off between spatial locality and transfer overhead:

1. **Increasing block size (from 16 to 64 bytes)**:
   - Takes advantage of spatial locality by fetching neighbouring words that the program will likely need.
   - Reduces the number of compulsory misses.
   - Reduces the number of tag bits required per cache byte (since larger blocks mean fewer total lines).
2. **Excessively large blocks (beyond 128 bytes)**:
   - For a fixed total cache capacity, larger blocks mean fewer total sets. This causes more conflict and capacity misses.
   - **Miss penalty increases**: Transferring a 256-byte block across a 64-bit bus requires 32 sequential transfers, tying up the memory controller and stalling the CPU for dozens of additional cycles.
   - Spatial locality diminishes: if the program only uses 4 bytes of a 256-byte block, the remaining 252 bytes waste memory bandwidth and displace other useful data (**cache pollution**).

Modern desktop and server processors universally standardize on **64-byte blocks**.

## Average Memory Access Time (AMAT)

The standard formula for memory subsystem performance is **Average Memory Access Time** (AMAT):

$$
\text{AMAT} = t_{\text{hit}} + (\text{Miss Rate} \times \text{Miss Penalty})
$$

Where:
- $t_{\text{hit}}$ is the time to hit in the cache (typically 1 to 4 clock cycles for L1).
- $\text{Miss Rate}$ is the fraction of all memory accesses that miss.
- $\text{Miss Penalty}$ is the additional time required to fetch the block from the lower level of the memory hierarchy.

Every memory reference queries the cache first. The processor cannot know whether a request will hit or miss until it searches the tag array. Therefore, the cache hit latency $t_{\text{hit}}$ is spent on every reference, whether it hits or misses.

<Callout tone="orange" label="Forgetting hit latency on cache misses">
A frequent student error when calculating total access time on a miss is forgetting $t_{\text{hit}}$. Students compute $\text{Latency} = \text{Miss Penalty}$, assuming the cache was bypassed. In reality, the processor spent $t_{\text{hit}}$ cycles checking the cache tags before declaring the miss and initiating the memory fetch. The total time spent on a miss is $t_{\text{hit}} + \text{Miss Penalty}$.
</Callout>

### Multi-Level Cache Hierarchies

To overcome the latency-capacity dilemma, modern processors use a multi-level hierarchy:

- **Level 1 (L1)**: Small (32 KB to 64 KB per core), fast (1 to 4 cycles, ~1 ns). Split into dedicated **L1 Instruction Cache (L1 I-Cache)** and **L1 Data Cache (L1 D-Cache)** to allow simultaneous instruction fetching and data load/store without structural hazards.
- **Level 2 (L2)**: Moderate capacity (512 KB to 2 MB per core), fast (10 to 14 cycles, ~3 to 4 ns), unified (holds both instructions and data).
- **Level 3 (L3)**: Large capacity (16 MB to 96 MB shared across all cores), moderate latency (30 to 50 cycles, ~10 to 15 ns).

The multi-level AMAT equation expands as:

$$
\text{AMAT} = t_{L1} + \text{MR}_{L1} \times \left( t_{L2} + \text{MR}_{L2} \times \left( t_{L3} + \text{MR}_{L3} \times t_{\text{mem}} \right) \right)
$$

<Callout tone="orange" label="Confusing local and global miss rates">
In multi-level cache problems, students frequently mix up local and global miss rates. If L1 has a 4% miss rate ($\text{MR}_{L1} = 0.04$) and L2 has a 20% local miss rate ($\text{MR}_{L2,\text{local}} = 0.20$), only $0.04 \times 0.20 = 0.008$ (or 0.8%) of all CPU instructions reach main memory. Plugging 20% directly into the main memory miss penalty formula overestimates DRAM traffic by a factor of 25.
</Callout>

<Callout tone="sky" label="Local vs. global miss rate">
When analyzing multi-level caches:
- **Local Miss Rate ($\text{MR}_{\text{local}}$)**: The fraction of references arriving at that specific cache level that miss.
  $$\text{MR}_{L2\text{, local}} = \frac{\text{Misses at L2}}{\text{Total accesses to L2}}$$
- **Global Miss Rate ($\text{MR}_{\text{global}}$)**: The fraction of all CPU memory references that miss at that cache level.
  $$\text{MR}_{L2\text{, global}} = \frac{\text{Misses at L2}}{\text{Total CPU references}} = \text{MR}_{L1} \times \text{MR}_{L2\text{, local}}$$
</Callout>

<Callout tone="mint" label="Key takeaway">
Cache performance is governed by the interaction of replacement, write, and sizing policies. LRU preserves temporally active data, while write-back with write-allocate prevents memory bus saturation. Multi-level cache hierarchies minimize AMAT by combining small, ultra-fast L1 split caches with large, unified L2 and L3 caches.
</Callout>

## Exam-Style Practice

<ModelAnswer title="Problem 1: Multi-level cache AMAT and performance analysis">
A processor has a clock frequency of 2 GHz (clock cycle time $\tau = 0.5\text{ ns}$).
The memory hierarchy consists of a split L1 cache, a unified L2 cache, and main memory with the following parameters:

- L1 hit time: 1 clock cycle (0.5 ns)
- L1 miss rate: 4% (0.04)
- L2 hit time: 10 clock cycles (5 ns)
- L2 local miss rate: 20% (0.20)
- Main memory access latency: 100 clock cycles (50 ns)

1. Calculate the global miss rate for the L2 cache.
2. Calculate the Average Memory Access Time (AMAT) in clock cycles and in nanoseconds.
3. If an architectural redesign reduces the L2 local miss rate from 20% to 10%, calculate the new AMAT and the overall memory speedup.

---

**Solution:**

**Part 1: Global Miss Rate for L2:**
$$
\text{Global MR}_{L2} = \text{MR}_{L1} \times \text{Local MR}_{L2} = 0.04 \times 0.20 = 0.008\text{ (or 0.8 percent)}
$$
Only 0.8% of all memory accesses issued by the CPU reach main memory.

**Part 2: Baseline AMAT Calculation:**
Using the multi-level AMAT formula:
$$
\text{AMAT} = t_{L1} + \text{MR}_{L1} \times \text{Miss Penalty}_{L1}
$$
The miss penalty of L1 is the time spent resolving the miss through L2:
$$
\text{Miss Penalty}_{L1} = t_{L2} + \text{Local MR}_{L2} \times t_{\text{mem}}
$$
Substituting the given cycle counts:
$$
\text{Miss Penalty}_{L1} = 10\text{ cycles} + 0.20 \times 100\text{ cycles} = 10 + 20 = 30\text{ cycles}
$$
Now compute overall AMAT in clock cycles:
$$
\text{AMAT} = 1\text{ cycle} + 0.04 \times 30\text{ cycles} = 1 + 1.2 = 2.2\text{ clock cycles}
$$
Convert to nanoseconds ($\tau = 0.5\text{ ns}$):
$$
\text{AMAT} = 2.2 \times 0.5\text{ ns} = 1.1\text{ ns}
$$

**Part 3: Redesign with L2 Local Miss Rate = 10%:**
Recalculate the L1 miss penalty:
$$
\text{Miss Penalty}_{L1,\text{new}} = 10\text{ cycles} + 0.10 \times 100\text{ cycles} = 10 + 10 = 20\text{ cycles}
$$
Recalculate AMAT:
$$
\text{AMAT}_{\text{new}} = 1\text{ cycle} + 0.04 \times 20\text{ cycles} = 1 + 0.8 = 1.8\text{ clock cycles}
$$
In nanoseconds:
$$
\text{AMAT}_{\text{new}} = 1.8 \times 0.5\text{ ns} = 0.9\text{ ns}
$$
Memory speedup achieved:
$$
\text{Speedup} = \frac{\text{AMAT}_{\text{baseline}}}{\text{AMAT}_{\text{new}}} = \frac{2.2}{1.8} \approx 1.222
$$
This represents a 22.2% reduction in memory access latency.
</ModelAnswer>

<ModelAnswer title="Problem 2: Memory bus traffic under write-through vs. write-back">
A processor executes a benchmark program of 1,000,000 instructions.
Memory reference statistics for the benchmark:
- 30% of instructions are memory data reads (loads).
- 10% of instructions are memory data writes (stores).
- The remaining 60% are ALU operations that perform no data memory accesses.
- Assume instruction fetch accesses are handled by a separate dedicated I-cache that incurs zero data bus traffic.

The data cache has a block size of 64 bytes. The data miss rate for reads is 3%, and the data miss rate for writes is 5%.
In the write-back cache, 40% of evicted blocks are dirty ($D = 1$).
Assume a write-allocate policy for write-back, and a no-write-allocate policy for write-through. Assume word writes transfer 4 bytes.

Calculate the total number of bytes transferred across the main memory bus for:
1. A write-through cache with a write buffer.
2. A write-back cache.

---

**Solution:**

**Total memory references:**
- Read instructions ($N_{\text{reads}}$) = $1{,}000{,}000 \times 0.30 = 300{,}000$ reads.
- Write instructions ($N_{\text{writes}}$) = $1{,}000{,}000 \times 0.10 = 100{,}000$ writes.

**Part 1: Write-Through (No-Write-Allocate):**
In write-through:
- Every read miss fetches a full 64-byte block from memory.
  $$\text{Read misses} = 300{,}000 \times 0.03 = 9{,}000\text{ misses}$$
  $$\text{Bytes from read misses} = 9{,}000 \times 64\text{ bytes} = 576{,}000\text{ bytes}$$
- Because the cache is no-write-allocate, write misses do not fetch blocks.
- Every write instruction (both hits and misses) must write its 4-byte word directly to main memory:
  $$\text{Bytes from writes} = 100{,}000 \times 4\text{ bytes} = 400{,}000\text{ bytes}$$
- Total memory bus bytes:
  $$\text{Total Bytes}_{\text{WT}} = 576{,}000 + 400{,}000 = 976{,}000\text{ bytes} \approx 953.1\text{ KB}$$

**Part 2: Write-Back (Write-Allocate):**
In write-back:
- Read misses fetch a 64-byte block:
  $$\text{Read misses} = 300{,}000 \times 0.03 = 9{,}000\text{ blocks}$$
- Write misses fetch a 64-byte block (due to write-allocate):
  $$\text{Write misses} = 100{,}000 \times 0.05 = 5{,}000\text{ blocks}$$
- Total block fetches = $9{,}000 + 5{,}000 = 14{,}000$ blocks.
  $$\text{Bytes fetched into cache} = 14{,}000 \times 64\text{ bytes} = 896{,}000\text{ bytes}$$
- Each of these 14,000 block allocations causes an eviction.
  Of the evicted blocks, 40% are dirty and must be written back to main memory:
  $$\text{Evicted dirty blocks} = 14{,}000 \times 0.40 = 5{,}600\text{ blocks}$$
  $$\text{Bytes written back to memory} = 5{,}600 \times 64\text{ bytes} = 358{,}400\text{ bytes}$$
- Total memory bus bytes:
  $$\text{Total Bytes}_{\text{WB}} = 896{,}000 + 358{,}400 = 1{,}254{,}400\text{ bytes} \approx 1{,}225\text{ KB}$$

Notice that when the write miss rate is high and blocks are large (64 bytes vs 4-byte words), write-allocate fetches 64 bytes for each miss. However, if the program demonstrates temporal locality where writes repeatedly update existing cached blocks (write hit rate 95%), write-back performs all repeated writes locally at zero memory bus cost.
</ModelAnswer>
