# Recipes, Programs, and Proof

The standard definition of an algorithm sounds simple:

> An **algorithm** is a well-defined procedure that takes some input and turns it into some output in a finite number of steps.

Another common phrasing calls an algorithm a **sequence of computational steps that transform the input into the output**.

A cooking recipe matches that idea. Take flour, eggs, and milk, whisk them together, pour the batter, flip when bubbles appear, and stop after five pancakes. The recipe has inputs, steps, an output, and an end. What makes something an *algorithm* is how strictly each part is defined. The rest of this course builds on that strict definition.

## Problems and instances

An algorithm is a tool for solving a **computational problem**. The problem and the algorithm do different jobs:

- The **problem** says *what* we want: which inputs are allowed, and what output each one should get. This is the input/output relationship.
- The **algorithm** says *how* to get there: one specific step-by-step procedure that produces that output.

Here is the sorting problem, written the way textbooks state it:

- **Input:** a sequence of $n$ numbers $\langle a_1, a_2, \ldots, a_n \rangle$.
- **Output:** a permutation (a reordering) $\langle a'_1, a'_2, \ldots, a'_n \rangle$ of those same numbers, such that $a'_1 \le a'_2 \le \cdots \le a'_n$.

One particular input is called an **instance** of the problem. $\langle 8, 1, 4, 9, 3, 7 \rangle$ is an instance of sorting, and the right output for it is $\langle 1, 3, 4, 7, 8, 9 \rangle$. A problem has infinitely many instances. An algorithm has to handle all of them.

The problem statement does not specify *how* to sort. Selection sort, merge sort, and quick sort are three different algorithms for this single problem, and module 1 covers each of them.

<Callout tone="orange" label="Common mistake: mixing up problem and instance">
When asked for an instance of the searching problem, students often describe the problem again: "find a value in an array." An instance is one concrete input with actual values: "find 7 in ⟨3, 7, 1⟩." The problem is the whole set of such inputs, paired with the rule defining the correct output.
</Callout>

## What "well-defined" demands

A procedure counts as an algorithm only if it has all of these:

- **Input.** Zero or more values it starts from. (Zero is allowed: "print the first 10 primes" needs no input.)
- **Output.** At least one result. A procedure that produces nothing has done nothing.
- **Definiteness.** Every step is precise. "Whisk until it looks right" is vague. "Whisk for 60 seconds" is precise.
- **Finiteness.** It *must* stop. A loop that runs forever on some input is a bug.
- **Effectiveness.** Each step is basic enough to carry out with a pencil or on a CPU.

We also want algorithms to be *efficient* (they do not waste time or memory) and *understandable* (other programmers can read and verify them). These two goals drive algorithm design and analysis.

Many course notes list these **properties of an algorithm** in plain sentences instead of one-word names. They are the same ideas:

| How notes often say it | The name used above |
| --- | --- |
| Takes zero or more inputs | Input |
| Results in one or more outputs | Output |
| Each step can be easily understood by someone reading it | Definiteness |
| Must terminate after a finite number of steps | Finiteness |
| All operations can be carried out in a finite amount of time | Effectiveness |
| Should be efficient and flexible, and use as little memory as possible | Efficiency |
| Should be concise and compact, so its correctness is easy to check | Understandable |

"Flexible" means the procedure works on every valid input rather than just one sample input. The next section calls this property *generality*.

Finiteness and effectiveness are easy to confuse because both involve limits on steps. **Finiteness** applies to the whole algorithm: the total number of steps must end. **Effectiveness** applies to each single step: each operation must be possible to complete. For example, "add 1 to x, forever" fails finiteness, even though each addition is easy. "Write down every digit of π" fails effectiveness because that single operation can never finish.

## What design and analysis aim for

The course is called design *and* analysis because there are two jobs:

- **Design:** find an algorithm that solves the problem at the lowest cost.
- **Analysis:** predict that cost before running anything: how much **time** and **memory** the algorithm will need, and how that grows as the input grows.

A good algorithm is judged on five things:

- **Efficiency:** time and space. Most of this course is about measuring this.
- **Simplicity:** a simpler algorithm is easier to understand, prove and code, and has fewer places for bugs to hide.
- **Generality:** it handles the full range of inputs, including the special cases: an empty array, one element, all values equal.
- **Optimality:** no other algorithm for the same problem can run faster or use less space. For example, no sort that compares elements can beat about $n \log n$ comparisons in the worst case (here $n$ is the number of items, and $\log n$, which the [next lesson](/courses/algorithm-design-and-analysis/counting-steps#growth-is-what-matters) explains, counts how many times you can halve $n$), so merge sort is optimal in that sense. Advanced Algorithms [proves this lower bound](/courses/advanced-algorithms/sorting-lower-bounds#the-lower-bound).
- **Implementation:** how the algorithm's data and operations map to code. An algorithm that frequently requests the smallest remaining item needs a suitable data structure to supply it quickly.

Textbooks often group these goals as the **basic issues** of algorithm study: designing algorithms, expressing them in code, proving them correct, analyzing efficiency, and evaluating optimality.

## Correctness

An algorithm is **correct** if, for *every* valid input instance, it halts and produces the correct output.

That means every valid input. A sorting algorithm that works on 99.9% of arrays and silently scrambles the rest is still incorrect. Testing can show that a bug exists, but only reasoning can prove none exist. For loops, that reasoning is a [loop invariant](/courses/discrete-mathematics/loop-invariants#what-a-loop-invariant-is).

<Callout tone="orange" label="Why this matters at work">
Most production incidents do not stem from slow algorithms. They happen when code fails on an unexpected input: an empty list, duplicate values, negative numbers, or boundary cases. Asking "does this work for *every* input?" catches those edge cases before users encounter them.
</Callout>

## There's no single best algorithm

Several correct algorithms usually exist for one problem, and which one is best depends on the situation. For sorting, it depends on:

1. **How many items there are.** For 20 items, a simple sort whose work grows with the *square* of the number of items (a **quadratic** sort: 20 items, about 400 steps) runs instantly. For 20 million items, that same method takes 400 trillion steps and becomes unusable.
2. **Restrictions on the values.** If every value is a whole number from 0 to 100, you can sort by counting how many times each value appears, without comparing items at all.
3. **Where the data is stored:** main memory, disks, or solid-state drives. Jumping between random locations on a disk is slow, so sequential reads are much faster. That is why [merge sort is used for data too big for memory](/courses/algorithm-design-and-analysis/merge-sort#where-this-shows-up-today).
4. **How sorted the items already are.** On a nearly sorted array, [insertion sort](/courses/algorithm-design-and-analysis/insertion-sort#why-its-the-best-of-the-simple-sorts) runs in close to **linear** time, meaning time roughly proportional to the number of items: twice the items, twice the time.

The question "which sort is best?" has no single answer without context. The best choice depends on data size, existing order, and storage hardware.

## Algorithm vs. program

People often use the two words interchangeably, although they refer to different concepts.

| Algorithm | Program |
| --- | --- |
| Abstract and general | Concrete and specific |
| Written in pseudocode, a diagram, or plain English | Written in a real language (Java, Python, C) |
| Describes *how* to solve the problem | *Implements* that description so a machine can run it |
| Cannot execute directly on hardware | Runs on a computer |

**Pseudocode** sits between plain prose and working code: exact steps written with loops and conditionals, without language-specific syntax like types, semicolons, or imports. There is no single official syntax; the steps only need to be clear and unambiguous. The [example at the end of this lesson](#a-first-algorithm-three-ways) shows one.

One algorithm can become a thousand programs. [Binary search](/courses/algorithm-design-and-analysis/linear-and-binary-search#binary-search-throw-away-half) is one idea, and there's a version of it in the Java standard library (`Arrays.binarySearch`), in every database index, and in the `git bisect` command.

This course uses **Java** because most university computer science labs teach it. Keep the distinction in mind: when an exam asks you to "write the algorithm," it usually expects the logic as clear steps or pseudocode, not a fully compiled Java class.

## How an algorithm gets made

Designing an algorithm is an iterative cycle where writing code comes last. Here is the **algorithm design and analysis process**:

1. **Understand the problem.** What exactly is the input? What counts as a correct answer? What are the unusual edge cases? Work a few small instances by hand.
2. **Decide on the approach.** The full name of this box is "Decide on: computational means, exact vs. approximate solving, algorithm design technique", three things to settle before designing anything:
   - **The computational means:** what kind of machine runs it. Almost everything in this course assumes an ordinary computer that does one step at a time; a machine that runs many steps in parallel needs different algorithms. How much speed and memory you have counts here too.
   - **Exact or approximate solving:** do you need the exact best answer, or is a good-enough one acceptable? For the hard problems below, exact answers can take too long, so people settle for close ones.
   - **The algorithm design technique:** brute force, [divide and conquer](/courses/algorithm-design-and-analysis/merge-sort#divide-and-conquer), greedy, or [dynamic programming](/courses/algorithm-design-and-analysis/dynamic-programming). You'll learn all four here. This is also when you pick your data structures.
3. **Design an algorithm:** write the steps.
4. **Prove correctness:** prove it produces the correct output for every valid input.
5. **Analyze the algorithm:** how much time and memory does it need?
6. **Code the algorithm** in a programming language.

The feedback arrows capture the real design cycle. If a correctness proof fails, or the complexity analysis shows the approach is too slow, you return to step 3 to redesign. When no design with your chosen technique succeeds, you step back to step 2 to choose a different technique or accept an approximation.

Writing code comes *last*. If you jump straight to step 6, you end up resolving logic and efficiency issues by trial and error in a debugger late at night.

<Callout tone="sky" label="Exam tip">
"Draw the flowchart of the algorithm design and analysis process" is a common exam question. Draw the six boxes above, top to bottom, with "Decide on" written out in full: *computational means, exact vs. approximate solving, algorithm design technique*. Then draw the feedback arrows: from "Prove correctness" back to "Design" and to "Decide on", and from "Analyze" back to "Design" and to "Decide on". Students often draw only the straight line down and lose marks for the loops.
</Callout>

## The kinds of problems algorithms solve

Most problems fall into a few families. Exams often ask you to list them with an example of each, so here is the full list, with where this course covers each one:

| Problem type | Examples | In this course |
| --- | --- | --- |
| **Numerical** | Solving equations (Newton-Raphson method), numerical integration, the [greatest common divisor](/courses/computational-mathematics/divisibility-and-euclid#greatest-common-divisor) | [Euclid's GCD](/courses/algorithm-design-and-analysis/euclid-gcd), module 2 |
| **Sorting** | Sorting a list of numbers, putting names in alphabetical order | Module 1 |
| **Searching** | Linear search in an array, binary search in a sorted list | Module 2 |
| **String processing** | Finding a word in a document, spell-checking | (not covered) |
| **Graph** | Finding the shortest path (Dijkstra's algorithm), detecting cycles | Module 3 |
| **Optimization** | Keeping costs as low as possible when sharing out resources, making as much profit as possible | Module 4 |
| **Dynamic programming** | Computing Fibonacci numbers, the knapsack problem | [Dynamic programming](/courses/algorithm-design-and-analysis/dynamic-programming), module 4 |
| **Machine learning** | Classification (is this email spam?), [regression](/courses/computational-mathematics/derivatives-and-curve-fitting#fitting-a-curve-to-data) (predict a house price) | (not covered) |
| **Data compression** | Huffman coding, run-length encoding | [Huffman codes](/courses/advanced-algorithms/huffman-and-activity-selection#huffman-codes) in Advanced Algorithms |
| **Cryptography** | RSA for sending data securely, AES for encrypting data | [What is Cryptography](/courses/computational-mathematics/what-is-cryptography) in Computational Mathematics |
| **Game theory** | The minimax algorithm for playing games such as chess | (not covered) |

Sorting, searching, string processing, graph and numerical problems are often called the **important problem types**, because so many other algorithms use them as building blocks.

Then there are the **hard problems**: the Traveling Salesman Problem (the shortest route that visits every city once and returns home), the Knapsack Problem (the most value that fits in a bag with a weight limit), and Graph Coloring (color a map's regions so no two neighbors share a color, using as few colors as possible). No known algorithm solves these efficiently in the general case. Existing exact algorithms check nearly every possibility, and the number of combinations grows rapidly: 20 cities can be visited in more than $10^{16}$ distinct routes. These problems belong to the *NP-complete* class, which [Advanced Algorithms defines](/courses/advanced-algorithms/p-and-np#np-complete).

Two things in that list look like contradictions, and exams like to test them:

- **Finding a shortest path is not an intractable problem.** Some notes list the shortest path alongside the Traveling Salesman Problem. Finding the shortest path between two nodes is efficient: [Dijkstra's algorithm](/courses/advanced-algorithms/shortest-paths#dijkstras-algorithm) runs in **polynomial time** (its step count grows as a power of the input size, such as $n^2$, rather than exponentially like $2^n$). That is why the table above categorizes it as a standard graph problem. The computationally hard problem is finding the shortest *tour* visiting every city.
- **The knapsack problem appears in two places.** It is NP-complete in general, yet dynamic programming solves it efficiently when the weight capacity is small, as the [knapsack analysis](/courses/algorithm-design-and-analysis/dynamic-programming#analysis) explains.

## Data structures

Algorithms work on data, and the way the data is stored changes how fast the algorithm can be.

> A **data structure** is a way to store and organize data so that it can be accessed and changed easily.

An array is the simplest one: items side by side, each reachable by its index in one step. Others (linked lists, stacks, queues, trees, hash tables) make different operations fast. Finding an item in an unsorted array takes a pass over every item, while a hash table can usually find it in one step. Choosing the data structure is part of step 2 of the design process above. The [Data Structures course](/courses/data-structures/arrays-and-memory) covers them one by one, starting with arrays.

## A first algorithm, three ways

Problem: *find the largest number in an array.*

**In plain English:** remember the first number. Walk through the rest. Whenever you see a bigger one, remember that instead. When you reach the end, the number you remember is the answer.

**In pseudocode** (the arrow `←` means "gets": `max ← a[0]` stores `a[0]` in `max`, which Java writes as `max = a[0]`):

```text
max ← a[0]
for i ← 1 to n - 1
    if a[i] > max
        max ← a[i]
return max
```

**In Java:**

```java
static int findMax(int[] a) {
    int max = a[0];
    for (int i = 1; i < a.length; i++) {
        if (a[i] > max) {
            max = a[i];
        }
    }
    return max;
}
```

Trace it on the instance ⟨8, 1, 4, 9, 3, 7⟩, one row per loop pass:

| i | a[i] | a[i] > max? | max after |
| --- | --- | --- | --- |
| start | | | 8 |
| 1 | 1 | 1 > 8? no | 8 |
| 2 | 4 | 4 > 8? no | 8 |
| 3 | 9 | 9 > 8? yes | 9 |
| 4 | 3 | 3 > 9? no | 9 |
| 5 | 7 | 7 > 9? no | 9 |

The loop ends after $i = 5 = n - 1$ and returns 9. The loop starts at 1, not 0, because `a[0]` is already in `max`; comparing it with itself would waste a step.

A common mistake is to initialize with `max ← 0` instead of `max ← a[0]`. That initialization works on positive numbers, but fails on ⟨−5, −2, −9⟩, where it returns 0, a value not present in the input array.

Now check it against the definition. Input: an array. Output: one number. Definite: every step is exact. Finite: the loop runs exactly $n - 1$ times. Correct? Almost. If the array is **empty**, `a[0]` throws an exception. Either the problem promises at least one element, or the algorithm has to handle the empty case. Testing edge cases like empty inputs is a central part of verifying correctness.
