# Recipes, Programs, and Proof

Most algorithms courses open with a definition that sounds obvious and then move on too fast. Here it is:

> An **algorithm** is a well-defined procedure that takes some input and turns it into some output in a finite number of steps.

That describes a recipe too. "Take flour, eggs and milk, whisk, pour, flip when bubbles appear, stop after five pancakes" has input, steps, output and an end. What makes something an *algorithm* is how strictly we read each of those words, and the rest of the course depends on that strictness, so it's worth a few minutes here.

## What "well-defined" demands

A procedure counts as an algorithm only if it has all of these:

- **Input.** Zero or more values it starts from. (Zero is allowed: "print the first 10 primes" needs no input.)
- **Output.** At least one result. A procedure that produces nothing has done nothing.
- **Definiteness.** Every step is precise. "Whisk until it looks right" isn't. "Whisk for 60 seconds" is.
- **Finiteness.** It *must* stop. A loop that runs forever on some input is a bug.
- **Effectiveness.** Each step is basic enough to carry out with a pencil or on a CPU.

We also want it to be *efficient* (it doesn't waste time or memory) and *understandable* (someone else can read it and trust it). Those two are where design and analysis come in.

## Correctness

An algorithm is **correct** if, for *every* valid input, it stops and gives the right output.

That means every input, not just the three examples you tried. A sorting algorithm that works on 99.9% of arrays and silently scrambles the rest is wrong. This is why algorithm courses spend time on traces and proofs: testing can show that a bug exists, but only reasoning can show that one doesn't.

<Callout tone="orange" label="Why this matters at work">
Most production incidents aren't caused by a slow algorithm. They come from an algorithm that was wrong on an input nobody thought about: an empty list, a duplicate, a negative number, a value right at the edge. Asking "does this work for *every* input?" catches those before users do.
</Callout>

## Algorithm vs. program

People use the two words interchangeably, but they mean different things.

| Algorithm | Program |
| --- | --- |
| Abstract and general | Concrete and specific |
| Written in pseudocode, a diagram, or plain English | Written in a real language (Java, Python, C) |
| Describes *how* to solve the problem | *Implements* that description so a machine can run it |
| Can't be executed directly | Runs on a computer |

One algorithm can become a thousand programs. Binary search is one idea, and there's a version of it in the Java standard library (`Arrays.binarySearch`), in every database index, and in the `git bisect` command.

This course writes everything in **Java**, because that's what most university labs use. Keep the distinction in mind, though. When an exam asks you to "write the algorithm," it usually wants the idea as clear steps or pseudocode, not a class that compiles.

## How an algorithm gets made

Designing an algorithm is a loop, and typing comes at the end of it:

1. **Understand the problem.** What exactly is the input? What counts as a right answer? What are the weird cases?
2. **Choose your tools.** Do you need the exact answer or a good-enough one? Which data structures? Which strategy: brute force, divide and conquer, greedy, or dynamic programming? (You'll learn all four here.)
3. **Design** the steps.
4. **Prove** it's correct, or at least convince yourself carefully.
5. **Analyze** how much time and memory it needs. If it's too slow, go back to step 3.
6. **Code** it.

Coding is *last*. If you jump straight to step 6, you end up doing steps 3 to 5 by trial and error in a debugger at 2 a.m.

</Callout>

## The kinds of problems algorithms solve

Most problems you'll meet fall into a few families, and this course covers most of them:

- **Sorting:** put things in order (module 1).
- **Searching:** find one thing among many (module 2).
- **Numerical:** GCD, primes, powers (module 2).
- **Graph problems:** routes, networks, connections (module 3).
- **Optimization:** the best choice under constraints (module 4, greedy and dynamic programming).

Then there are the **hard problems**: the Traveling Salesman Problem (shortest route through every city), the Knapsack Problem (most value that fits in a bag), and Graph Coloring. Nobody knows a fast algorithm for any of them; they belong to the *NP-complete* class. At the end of the course you'll solve a small version of knapsack and see where the difficulty comes from.

## A first algorithm, three ways

Problem: *find the largest number in an array.*

**In plain English:** remember the first number. Walk through the rest. Whenever you see a bigger one, remember that instead. When you reach the end, the number you remember is the answer.

**In pseudocode:**

```text
max ← a[0]
for i ← 1 to n - 1
    if a[i] > max
        max ← a[i]
return max
```

**In Java:**

```java
static int findMax(int[] a) {
    int max = a[0];
    for (int i = 1; i < a.length; i++) {
        if (a[i] > max) {
            max = a[i];
        }
    }
    return max;
}
```

Now check it against the definition. Input: an array. Output: one number. Definite: every step is exact. Finite: the loop runs exactly $n - 1$ times. Correct? Almost. If the array is **empty**, `a[0]` throws an exception. Either the problem promises at least one element, or the algorithm has to handle that case. Asking "what about the empty input?" is what correctness thinking looks like in practice.
