# Recipes, Programs, and Proof

Every course on algorithms opens with a definition that sounds obvious and then moves on too fast. Here it is:

> An **algorithm** is a well-defined procedure that takes some input and turns it into some output in a finite number of steps.

That's a recipe. "Take flour, eggs and milk, whisk, pour, flip when bubbles appear, stop after five pancakes." Input, steps, output, an end. What makes it an *algorithm* and not just a recipe is how strict we are about each of those words. That strictness is what this whole course is built on, so it's worth slowing down here for a minute.

## What "well-defined" actually demands

A procedure only counts as an algorithm if it has all of these:

- **Input.** Zero or more values it starts from. (Zero is allowed: "print the first 10 primes" needs no input.)
- **Output.** At least one result. A procedure that produces nothing has done nothing.
- **Definiteness.** Every step is precise. "Whisk until it looks right" isn't. "Whisk for 60 seconds" is.
- **Finiteness.** It *must* stop. A loop that runs forever on some input is a bug, not an algorithm.
- **Effectiveness.** Each step is basic enough to actually do — with a pencil, or by a CPU.

On top of those, we want it to be *efficient* (not waste time or memory) and *understandable* (someone else can read it and trust it). Those two are where design and analysis come in.

## Correctness: the part people skip

An algorithm is **correct** if, for *every* valid input, it stops and gives the right output.

Every. Not "for the three examples I tried." A sorting algorithm that works on 99.9% of arrays and silently scrambles the rest is not "mostly correct" — it's wrong. That's why algorithm courses spend time on traces and proofs: testing can show a bug exists, but only reasoning can show one doesn't.

<Callout tone="orange" label="Why this matters at work">
Most production incidents aren't "the algorithm was slow." They're "the algorithm was wrong on an input nobody thought about" — an empty list, a duplicate, a negative number, a value at the very edge. Thinking about correctness as *every input* is the habit that catches those before users do.
</Callout>

## Algorithm vs. program

People use the words interchangeably. They aren't the same thing.

| Algorithm | Program |
| --- | --- |
| Abstract and general | Concrete and specific |
| Written in pseudocode, a diagram, or plain English | Written in a real language — Java, Python, C |
| Describes *how* to solve the problem | *Implements* that description so a machine can run it |
| Can't be executed directly | Runs on a computer |

One algorithm can become a thousand programs. Binary search is one idea; there's a version of it in the Java standard library (`Arrays.binarySearch`), in every database index, and in the `git bisect` command. Same algorithm, different programs.

This course writes everything in **Java**, because that's what most university labs use. But keep the distinction in your head: when an exam asks you to "write the algorithm," it usually wants the idea — clear steps or pseudocode — not a compiling class.

## How an algorithm actually gets made

Designing an algorithm isn't "think, then type." It's a loop:

1. **Understand the problem.** What exactly is the input? What counts as a right answer? What are the weird cases?
2. **Choose your tools.** Exact answer or a good-enough one? Which data structures? Which strategy — brute force, divide and conquer, greedy, dynamic programming? (You'll learn all four here.)
3. **Design** the steps.
4. **Prove** it's correct — at least convince yourself carefully.
5. **Analyze** how much time and memory it needs. If it's too slow, go back to step 3.
6. **Code** it.

Notice coding is *last*. If you jump straight to step 6, you end up doing steps 3–5 by trial and error, in a debugger, at 2 a.m.

</Callout>

## The kinds of problems algorithms solve

Most problems you'll meet fall into a handful of families. You'll study most of these in this course:

- **Sorting** — put things in order (module 1).
- **Searching** — find one thing among many (module 2).
- **Numerical** — GCD, primes, powers (module 2).
- **Graph problems** — routes, networks, connections (module 3).
- **Optimization** — the best choice under constraints (module 4: greedy and dynamic programming).

And then there are the **hard problems**: the Traveling Salesman Problem (shortest route through every city), the Knapsack Problem (most value that fits in a bag), Graph Coloring. Nobody knows a fast algorithm for any of them — these belong to the famous *NP-complete* class. You'll meet a small, solvable version of knapsack at the end of the course and see exactly where the difficulty comes from.

## A first algorithm, three ways

Problem: *find the largest number in an array.*

**In plain English:** remember the first number. Walk through the rest. Whenever you see a bigger one, remember that instead. When you reach the end, the number you remember is the answer.

**In pseudocode:**

```text
max ← a[0]
for i ← 1 to n - 1
    if a[i] > max
        max ← a[i]
return max
```

**In Java:**

```java
static int findMax(int[] a) {
    int max = a[0];
    for (int i = 1; i < a.length; i++) {
        if (a[i] > max) {
            max = a[i];
        }
    }
    return max;
}
```

Now check it against the definition. Input: an array. Output: one number. Definite: every step is exact. Finite: the loop runs exactly $n - 1$ times. Correct? Almost. What happens if the array is **empty**? `a[0]` throws an exception. Either the problem says "the array has at least one element," or the algorithm has to handle that case. That one question — *what about the empty input?* — is correctness thinking in action.
