# Dynamic Programming: The 0/1 Knapsack

Greedy algorithms make a single choice at each step and never reconsider. Sometimes that produces the right answer, but as the coin example showed, a greedy choice can miss the best solution entirely. Trying every combination guarantees an optimal answer, but brute-force search is usually far too slow. **Dynamic programming** solves this by evaluating all valid options efficiently, without repeating work.

## The problem with plain recursion

Consider the [Fibonacci sequence](/courses/discrete-mathematics/induction#recursion-is-induction): $F(0) = 0$, $F(1) = 1$, and each subsequent number is the sum of the two preceding values: $F(n) = F(n-1) + F(n-2)$. The mathematical definition translates directly into Java:

```java
static long fib(int n) {
    if (n < 2) return n;
    return fib(n - 1) + fib(n - 2);
}
```

This implementation is correct, but extraordinarily slow. Computing `fib(5)` calculates `fib(3)` twice, `fib(2)` three times, and `fib(1)` five times. The same subproblems are recalculated repeatedly. The total number of recursive calls [grows exponentially](/courses/algorithm-design-and-analysis/counting-steps#getting-the-big-o-without-the-algebra), scaling by roughly 1.6 with each increase in $n$, making **$O(2^n)$** an upper bound. A call to `fib(50)` triggers billions of operations.

When a recursive algorithm encounters identical subproblems again and again, those pieces are called **overlapping subproblems**. Dynamic programming is designed specifically for problems with this structure:

> Solve each smaller subproblem **only once**, record its answer in a **table**, and look up the stored value whenever it is needed again.

These subproblems usually arise from a **recurrence relation**, an equation that defines the solution to a problem in terms of solutions to smaller instances of itself. The relation $F(n) = F(n-1) + F(n-2)$ is a classic recurrence.

```java
static long fib(int n) {
    long[] F = new long[n + 2];
    F[0] = 0; F[1] = 1;
    for (int i = 2; i <= n; i++)
        F[i] = F[i - 1] + F[i - 2];     // each entry computed once
    return F[n];
}
```

The mathematical recurrence remains unchanged, but recording intermediate values in an array reduces the running time from exponential to $O(n)$. Applying dynamic programming to other problems comes down to defining the subproblems and deciding what information to store in the table.

## The 0/1 knapsack problem

Imagine you have a knapsack that can hold at most a total weight of $W$. You are given $n$ items, each having a weight $w_i$ and a value $v_i$. The objective is to select the most valuable [subset](/courses/discrete-mathematics/sets#subsets) of items that fits within the capacity limit. In textbooks, value is often called the **benefit** or **profit**, with arrays labeled `wt` and `val`. Each item is indivisible: you either take it (1) or leave it (0), giving the **0/1 knapsack problem** its name.

This is a computationally challenging problem. Evaluating every possible subset requires testing $2^n$ combinations. That is simple for 4 items (16 subsets), but impossible for 60 items (over $10^{18}$ subsets).

A greedy approach also fails on this problem. Suppose the knapsack has capacity 50, and you have three items: weight 10 with value 60 (value density 6), weight 20 with value 100 (value density 5), and weight 30 with value 120 (value density 4). A greedy heuristic that chooses items with the highest value per unit of weight takes the first two items (total value 160), leaving no remaining capacity for the third. The optimal solution takes the second and third items, which fit within capacity 50 and achieve a total value of **220**.

## Breaking it into subproblems

Define a two-dimensional table where each cell represents the solution to a smaller subproblem:

> $V[i, w]$ represents the maximum value achievable using **only the first $i$ items** with a maximum **capacity $w$**.

The answer to the complete problem will appear in cell $V[n, W]$. To determine the value of any cell $V[i, w]$, ask: **what happens with item $i$?**

- **It does not fit** ($w_i \gt w$). The item is too heavy for current capacity $w$, so you cannot take it. The best value is whatever you could achieve using only the first $i - 1$ items: $V[i, w] = V[i-1, w]$.
- **It fits.** You have two choices and select whichever yields greater value:
  - **Skip it:** do not take item $i$, giving value $V[i-1, w]$.
  - **Take it:** collect its value $v_i$, and use the remaining capacity $w - w_i$ to take the best combination from the first $i - 1$ items: $v_i + V[i-1, w - w_i]$.

$$
V[i, w] = \max\big(V[i-1, w],\ \ v_i + V[i-1, w - w_i]\big)
$$

Row 0 (considering 0 items) and column 0 (having 0 capacity) are filled entirely with **zero**, because you cannot gain value without items or without capacity.

Notice that every cell depends exclusively on values in the row **above** it. Filling the table row by row from top to bottom, and left to right within each row, guarantees that every prerequisite value is already calculated when needed.

<Callout tone="orange" label="Common mistake: reading from the same row">
The 'take' choice accesses $V[i-1, w - w_i]$, which comes from the row **above**. A frequent coding mistake is writing $V[i, w - w_i]$ from the current row instead. Reading from the current row allows item $i$ to be selected multiple times, solving the unbounded knapsack problem where item quantities are unlimited. In the four-item example below, that bug produces a corner value of **200** by taking item 4 five times (weight 1, value 40), instead of the correct 0/1 limit of 140.
</Callout>

| $V[i, w]$ | w = 0 | 1 | 2 | 3 | 4 | 5 |

| 4 | 0 | 40 | 40 | 100 | 140 | **140** |

Row 3 is identical to row 2 across all columns. Item 3 weighs 4, and for every capacity where it fits, taking it yields a lower total value than keeping the selection from row 2.

## Which items were taken?

The table computes the maximum possible value, but does not list the chosen items directly. To reconstruct the subset, **backtrack** through the table starting from the final cell, $V[n, W]$:

- If $V[i, w] = V[i-1, w]$, item $i$ did not improve the total, so it was **skipped**. Move up one row to $(i - 1, w)$.
- If $V[i, w] \ne V[i-1, w]$, item $i$ was **taken**. Record item $i$, then move up one row and left by $w_i$ to $(i - 1, w - w_i)$.
- Stop when $i = 0$ or $w = 0$.

When you take an item, always subtract its weight from the current capacity before moving to the row above. Omitting this step checks the wrong column, which can cause the backtrack to select items that exceed the capacity.

Tracing the backtrack on the completed table:

| i, w | Comparison | Action |
| --- | --- | --- |
| 4, 5 | 140 ≠ V[3, 5] = 120 | take item 4; new capacity w = 5 − 1 = 4 |
| 3, 4 | 100 = V[2, 4] = 100 | skip item 3; move to row 2 |
| 2, 4 | 100 = V[1, 4] = 100 | skip item 2; move to row 1 |
| 1, 4 | 100 ≠ V[0, 4] = 0 | take item 1; new capacity w = 4 − 3 = 1 |
| 0, 1 | i = 0 | stop |

The optimal solution contains items 1 and 4, giving total weight $3 + 1 = 4$ and total value $100 + 40 = 140$. The knapsack does not need to be completely full: one unit of capacity remains unused because none of the remaining available items has a weight of 1.

Continuing the steps in the visualizer above highlights this backtracking traversal in violet.

## Analysis

The table contains $(n + 1) \times (W + 1)$ cells, and each cell requires $O(1)$ constant time arithmetic to compute. **Time and space: $O(nW)$.**

Compare this with exhaustive brute-force search at $O(2^n)$. For 100 items and a capacity of 1,000, dynamic programming evaluates 100,000 cell updates instead of $2^{100} \approx 10^{30}$ subset combinations.

<Callout tone="violet" label="The fine print">
While $O(nW)$ appears polynomial at first glance, $W$ is a numeric value rather than a count of distinct input items. Adding one digit to the representation of $W$ multiplies its numeric value by ten and widens the table tenfold. Because the size of the input is measured in the number of bits required to encode $W$, the running time is exponential with respect to input length, an efficiency known as **[pseudo-polynomial](/courses/advanced-algorithms/p-and-np#np-complete)** time. This is why 0/1 knapsack remains NP-complete: dynamic programming solves it efficiently when capacity $W$ is small, but does not provide a general polynomial-time solution for arbitrarily large numbers.
</Callout>

## DP vs. greedy vs. divide and conquer

| | Divide and conquer | Greedy | Dynamic programming |
| --- | --- | --- | --- |
| Subproblems | Independent | One choice at a time | Overlapping |
| Explores alternatives? | n/a | No, commits immediately | Yes, evaluates all viable options |
| Always optimal? | n/a | Only with mathematical proof | Yes |
| Examples | Merge sort, quick sort | Prim, Kruskal | Fibonacci table, knapsack |

## The Java

```java
public class Knapsack {

    static int knapsack(int[] wt, int[] val, int W) {
        int n = wt.length;
        int[][] V = new int[n + 1][W + 1];          // Java fills it with 0s

        for (int i = 1; i <= n; i++)
            for (int w = 1; w <= W; w++)
                if (wt[i - 1] > w)
                    V[i][w] = V[i - 1][w];
                else
                    V[i][w] = Math.max(V[i - 1][w],
                                       val[i - 1] + V[i - 1][w - wt[i - 1]]);

        // backtrack to find the items
        int w = W;
        for (int i = n; i >= 1; i--)
            if (V[i][w] != V[i - 1][w]) {
                System.out.println("take item " + i);
                w -= wt[i - 1];
            }
        return V[n][W];
    }

    public static void main(String[] args) {
        int[] wt = {3, 2, 4, 1};
        int[] val = {100, 20, 60, 40};
        System.out.println("best value = " + knapsack(wt, val, 5));   // 140
    }
}
```

Note the array indexing: table row `i` corresponds to item `i`, but zero-indexed arrays store item `i` at `wt[i - 1]` and `val[i - 1]`.

- Item 2: weight $w_2 = 2$, value $v_2 = 20$
- Item 3: weight $w_3 = 4$, value $v_3 = 60$
- Item 4: weight $w_4 = 1$, value $v_4 = 40$

1. State the base cases and the recurrence relation for table cell $V[i, w]$, explaining the condition under which an item cannot be considered.
2. Hand-calculate each entry in the $(4 + 1) \times (5 + 1)$ table from $i = 0$ to $4$ and $w = 0$ to $5$. Show the explicit numerical evaluation for cells $V[1, 3]$, $V[2, 5]$, $V[3, 4]$, and $V[4, 5]$.
3. Explain why Row 3 is completely identical to Row 2 across all columns, and explain what this reveals about Item 3.

<ModelAnswer>
**(a) Recurrence relation and base cases:**
- **Base cases:**
  - $V[0, w] = 0$ for all $0 \le w \le W$: with 0 items available, the achievable value is zero.
  - $V[i, 0] = 0$ for all $0 \le i \le n$: with zero capacity, no items can be carried.
- **Recurrence for cell $V[i, w]$:**
  - If $w_i > w$ (item $i$ is heavier than current capacity $w$):
    $$
    V[i, w] = V[i - 1, w]
    $$
  - If $w_i \le w$ (item $i$ fits):
    $$
    V[i, w] = \max\big(V[i - 1, w],\ \ v_i + V[i - 1, w - w_i]\big)
    $$
  The first term $V[i - 1, w]$ represents **skipping** item $i$. The second term $v_i + V[i - 1, w - w_i]$ represents **taking** item $i$, earning value $v_i$ and using the remaining capacity $w - w_i$ to take the best selection from the previous $i - 1$ items.

**(b) Complete table evaluation:**

- **Row 0 ($i = 0$, 0 items):**
  $V[0, w] = [0, 0, 0, 0, 0, 0]$ for $w = 0, 1, 2, 3, 4, 5$.

- **Row 1 ($i = 1$, $w_1 = 3, v_1 = 100$):**
  - For $w = 0, 1, 2$: $w < 3 \implies V[1, w] = V[0, w] = 0$.
  - For $w = 3$: $\max(V[0, 3], 100 + V[0, 0]) = \max(0, 100 + 0) = \mathbf{100}$.
  - For $w = 4$: $\max(V[0, 4], 100 + V[0, 1]) = \max(0, 100 + 0) = \mathbf{100}$.
  - For $w = 5$: $\max(V[0, 5], 100 + V[0, 2]) = \max(0, 100 + 0) = \mathbf{100}$.
  - Row 1: `[0, 0, 0, 100, 100, 100]`.

- **Row 2 ($i = 2$, $w_2 = 2, v_2 = 20$):**
  - For $w = 0, 1$: $w < 2 \implies V[2, w] = V[1, w] = 0$.
  - For $w = 2$: $\max(V[1, 2], 20 + V[1, 0]) = \max(0, 20 + 0) = \mathbf{20}$.
  - For $w = 3$: $\max(V[1, 3], 20 + V[1, 1]) = \max(100, 20 + 0) = \mathbf{100}$.
  - For $w = 4$: $\max(V[1, 4], 20 + V[1, 2]) = \max(100, 20 + 0) = \mathbf{100}$.
  - For $w = 5$: $\max(V[1, 5], 20 + V[1, 3]) = \max(100, 20 + 100) = \mathbf{120}$.
  - Row 2: `[0, 0, 20, 100, 100, 120]`.

- **Row 3 ($i = 3$, $w_3 = 4, v_3 = 60$):**
  - For $w = 0, 1, 2, 3$: $w < 4 \implies V[3, w] = V[2, w] \implies 0, 0, 20, 100$.
  - For $w = 4$: $\max(V[2, 4], 60 + V[2, 0]) = \max(100, 60 + 0) = \mathbf{100}$.
  - For $w = 5$: $\max(V[2, 5], 60 + V[2, 1]) = \max(120, 60 + 0) = \mathbf{120}$.
  - Row 3: `[0, 0, 20, 100, 100, 120]`.

- **Row 4 ($i = 4$, $w_4 = 1, v_4 = 40$):**
  - For $w = 0$: $V[4, 0] = 0$.
  - For $w = 1$: $\max(V[3, 1], 40 + V[3, 0]) = \max(0, 40 + 0) = \mathbf{40}$.
  - For $w = 2$: $\max(V[3, 2], 40 + V[3, 1]) = \max(20, 40 + 0) = \mathbf{40}$.
  - For $w = 3$: $\max(V[3, 3], 40 + V[3, 2]) = \max(100, 40 + 20) = \mathbf{100}$.
  - For $w = 4$: $\max(V[3, 4], 40 + V[3, 3]) = \max(100, 40 + 100) = \mathbf{140}$.
  - For $w = 5$: $\max(V[3, 5], 40 + V[3, 4]) = \max(120, 40 + 100) = \mathbf{140}$.
  - Row 4: `[0, 40, 40, 100, 140, 140]`.

| $V[i, w]$ | w = 0 | w = 1 | w = 2 | w = 3 | w = 4 | w = 5 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **i = 0** | 0 | 0 | 0 | 0 | 0 | 0 |
| **i = 1** | 0 | 0 | 0 | 100 | 100 | 100 |
| **i = 2** | 0 | 0 | 20 | 100 | 100 | 120 |
| **i = 3** | 0 | 0 | 20 | 100 | 100 | 120 |
| **i = 4** | 0 | 40 | 40 | 100 | 140 | **140** |

**(c) Why Row 3 equals Row 2:**
- Item 3 weighs $w_3 = 4$ with value $v_3 = 60$.
- For capacities $w < 4$, item 3 cannot fit, so $V[3, w] = V[2, w]$ directly.
- For capacity $w = 4$, taking item 3 yields $60 + V[2, 0] = 60$, which is inferior to skipping it and retaining $V[2, 4] = 100$ (from Item 1).
- For capacity $w = 5$, taking item 3 yields $60 + V[2, 1] = 60$, which is inferior to retaining $V[2, 5] = 120$ (from Item 1 + Item 2).
- Thus, Item 3 is dominated: in every column where it fits, the previous items provide greater value. Item 3 is never selected for any capacity up to 5.

**2.** *(Optimal subset reconstruction via table backtracking)* The bottom-right cell $V[4, 5] = 140$ reveals the maximum value achievable, but does not identify which items to pack.

1. State the exact rule used during backtracking to decide whether item $i$ was included in the optimal knapsack.
2. Trace the backtracking procedure step by step starting from cell $V[4, 5]$ down to $i = 0$. In each step, record:
   - Current cell $(i, w)$ and its value $V[i, w]$.
   - Value of the cell directly above: $V[i - 1, w]$.
   - Comparison result and decision: **Take Item $i$** vs **Skip Item $i$**.
   - Updated capacity $w$ and next cell inspected.
3. List the items chosen, and verify that their combined weight does not exceed $W = 5$ and their combined value equals $140$.

<ModelAnswer>
**(a) Backtracking decision rule:**
- Compare $V[i, w]$ with $V[i - 1, w]$:
  - If $V[i, w] == V[i - 1, w]$: The maximum value achievable with $i$ items is no better than without item $i$. Therefore, item $i$ was **skipped**. Move directly up to cell $(i - 1, w)$ with capacity $w$ unchanged.
  - If $V[i, w] \ne V[i - 1, w]$: Item $i$ contributed to the maximum value and was **taken**. Add item $i$ to the solution set, subtract its weight from capacity ($w \leftarrow w - w_i$), and move to cell $(i - 1, w - w_i)$.
- Stop as soon as $i = 0$ or $w = 0$.

**(b) Step-by-step backtrack trace:**

1. **Start at $(i = 4, w = 5)$:**
   - $V[4, 5] = 140$.
   - Directly above: $V[3, 5] = 120$.
   - Since $140 \ne 120$, **Item 4 was TAKEN**.
   - Subtract weight $w_4 = 1$: new capacity $w = 5 - 1 = 4$.
   - Next cell: $(i = 3, w = 4)$.

2. **At $(i = 3, w = 4)$:**
   - $V[3, 4] = 100$.
   - Directly above: $V[2, 4] = 100$.
   - Since $100 == 100$, **Item 3 was SKIPPED**.
   - Capacity remains $w = 4$.
   - Next cell: $(i = 2, w = 4)$.

3. **At $(i = 2, w = 4)$:**
   - $V[2, 4] = 100$.
   - Directly above: $V[1, 4] = 100$.
   - Since $100 == 100$, **Item 2 was SKIPPED**.
   - Capacity remains $w = 4$.
   - Next cell: $(i = 1, w = 4)$.

4. **At $(i = 1, w = 4)$:**
   - $V[1, 4] = 100$.
   - Directly above: $V[0, 4] = 0$.
   - Since $100 \ne 0$, **Item 1 was TAKEN**.
   - Subtract weight $w_1 = 3$: new capacity $w = 4 - 3 = 1$.
   - Next cell: $(i = 0, w = 1)$.

5. **At $(i = 0, w = 1)$:**
   - $i = 0$: halting condition reached. Backtracking terminates.

**(c) Selected subset verification:**
- Items taken: **Item 1** and **Item 4**.
- Total weight:
  $$
  w_1 + w_4 = 3 + 1 = 4 \le 5\text{ (valid capacity)}
  $$
- Total value:
  $$
  v_1 + v_4 = 100 + 40 = 140\text{ (matches } V[4, 5]\text{ exactly)}
  $$
- Notice that 1 unit of capacity remains empty ($5 - 4 = 1$) because no remaining item has weight 1. Dynamic programming correctly finds the optimal value even when capacity cannot be filled completely.
</ModelAnswer>

**3.** *(The unbounded knapsack coding error and 1D array space optimization)*

1. A programmer implements the 0/1 knapsack table but makes an indexing error in the recurrence:
   $$
   V_{\text{buggy}}[i, w] = \max\big(V[i - 1, w],\ \ v_i + V[i, w - w_i]\big)
   $$
   Notice that the second term accesses row $i$ rather than row $i - 1$. Trace the values computed in Row 4 ($w_4 = 1, v_4 = 40$) for $w = 1, 2, 3, 4, 5$ using this formula, and compare the resulting corner value with the correct 0/1 value.
2. What physical problem does this buggy recurrence actually solve?
3. To reduce memory from $O(n \cdot W)$ to $O(W)$, the 2D table can be replaced by a single 1D array `int[] dp = new int[W + 1]`. Explain why the capacity loop must run backwards from $W$ down to $w_i$:
   ```java
   for (int i = 0; i < n; i++) {
       for (int w = W; w >= wt[i]; w--) {
           dp[w] = Math.max(dp[w], val[i] + dp[w - wt[i]]);
       }
   }
   ```
   What happens if an engineer writes `for (int w = wt[i]; w <= W; w++)` instead?

<ModelAnswer>
**(a) Buggy recurrence trace on Row 4 ($w_4 = 1, v_4 = 40$):**
- When computing row 4, row 3 is already complete: `V[3] = [0, 0, 20, 100, 100, 120]`.
- $w = 1$: $\max(V[3, 1], 40 + V_{\text{buggy}}[4, 0]) = \max(0, 40 + 0) = \mathbf{40}$.
- $w = 2$: $\max(V[3, 2], 40 + V_{\text{buggy}}[4, 1]) = \max(20, 40 + 40) = \mathbf{80}$.
- $w = 3$: $\max(V[3, 3], 40 + V_{\text{buggy}}[4, 2]) = \max(100, 40 + 80) = \mathbf{120}$.
- $w = 4$: $\max(V[3, 4], 40 + V_{\text{buggy}}[4, 3]) = \max(100, 40 + 120) = \mathbf{160}$.
- $w = 5$: $\max(V[3, 5], 40 + V_{\text{buggy}}[4, 4]) = \max(120, 40 + 160) = \mathbf{200}$.
- Instead of the correct 0/1 value **140**, the buggy code computes **200**!

**(b) What problem the bug solves:**
- Reading from $V[i, w - w_i]$ on the **same row** solves the **Unbounded Knapsack problem** (or Complete Knapsack problem), where an unlimited supply of each item is available.
- At $w = 5$, item 4 (weight 1, value 40) was taken **5 times** ($5 \times 1 = 5 \le 5$), yielding $5 \times 40 = 200$. In 0/1 knapsack, each item is unique and can be taken at most once.

**(c) Why 1D array space optimization requires backwards iteration:**
- In the 1D array `dp[w]`, we want `dp[w - wt[i]]` to represent the value from the **previous item iteration** (equivalent to $V[i - 1, w - w_i]$).
- When iterating **backwards** ($w = W \to wt[i]$), when updating `dp[w]`, the value at `dp[w - wt[i]]` has not been modified yet in the current outer loop iteration; it still holds the value from item $i - 1$. This strictly enforces the 0/1 constraint.
- If the loop iterates **forwards** ($w = wt[i] \to W$), updating `dp[1] = 40` immediately overwrites the old value. When computing `dp[2]`, it reads the newly overwritten `dp[1] = 40`, yielding `dp[2] = 40 + 40 = 80`. Forward iteration accidentally transforms the 0/1 knapsack code into an unbounded knapsack solver!
</ModelAnswer>

**4.** *(Pseudo-polynomial time complexity and algorithmic paradigms)*

1. The dynamic programming algorithm for 0/1 knapsack has time complexity $\Theta(n \cdot W)$ and space complexity $\Theta(n \cdot W)$ (or $O(W)$ space with 1D optimization). Explain why this is called **pseudo-polynomial** rather than truly polynomial time.
2. Suppose a knapsack problem has $n = 40$ items and capacity $W = 2^{30} \approx 10^9$. Contrast the viability of the DP approach versus exhaustive brute-force search ($O(2^n)$).
3. Compare Divide and Conquer, Greedy, and Dynamic Programming across three dimensions: subproblem overlap, decision commitment (reversibility), and optimality guarantee.

<ModelAnswer>
**(a) Why $\Theta(n \cdot W)$ is pseudo-polynomial:**
- In computational complexity theory, the input size of an integer $W$ is measured by the number of bits required to encode it:
  $$
  k = \lceil \log_2(W + 1) \rceil\text{ bits}
  $$
- Therefore, $W = 2^k$. The running time $\Theta(n \cdot W) = \Theta(n \cdot 2^k)$ is actually **exponential** in the length of the input $k$.
- An algorithm is called **pseudo-polynomial** if its running time is polynomial in the *numeric value* of the input numbers, but exponential in their *bit length*.
- Because 0/1 knapsack is NP-complete, no truly polynomial algorithm ($O(n^c \cdot k^d)$) is known unless $P = NP$. When $W$ is a modest integer (e.g. $W \le 10{,}000$), DP is extremely fast; when $W$ is large, the table size explodes.

**(b) Viability comparison for $n = 40$ and $W = 10^9$:**
- **Dynamic programming:** Requires creating a table or array of size $W = 10^9$. Storing $10^9$ 32-bit integers requires **4 gigabytes** of memory for a single row, and $\Theta(n \cdot W) = 40 \times 10^9 = 4 \times 10^{10}$ operations. If $W$ were $10^{12}$, DP would fail completely with `OutOfMemoryError`.
- **Brute force ($2^n$):** For $n = 40$, $2^{40} \approx 1.1 \times 10^{12}$ subsets. While very slow, a meet-in-the-middle bidirectional search splits the items into two sets of 20 ($2^{20} \approx 10^6$ subsets each) and runs in $O(n \cdot 2^{n/2}) \approx 40 \times 10^6$ operations, which solves the problem in a fraction of a second, completely outperforming dynamic programming when $W \gg 2^{n/2}$.

**(c) Comparison of algorithmic paradigms:**

| Paradigm | Subproblem structure | Decision commitment | Optimality guarantee |
| :--- | :--- | :--- | :--- |
| **Divide and Conquer** | Independent subproblems (disjoint sub-arrays) | Combines answers after recursion; no local commitment | Guaranteed optimal if recurrence is correct (e.g., Merge Sort) |
| **Greedy** | One local choice made at each step | **Irrevocable:** choices are never undone; no backtracking | Only optimal if problem exhibits greedy-choice property (e.g., Prim, Kruskal); otherwise can fail (e.g., coin change) |
| **Dynamic Programming** | **Overlapping** subproblems with optimal substructure | Evaluates all viable options by table lookup without duplicate work | **Guaranteed optimal:** exhaustively considers all valid combinations in polynomial/pseudo-polynomial time |
