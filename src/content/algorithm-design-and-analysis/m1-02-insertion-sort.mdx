# Insertion Sort: Sorting Like a Card Player

If you've ever picked up a hand of playing cards and put it in order, you've done insertion sort.

The cards you've sorted so far are in your left hand. You pick up the next card with your right hand, slide it along until it's in the right spot (pushing the bigger cards over to make room), and drop it in. You repeat until the table is empty, and that's the whole algorithm.

## The idea

At any moment the array has two parts:

- **Left side:** already sorted among themselves (your hand).
- **Right side:** not looked at yet (the cards on the table).

Each step takes the first element of the right side, the **key**, and inserts it in the correct place on the left. To make room, every element on the left that's bigger than the key **shifts one position right**.

<SortVisualizer algorithm="insertion" initial={[12, 11, 13, 5, 6, 3, 9]} />

Watch the purple **key** chip. While it's "in your hand," the bars bigger than it slide right one by one and leave a gap. When the loop finds an element that isn't bigger, or runs off the left end, the key drops into the gap.

The notes walk through 6, 2, 11, 7, 5. The first element counts as already sorted, so the work starts with the second:

| Key | Compared with | What moves | Array after |
| --- | --- | --- | --- |
| 2 | 6 | 2 < 6: shift 6 right, put 2 in front | **2 6** 11 7 5 |
| 11 | 6 | 11 > 6: nothing shifts | **2 6 11** 7 5 |
| 7 | 11, 6 | 7 < 11: shift 11; 7 > 6, stop | **2 6 7 11** 5 |
| 5 | 11, 7, 6, 2 | 5 < 11, 7, 6: shift all three; 5 > 2, stop | **2 5 6 7 11** |

The "compared with" column runs from the **end** of the sorted part backwards. That's why 11 only needs one comparison: it's bigger than the last card in your hand, so it's bigger than all of them.

The notes' pseudocode, in the textbook's notation:

```text
ALGORITHM InsertionSort(A[0..n − 1])
for i ← 1 to n − 1 do
    key ← A[i]
    j ← i − 1
    while j ≥ 0 and A[j] > key do
        A[j + 1] ← A[j]
        j ← j − 1
    A[j + 1] ← key
```

The last line runs once per key, after the `while` loop ends, not inside it.

### An exam answer in steps

A past exam's answer sheet sorts 1, 12, 46, 6, 37, 5, 46, 3, 32 this way, one line per key that moves. Keys that are already bigger than everything before them (12, the first 46, and the second 46) don't move, so the sheet skips them:

| Key | Smaller than | Array after |
| --- | --- | --- |
| 6 | 46, 12 | 1 **6** 12 46 37 5 46 3 32 |
| 37 | 46 | 1 6 12 **37** 46 5 46 3 32 |
| 5 | 46, 37, 12, 6 | 1 **5** 6 12 37 46 46 3 32 |
| 3 | 46, 46, 37, 12, 6, 5 | 1 **3** 5 6 12 37 46 46 32 |
| 32 | 46, 46, 37 | 1 3 5 6 12 **32** 37 46 46 |

The second 46 stops behind the first, since the loop only shifts values strictly bigger than the key. That's what keeps insertion sort stable, as explained below. Each line moves a key **leftwards into place** past the bigger ones, which is how you tell an insertion sort answer from a [selection sort](/courses/algorithm-design-and-analysis/selection-and-bubble-sort#selection-sort-find-the-smallest-put-it-first) one, where each line swaps the smallest remaining value to the front.

Insertion sort **shifts** where [bubble sort](/courses/algorithm-design-and-analysis/selection-and-bubble-sort#bubble-sort-fix-the-neighbours) swaps, so each move costs one assignment instead of three. That small detail makes it quicker than bubble sort in practice, even though both have the same [Big-O](/courses/algorithm-design-and-analysis/counting-steps#the-three-notations).

## Analysis

The basic operation is the comparison `a[j] > key` in the `while` condition.

**Worst case: reverse-sorted input.** Every new key is smaller than everything in your hand, so it travels all the way to the front. The $i$-th key does $i$ comparisons:

$$
1 + 2 + \dots + (n-1) = \frac{n(n-1)}{2} = O(n^2)
$$

**Best case: already sorted input.** Every key is bigger than the last card in your hand. The `while` loop checks once, fails, and the key stays put. That's one comparison per element: **$O(n)$**.

**Average case:** on random input, each key is smaller than about half of the cards already in your hand, so it travels about halfway. That's half of the worst case's $n(n-1)/2$, roughly $n^2/4$ comparisons, which is still $O(n^2)$: halving doesn't change the class.

The notes sum it up in a table: best case $n$, average case $n^2$, worst case $n^2$. They also say it plainly: insertion sort is not efficient on large data sets (the average and worst cases show that), but it makes fewer comparisons when the array is partially sorted.

Try it: type `1, 2, 3, 4, 5, 6, 7` into the visualizer and count the steps. Then try `7, 6, 5, 4, 3, 2, 1`.

## Why it's the best of the simple sorts

Insertion sort's running time depends on **how unsorted** the input is. If every element is only a few positions from where it belongs (a *nearly sorted* array), each key shifts only a few places and the whole sort runs in close to linear time.

Real data is often nearly sorted: a list of transactions ordered by time except for a few late arrivals, or a leaderboard where only a couple of scores changed.

Other properties:

- **In place:** it only needs the `key` and `j` variables, so $O(1)$ extra space.
- **Stable:** it only shifts elements that are *strictly* bigger (`a[j] > key`), so equal values never pass each other. Change `>` to `>=` and it stops being stable, which is a common exam trap.
- **Online:** it can sort data *as it arrives*. You don't need the whole array up front, because each new element is just the next card.

<Callout tone="sky" label="The headline facts">
Insertion sort: $O(n^2)$ average and worst, $O(n)$ best, in place, stable. Great on small or nearly sorted input.
</Callout>

## The lab version

```java
public static void insertionSort(int[] array) {
    for (int i = 1; i < array.length; i++) {
        int key = array[i];
        int j = i - 1;
        while (j >= 0 && array[j] > key) {
            array[j + 1] = array[j];
            j--;
        }
        array[j + 1] = key;
    }
}
```

The line `key = array[i]` has to come first. The first shift, `array[j + 1] = array[j]`, writes into position `i`, so without a saved copy the key would be overwritten and lost. Forgetting it is a common bug: the sort runs, and the result has a duplicated value and a missing one.

Watch the order in the `while` condition: `j >= 0` must come **before** `array[j] > key`. Java's `&&` stops at the first false, so when `j` reaches `-1` it never tries to read `array[-1]`. Swap the order and the program crashes on the first key that belongs at the very front.

Time it against [selection sort](/courses/algorithm-design-and-analysis/selection-and-bubble-sort#selection-sort-find-the-smallest-put-it-first) on a random array of 5,000 numbers. Then sort the array first and time both again. Selection sort's time barely changes, while insertion sort's drops to almost nothing.
