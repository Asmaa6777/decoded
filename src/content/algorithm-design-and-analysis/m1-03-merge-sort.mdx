# Divide and Conquer: Merge Sort

Selection, bubble and insertion sort all work the same basic way: fix one element at a time, and to fix each one, look at (almost) everything else. That's where the $n^2$ comes from — $n$ elements, $n$ work each.

To beat $n^2$ you need a different *strategy*, not a cleverer loop. The first one we'll study is the most important design idea in this course.

## Divide and conquer

Three steps:

1. **Divide** the problem into smaller subproblems of the same kind.
2. **Conquer** each subproblem by solving it recursively. Once a subproblem is small enough, solve it directly — that's the **base case**.
3. **Combine** the sub-solutions into a solution for the whole problem.

If that sounds like recursion, it is. Divide and conquer is recursion with a plan: make the problem smaller *in a way that makes combining cheap*.

## Merge sort in one paragraph

To sort an array: split it in half, sort the left half, sort the right half, then **merge** the two sorted halves into one sorted array. How do you sort each half? The same way — split it, sort the halves, merge. Keep splitting until the pieces have one element each, and a one-element array is already sorted. That's the base case. Everything else is merging.

## The merge step

Merging two sorted lists is easy, and it's the heart of the algorithm. Think of two sorted piles of exam papers, smallest on top. Look at the top paper of each pile, take the smaller one, put it on the output pile. Repeat. When one pile runs out, put the rest of the other pile on top — it's already sorted.

Each comparison places exactly one element, so merging two halves with $n$ elements in total takes **$O(n)$** time.

## Analysis: where $n \log n$ comes from

Look at the split diagram again as layers.

- **How many layers?** Each layer halves the pieces. Starting from $n$, you can halve about $\log_2 n$ times before reaching size 1. For a million elements, that's only about 20 layers.
- **How much work per layer?** Every element gets merged exactly once on each layer. That's $O(n)$ work per layer.

$$
\underbrace{\log_2 n}_{\text{layers}} \times \underbrace{n}_{\text{work per layer}} = O(n \log n)
$$

And here's the best part: merge sort *always* splits exactly in half, no matter what the data looks like. So best, average and worst case are all **$O(n \log n)$**. There's no bad input.

Go back to the [growth table](/courses/algorithm-design-and-analysis/counting-steps) and compare $n^2$ with $n \log n$ at a million: the difference between hours and a fraction of a second. That's what changing strategy buys you.

<Callout tone="orange" label="The price">
Merge sort is **not in place**. The merge step needs a temporary array as big as the piece being merged — $O(n)$ extra memory. When memory is tight, that matters. (Quick sort, next lesson, avoids it.)
</Callout>

Two more properties:

- **Stable.** When the two fronts are equal, the merge takes from the *left* half first (`a[i] <= a[j]`). Equal elements keep their original order.
- **Great for huge data.** Merging only ever reads each list front to back, so it works even when the data is too big for memory and lives on disk.

## The lab version

Labs often write merge sort slightly differently: instead of index ranges, each call copies its halves into **new** arrays. It's the same algorithm, and a bit easier to read:

```java
public static void mergeSort(int[] input) {
    int n = input.length;
    if (n < 2) return;                      // base case

    int mid = n / 2;
    int[] left = new int[mid];
    int[] right = new int[n - mid];
    for (int i = 0; i < mid; i++) left[i] = input[i];
    for (int i = mid; i < n; i++) right[i - mid] = input[i];

    mergeSort(left);                        // conquer
    mergeSort(right);
    merge(input, left, right);              // combine
}

private static void merge(int[] input, int[] left, int[] right) {
    int i = 0, j = 0, k = 0;
    while (i < left.length && j < right.length) {
        if (left[i] <= right[j]) input[k++] = left[i++];
        else                     input[k++] = right[j++];
    }
    while (i < left.length)  input[k++] = left[i++];
    while (j < right.length) input[k++] = right[j++];
}
```

Run it on 100,000 random numbers and time it. Then try insertion sort on the same 100,000 — and go make a cup of tea.
