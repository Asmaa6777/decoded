# Divide and Conquer: Merge Sort

Selection, bubble, and [insertion sort](/courses/algorithm-design-and-analysis/insertion-sort#the-idea) share the same underlying structure: each pass places one element by scanning the rest of the array. That repeated scanning produces quadratic $O(n^2)$ complexity.

Breaking past the $n^2$ barrier requires a different algorithmic strategy: dividing problems into smaller subproblems.

## Divide and conquer

**Divide and conquer** is a design strategy based on recursion. It solves a computational problem through three steps:

1. **Divide** the problem into smaller subproblems of the same kind.
2. **Conquer** each subproblem by solving it recursively. When a subproblem is small enough, solve it directly. That stopping condition is the **base case**.
3. **Combine** the subproblem solutions into a solution for the original problem.

This strategy relies on **[recursion](/courses/discrete-mathematics/induction#recursion-is-induction)**, where a method solves a task by calling itself on smaller instances of the same problem. Every recursive method requires a **base case** to terminate execution without recursing further. Divide and conquer partitions problems specifically so that the combine step remains computationally efficient.

Course notes describe the pattern in two ways: either as three explicit phases (divide, conquer, combine), or as two phases (divide and conquer, where conquering includes combining). If an exam question asks for the steps of divide and conquer, list the standard three: divide, conquer, combine.

The notes cite three examples of divide and conquer: the **maximum and minimum problem** (finding the minimum and maximum of each half, then comparing the two winners), [binary search](/courses/algorithm-design-and-analysis/linear-and-binary-search#binary-search-throw-away-half), and sorting (merge sort and quick sort).

## Merge sort in one paragraph

In **merge sort**, the algorithm splits an array in half, sorts each half recursively, and merges the two sorted halves into one sorted array. The base case occurs when a subarray contains fewer than two elements, which is already sorted by definition. All ordering work takes place during the merge step.

## The merge step

Merging two sorted arrays is the central operation of merge sort. Consider two sorted piles of papers arranged with the smallest numbers on top. Comparing the top items from each pile, taking the smaller one, and placing it into an output pile repeated until one pile is empty completes the merge. The remaining items from the other pile are then appended directly to the output.

Because each comparison places at least one element into its final sorted position, merging two sorted subarrays containing $n$ total elements takes $\Theta(n)$ time.

The notes merge `L = 2, 6, 11` and `R = 4, 5, 7` into `A` with three indices: `i` for the left list, `j` for the right, `k` for the output.

| Step | Compare | Take | A so far | i, j, k after |
| --- | --- | --- | --- | --- |
| 1 | 2 vs 4 | 2 | 2 | 1, 0, 1 |
| 2 | 6 vs 4 | 4 | 2 4 | 1, 1, 2 |
| 3 | 6 vs 5 | 5 | 2 4 5 | 1, 2, 3 |
| 4 | 6 vs 7 | 6 | 2 4 5 6 | 2, 2, 4 |
| 5 | 11 vs 7 | 7 | 2 4 5 6 7 | 2, 3, 5 |
| 6 | R is empty | 11 | 2 4 5 6 7 11 | 3, 3, 6 |

At step 6 the right list has run out, so the rest of the left list (just 11) is copied over without comparing. That is safe because the left list is already sorted.

The notes give the textbook's pseudocode for the merge:

```text
ALGORITHM Merge(B[0..p − 1], C[0..q − 1], A[0..p + q − 1])
// merges two sorted arrays B and C into one sorted array A
i ← 0; j ← 0; k ← 0
while i < p and j < q do
    if B[i] ≤ C[j]
        A[k] ← B[i]; i ← i + 1
    else
        A[k] ← C[j]; j ← j + 1
    k ← k + 1
if i = p
    copy C[j..q − 1] to A[k..p + q − 1]
else
    copy B[i..p − 1] to A[k..p + q − 1]
```

`B` has $p$ elements and `C` has $q$. When `i = p`, `B` is used up, so the rest of `C` goes to the end; otherwise the rest of `B` does.

## Analysis: where $n \log n$ comes from

Examining the recursion tree by levels explains the running time:

- **Number of levels:** each level halves subarray lengths. An array of size $n$ can be halved $\log_2 n$ times before reaching subarrays of size 1, matching the definition of [logarithmic scaling](/courses/algorithm-design-and-analysis/counting-steps#getting-the-big-o-without-the-algebra). For 8 elements, the subarrays divide across 3 levels ($\log_2 8 = 3$). For one million elements, the tree requires only about 20 levels.
- **Work per level:** merging all subarrays across any single level processes all $n$ elements, requiring $\Theta(n)$ operations per level.

$$
\underbrace{\log_2 n}_{\text{levels}} \times \underbrace{n}_{\text{work per level}} = \Theta(n \log n)
$$

Because merge sort always splits arrays evenly down the middle regardless of element values, best, average, and worst-case complexities are all **$\Theta(n \log n)$**.

Comparing $n^2$ with $n \log n$ in the [growth table](/courses/algorithm-design-and-analysis/counting-steps) illustrates the difference at scale: at one million elements, quadratic algorithms take hours, while $n \log n$ takes fractions of a second.

<Callout tone="orange" label="The price">
Merge sort is **not in place**. The merge operation requires a temporary array sized to the elements being merged, consuming $O(n)$ auxiliary memory ([space complexity](/courses/algorithm-design-and-analysis/counting-steps#space-is-a-cost-too)). When memory is limited, this extra space requirement is significant. [Quick sort](/courses/algorithm-design-and-analysis/quick-sort#the-idea), covered in the next lesson, sorts in place.
</Callout>

<Callout tone="orange" label="Common mistakes in the merge">
Two implementation bugs occur frequently. **Omitting remaining elements:** the main merge loop terminates when either half runs out. Without the following cleanup loops, elements from the unfinished half are omitted. **Writing `<` instead of `<=`: ** when comparing elements from left and right halves, using strict `<` pulls from the right half first on equal values. The array still sorts, but the sort is no longer stable.
</Callout>

Two additional properties:

- **Stable:** when elements at the front of both halves are equal, the merge step selects from the left half first (`a[i] <= a[j]`). Equal elements retain their relative initial order.
- **Efficient for external storage:** merging reads arrays sequentially from front to back, making it suitable for datasets that exceed available RAM and reside on disk.

Advanced Algorithms applies the same divide-and-conquer strategy to exponentiation and matrix multiplication, in [divide and conquer](/courses/advanced-algorithms/divide-and-conquer).

## The lab version

Labs often write merge sort by allocating sub-arrays directly on each recursive call:

```java
public static void mergeSort(int[] input) {
    int n = input.length;
    if (n < 2) return;                      // base case

    int mid = n / 2;
    int[] left = new int[mid];
    int[] right = new int[n - mid];
    for (int i = 0; i < mid; i++) left[i] = input[i];
    for (int i = mid; i < n; i++) right[i - mid] = input[i];

    mergeSort(left);                        // conquer
    mergeSort(right);
    merge(input, left, right);              // combine
}

private static void merge(int[] input, int[] left, int[] right) {
    int i = 0, j = 0, k = 0;
    while (i < left.length && j < right.length) {
        if (left[i] <= right[j]) input[k++] = left[i++];
        else                     input[k++] = right[j++];
    }
    while (i < left.length)  input[k++] = left[i++];
    while (j < right.length) input[k++] = right[j++];
}
```

Benchmarking merge sort on 100,000 random integers demonstrates its practical speed: it finishes in fractions of a second, whereas quadratic insertion sort on the same input requires minutes.

### Part 1: Midterm and written exam questions

**1.** *(First exam & lecture)* Define the Divide and Conquer algorithm design paradigm. List its three formal stages and explain the role of the base case. Name the three classic computational problems solved using Divide and Conquer identified in the course notes.

<ModelAnswer>
**Definition:**
Divide and Conquer is an algorithmic design strategy based on recursion that breaks a problem down into smaller subproblems of the same type until they become simple enough to solve directly.

**The three stages:**
1. **Divide:** Partition the problem instance into two or more smaller subproblems of the same kind.
2. **Conquer:** Solve each subproblem recursively. When a subproblem is small enough that it cannot or need not be divided further, solve it directly; this condition is the **base case**.
3. **Combine:** Merge the solutions of the subproblems to produce the final solution for the original problem instance.

**Role of the base case:**
The base case terminates the recursion. In Merge Sort, the base case is an array of size 0 or 1, which is sorted by definition and returned immediately without further division. Without a base case, recursive calls would continue indefinitely, resulting in a `StackOverflowError`.

**Three classic applications from course notes:**
1. **Maximum and minimum problem:** finding both the maximum and minimum elements in an array by dividing into halves and comparing subproblem extremes.
2. **Binary search:** searching a sorted array by halving the candidate range at each step.
3. **Sorting algorithms:** Merge Sort and Quick Sort.
</ModelAnswer>

**2.** *(Lecture recursion tree trace)* Trace Merge Sort on the 7-element array `[30, 20, 40, 5, 90, 80, 10]`. Illustrate how the array divides into subarrays, identify the base cases, and trace the bottom-up combine operations level by level until the array is fully sorted.

<ModelAnswer>
The input array has $n = 7$ elements: $\langle 30, 20, 40, 5, 90, 80, 10 \rangle$.
With integer division $mid = 7 / 2 = 3$, the array splits into:
- Left half ($A[0 \dots 2]$, size 3): $\langle 30, 20, 40 \rangle$
- Right half ($A[3 \dots 6]$, size 4): $\langle 5, 90, 80, 10 \rangle$

**Dividing the left half $\langle 30, 20, 40 \rangle$:**
- Split at $mid = 3 / 2 = 1$: left $\langle 30 \rangle$ (base case), right $\langle 20, 40 \rangle$.
- Right $\langle 20, 40 \rangle$ splits at $mid = 2 / 2 = 1$ into $\langle 20 \rangle$ and $\langle 40 \rangle$ (both base cases).
- Combine $\langle 20 \rangle$ and $\langle 40 \rangle \implies \langle 20, 40 \rangle$.
- Combine $\langle 30 \rangle$ and $\langle 20, 40 \rangle \implies \langle 20, 30, 40 \rangle$.

**Dividing the right half $\langle 5, 90, 80, 10 \rangle$:**
- Split at $mid = 4 / 2 = 2$: left $\langle 5, 90 \rangle$ and right $\langle 80, 10 \rangle$.
- Left $\langle 5, 90 \rangle$ splits into base cases $\langle 5 \rangle$ and $\langle 90 \rangle \implies$ combines to $\langle 5, 90 \rangle$.
- Right $\langle 80, 10 \rangle$ splits into base cases $\langle 80 \rangle$ and $\langle 10 \rangle \implies$ combines to $\langle 10, 80 \rangle$.
- Combine $\langle 5, 90 \rangle$ and $\langle 10, 80 \rangle \implies \langle 5, 10, 80, 90 \rangle$.

**Final combine step:**
Merge the two sorted halves:
$$
\text{Merge}(\langle 20, 30, 40 \rangle, \langle 5, 10, 80, 90 \rangle)
$$
- Compare 20 vs 5 $\to$ pick 5
- Compare 20 vs 10 $\to$ pick 10
- Compare 20 vs 80 $\to$ pick 20
- Compare 30 vs 80 $\to$ pick 30
- Compare 40 vs 80 $\to$ pick 40
- Left half exhausted; copy remaining right elements (80, 90).

**Final sorted array:** $\langle 5, 10, 20, 30, 40, 80, 90 \rangle$.
The tree has $\lceil \log_2 7 \rceil + 1 = 4$ levels.
</ModelAnswer>

**3.** *(Two-way merge trace)* Trace the execution of the `merge(inputArray, leftHalf, rightHalf)` method on `leftHalf = [2, 6, 11]` and `rightHalf = [4, 5, 7]`. Provide a trace table tracking pointer indices $l, r, m$, the compared values, the value placed into `inputArray`, and the cleanup phase when one half runs out. State the total number of comparisons.

<ModelAnswer>
Input subarrays: $leftHalf = \langle 2, 6, 11 \rangle$ ($leftSize = 3$) and $rightHalf = \langle 4, 5, 7 \rangle$ ($rightSize = 3$).

| Step | $l$ | $r$ | $m$ | Comparison | Action | $inputArray$ so far |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 0 | 0 | 0 | $2 \le 4$ (true) | take $leftHalf[0]$ (2), $l{++}$ | $\langle 2 \rangle$ |
| 2 | 1 | 0 | 1 | $6 \le 4$ (false) | take $rightHalf[0]$ (4), $r{++}$ | $\langle 2, 4 \rangle$ |
| 3 | 1 | 1 | 2 | $6 \le 5$ (false) | take $rightHalf[1]$ (5), $r{++}$ | $\langle 2, 4, 5 \rangle$ |
| 4 | 1 | 2 | 3 | $6 \le 7$ (true) | take $leftHalf[1]$ (6), $l{++}$ | $\langle 2, 4, 5, 6 \rangle$ |

| 7 | 2 | 3 | 5 | $l < leftSize$ ($2 < 3$ true) | copy $leftHalf[2]$ (11) directly, $l{++}$ | $\langle 2, 4, 5, 6, 7, 11 \rangle$ |

**Analysis:**
- **Key comparisons performed:** Exactly **5 comparisons**.
- The maximum number of comparisons needed to merge two sorted arrays of sizes $p$ and $q$ is $p + q - 1$. For $p = 3$ and $q = 3$, $3 + 3 - 1 = \mathbf{5\text{ comparisons}}$, which was reached here.
- Step 7 demonstrates why the cleanup loop is essential: when $rightHalf$ was exhausted, element 11 remained in $leftHalf$ and had to be copied over directly without additional comparisons.

**4.** *(Recurrence and stability)* State the recurrence relation for Merge Sort and derive its time complexity. Explain why standard array Merge Sort is not in-place, and prove why using `leftHalf[l] <= rightHalf[r]` guarantees stability while strict `<` violates it.

<ModelAnswer>
**Recurrence relation:**
Dividing an array of size $n$ takes constant time $O(1)$ to compute the midpoint. The algorithm then solves two subproblems of size $n / 2$. Merging the two sorted subarrays takes linear time $\Theta(n)$.
$$
T(n) = \begin{cases} 
\Theta(1) & \text{if } n < 2 \\ 
2T(n / 2) + \Theta(n) & \text{if } n \ge 2 
\end{cases}
$$

By the Master Theorem (or by summing the work across all $\log_2 n$ levels of the recursion tree, where each level does $c \cdot n$ work), $T(n) = \mathbf{\Theta(n \log n)}$. Because the tree always divides down the middle regardless of the values, best, worst, and average cases are all $\Theta(n \log n)$.

**Space complexity:**
Merge Sort is **not in place**. Merging two halves back into the original array without overwriting unexamined data requires allocating auxiliary storage. At the top level, this requires an extra array of size $n$. Therefore, its auxiliary space complexity is **$O(n)$**.

**Stability proof:**
When the fronts of both subarrays hold equal values ($leftHalf[l] == rightHalf[r]$):
- With `<=`, $leftHalf[l] \le rightHalf[r]$ evaluates to **true**. The algorithm takes the element from $leftHalf$, placing it into the merged array first. Because elements in $leftHalf$ originally preceded elements in $rightHalf$ in the parent array, their original relative order is preserved.
- With strict `<`, $leftHalf[l] < rightHalf[r]$ evaluates to **false**. The `else` branch executes, placing the element from $rightHalf$ first. This puts the right duplicate ahead of the left duplicate, breaking stability.
</ModelAnswer>
