# Linear vs Binary Search

**Searching** means finding a particular element among many. Either you find it (a *successful* search, usually returning its position) or you show it isn't there (an *unsuccessful* search, which by convention returns `-1`).

There are two basic ways to do it, and on large inputs the difference in speed between them is enormous.

## Linear search: check everything

Start at the beginning. Compare each element with the one you want. Stop when you find it or run out of array. Because it walks the array in sequence, the notes also call it **sequential search**. The value you're looking for is the **key** (`K` or `item` in the notes), and the position found is stored in `loc`, set to `-1` when the search fails.

The notes search for 15 in this array:

<SearchVisualizer algorithm="linear" array={[92, 87, 53, 10, 15, 23, 67]} target={15} />

15 ≠ 92, 15 ≠ 87, 15 ≠ 53, 15 ≠ 10, and the fifth comparison finds 15, so the search returns **index 4** (the fifth element, since indexes start at 0). Their second example searches for 3 in 6, 4, 1, 9, 7, 3, 2, 8: five misses, then a match at index 5 on the sixth comparison.

It's hard to make an algorithm simpler. Linear search works on **any** array, sorted or not, and needs **no** preparation. The notes list when to use it: when nothing is known about the array, when the array is unsorted, and when the list is **small**. It's also right when you'll only search once.

The notes' pseudocode, corrected:

```text
ALGORITHM SequentialSearch(A[0..n − 1], K)
for i ← 0 to n − 1 do
    if A[i] = K return i
return −1
```

<Callout tone="orange" label="A bug in the notes' version">
The notes put `else return −1` **inside** the loop. Then the first element that doesn't match ends the search, so it only ever checks `A[0]`. `return −1` belongs **after** the loop: you can only say the key is missing once you've checked every element. The notes also write the array as `A[0..n]`, which is $n + 1$ elements; it should be `A[0..n − 1]`.
</Callout>

### Analysis

- **Best case:** the target is first. **$O(1)$.**
- **Worst case:** the target is last or missing, so you check all $n$ elements. **$O(n)$.**
- **Average case:** about $n/2$ comparisons. **$O(n)$.** (The [counting steps lesson](/courses/algorithm-design-and-analysis/counting-steps) works this out exactly.)

The notes compare it with binary search and **hash tables**, which both search much faster. (A hash table computes where a value should be stored from the value itself, so a lookup usually goes straight to the right slot instead of walking the array. The [Data Structures course](/courses/data-structures/arrays-and-memory) covers it.) Linear search pays for its simplicity in speed.

## Binary search: throw away half

Now suppose the array is **sorted**. Look at the **middle** element. If it's the target, you're done. If it's smaller than the target, the target can't be anywhere on the left, because everything there is even smaller, so throw away the entire left half. If it's bigger, throw away the right half. Repeat on what's left.

Each comparison cuts the search space in half. It's [divide and conquer](/courses/algorithm-design-and-analysis/merge-sort#divide-and-conquer) again, with only one half to recurse into.

The notes' first example searches for $K = 70$ in a sorted array of 13 numbers:

<SearchVisualizer algorithm="binary" array={[3, 14, 27, 31, 39, 42, 55, 70, 74, 81, 85, 93, 98]} target={70} />

The notes call the ends `l` and `r` (left and right) and the middle `m`. Other examples call them `beg` and `end`, and the lab calls them `low` and `high`. They're the same three indexes:

| Iteration | l | r | m | A[m] | Decision |
| --- | --- | --- | --- | --- | --- |
| 1 | 0 | 12 | 6 | 55 | 70 > 55, so l ← 7 |
| 2 | 7 | 12 | 9 | 81 | 70 < 81, so r ← 8 |
| 3 | 7 | 8 | 7 | 70 | found, return 7 |

The middle is $m = \lfloor (l + r)/2 \rfloor$, rounded down: $(7 + 8)/2 = 7.5$ becomes 7.

Their second example looks for 15 in 3, 10, 15, 20, 35, 40, 60 with `beg` and `end`. Step 1: beg = 0, end = 6, mid = 3, and a[3] = 20 > 15, so end = 2. Step 2: mid = (0 + 2)/2 = 1, and a[1] = 10 < 15, so beg = 2. Step 3: mid = (2 + 2)/2 = 2, and a[2] = 15, so it returns index 2.

The third looks for 56 in 10, 12, 24, 29, 39, 40, 51, 56, 69. Mid = 4 (39 < 56, beg = 5), then mid = 6 (51 < 56, beg = 7), then mid = 7, which holds 56. The notes say the element is "found at 7th location", but index 7 is the **8th** element. Keep "index" (counted from 0) and "position" (counted from 1) apart, because exams mark that difference.

Try a target that isn't in the array, like `30`. Watch `low` and `high` close in until `low` passes `high`. At that point binary search *knows* the target is missing, without having looked at most of the array.

### Analysis

How many times can you halve $n$ before only one element is left? About $\log_2 n$ times. Each comparison is one halving, so that's also the number of comparisons. A million needs about 20 because $2^{20} = 1{,}048{,}576$: twenty halvings take a million down to one. The notes' 13-element example needs at most 4, since $2^3 = 8 \lt 13 \le 16 = 2^4$; searching for 70 happened to take 3.

| Array size $n$ | Linear search (worst) | Binary search (worst) |
| --- | --- | --- |
| 1,000 | 1,000 | 10 |
| 1,000,000 | 1,000,000 | 20 |
| 1,000,000,000 | 1,000,000,000 | 30 |

A billion elements take at most thirty comparisons. Best case **$O(1)$** (the first middle is the target), average and worst **$O(\log n)$**. The worst case keeps halving until one element is left.

The notes' pseudocode, with the textbook's arrow for assignment:

```text
ALGORITHM BinarySearch(A[0..n − 1], K)
l ← 0; r ← n − 1
while l ≤ r do
    m ← ⌊(l + r)/2⌋
    if K = A[m] return m
    else if K < A[m]  r ← m − 1
    else  l ← m + 1
return −1
```

The notes' advantages: each comparison throws away half the list, and it tells you whether the key is before or after the current position. On large lists it's far faster than linear search. Their disadvantages: it's easy to get wrong (see the three details below), and they say it "employs recursive approach". That one needs care: binary search *can* be written recursively, but the pseudocode above is a plain loop with no recursion at all.

<Callout tone="orange" label="The catch">
Binary search **only works on sorted data**, in ascending numeric or dictionary order. If the array isn't sorted, you have to sort it first in $O(n \log n)$, which only pays off if you'll search it many times. For a single search on unsorted data, linear search wins.
</Callout>

## The Java

```java
static int binarySearch(int[] a, int x) {
    int low = 0, high = a.length - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (a[mid] == x) return mid;
        else if (a[mid] < x) low = mid + 1;
        else high = mid - 1;
    }
    return -1;
}
```

<Callout tone="orange" label="Common mistake: binary search on unsorted data">
Binary search on an unsorted array doesn't crash. It quietly gives wrong answers. Search for 9 in 4, 9, 1, 7, 3: the middle is 1, and since 9 > 1 it throws away the left half, which is where the 9 was. It returns −1 for a value that's right there. If the data might not be sorted, sort it first or use linear search.
</Callout>

Binary search is easy to describe and easy to get *slightly* wrong. Check these three details every time:

1. **Use `low <= high`.** With `low < high`, a one-element range is never checked, and you'll miss targets sitting at the edges.
2. **`low = mid + 1` and `high = mid - 1`.** You already know `a[mid]` isn't the target, so exclude it. Write `low = mid` and the loop can get stuck forever.
3. **Use `low + (high - low) / 2` instead of `(low + high) / 2`.** On a huge array, `low + high` can be bigger than the largest `int` and overflow into a negative number. This exact bug lived in Java's own `Arrays.binarySearch` for about nine years before it was found in 2006.

A quick lab test: fill an array with even numbers using `array[i] = i * 2`, so it's sorted by construction, then search for `8` (it should return index `4`) and for `7` (it should return `-1`). The lab sheet prints `"Found at location: " + (x+1)`, so it says **5**: it reports the position counted from 1, not the index.

<Callout tone="orange" label="A bug in the lab's linear search">
The lab's `linearSearch` loops `for (int i = 0; i < array.length - 1; i++)`, which stops one short and never checks the last element. Searching for a value that's only in the last slot returns `-1`. The condition should be `i < array.length`.
</Callout>

## Where this shows up today

<ApplicationsGrid>
  <PracticalApplication title="Database indexes" tool="B-TREES">
    An index on a database column keeps the values sorted so lookups don't scan every row. A B-tree is binary search generalised to "many-way" search, built for disks.
  </PracticalApplication>
  <PracticalApplication title="git bisect" tool="DEBUGGING">
    Somewhere in your last 1,000 commits a bug appeared. `git bisect` checks the middle commit, you say "good" or "bad," and it halves the range. About 10 tests to find the culprit.
  </PracticalApplication>
  <PracticalApplication title="Java standard library" tool="JDK">
    `Arrays.binarySearch` and `Collections.binarySearch` are built in, and a `TreeMap` lookup is binary search over a balanced tree.
  </PracticalApplication>
  <PracticalApplication title="Binary search on the answer" tool="INTERVIEWS">
    "What's the smallest speed that finishes in time?" If you can check a guess, and bigger guesses are always better, you can binary search the answer itself. Interviewers like this technique.
  </PracticalApplication>
</ApplicationsGrid>
