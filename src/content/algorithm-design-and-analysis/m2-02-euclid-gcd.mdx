# Euclid's GCD: A 2,300-Year-Old Algorithm

Around 300 BC, Euclid wrote down a method for finding the greatest common divisor of two numbers. It's one of the oldest known algorithms and still the one everyone uses. A version of it runs inside the encryption that protects your phone's connections.

## The problem

The **greatest common divisor** of two non-negative integers $m$ and $n$ (not both zero), written $\gcd(m, n)$, is the largest integer that divides both of them **evenly**, with remainder zero.

The notes ask you to find these "by inspection", meaning by looking at the numbers and their divisors rather than running an algorithm:

- $\gcd(24, 54) = 6$
- $\gcd(18, 42) = 6$
- $\gcd(45, 210) = 15$
- $\gcd(97, 20) = 1$. Numbers like these, with no common divisor except 1, are called *[coprime](/courses/computational-mathematics/divisibility-and-euclid#greatest-common-divisor)*.

## The obvious way

Try every candidate. Start at the smaller of the two numbers and count down until you find one that divides both:

```java
static int gcdBruteForce(int m, int n) {
    for (int d = Math.min(m, n); d >= 1; d--)
        if (m % d == 0 && n % d == 0) return d;
    return Math.max(m, n);     // one of them is 0
}
```

It's correct, but in the worst case (coprime numbers) it tries every value down to 1. That's $O(\min(m, n))$. For two 10-digit numbers, that's billions of divisions.

## Euclid's idea

Euclid's whole algorithm follows from one equality:

$$
\gcd(m, n) = \gcd(n,\ m \bmod n)
$$

where $m \bmod n$ is the remainder when you divide $m$ by $n$ (`m % n` in Java).

**Why is that true?** Write $m = q \cdot n + r$, where $r$ is the remainder. Any number that divides both $m$ and $n$ also divides $r = m - q \cdot n$. And any number that divides both $n$ and $r$ also divides $m = q \cdot n + r$. So the pairs $(m, n)$ and $(n, r)$ have exactly the same common divisors, and therefore the same *greatest* one.

$(n, r)$ is also a smaller problem, because $r$ is always less than $n$. Keep applying the rule and the numbers keep shrinking until the second one becomes **0**. Every number divides 0 (because $0 = 0 \times m$, remainder zero), so the common divisors of $m$ and 0 are just the divisors of $m$, and the greatest of those is $m$ itself. So $\gcd(m, 0) = m$, and that's the answer.

The notes' example shows the whole chain on one line:

$$
\gcd(60, 24) = \gcd(24, 12) = \gcd(12, 0) = 12
$$

$60 \bmod 24 = 12$ (since $60 = 2 \times 24 + 12$), then $24 \bmod 12 = 0$, and the second number is 0, so the answer is 12.

## Watch it run

The table is how you'd write it on an exam: one row per division, with $m$ and $n$ sliding one column left each time. Try your own numbers, including two consecutive Fibonacci numbers like $89$ and $55$, which are the slowest possible input for Euclid. Each division of one Fibonacci number by the one before it goes in only **once**, so the remainder is the next Fibonacci number down, and the pair shrinks as slowly as it possibly can: $(89, 55) \to (55, 34) \to (34, 21) \to \cdots$

As steps:

1. If $n = 0$, return $m$ and stop.
2. Divide $m$ by $n$ and call the remainder $r$.
3. Set $m \leftarrow n$ and $n \leftarrow r$. Go back to step 1.

And in the notes' pseudocode, where `!=` means "not equal":

```text
ALGORITHM Euclid(m, n)
// input: two non-negative, not-both-zero integers m and n
while n != 0 do
    r ← m mod n
    m ← n
    n ← r
return m
```

### The homework: gcd(31415, 14142)

The notes set this one by Euclid's algorithm. Each row divides $m$ by $n$, writing $m = q \times n + r$, and the next row moves $n$ and $r$ one column left:

| m | n | m = q × n + r | r |
| --- | --- | --- | --- |
| 31415 | 14142 | 31415 = 2 × 14142 + 3131 | 3131 |
| 14142 | 3131 | 14142 = 4 × 3131 + 1618 | 1618 |
| 3131 | 1618 | 3131 = 1 × 1618 + 1513 | 1513 |
| 1618 | 1513 | 1618 = 1 × 1513 + 105 | 105 |
| 1513 | 105 | 1513 = 14 × 105 + 43 | 43 |
| 105 | 43 | 105 = 2 × 43 + 19 | 19 |
| 43 | 19 | 43 = 2 × 19 + 5 | 5 |
| 19 | 5 | 19 = 3 × 5 + 4 | 4 |
| 5 | 4 | 5 = 1 × 4 + 1 | 1 |
| 4 | 1 | 4 = 4 × 1 + 0 | 0 |
| 1 | 0 | stop | |

So $\gcd(31415, 14142) = 1$: the two numbers are coprime. Ten divisions settled it, where counting down from 14142 would have taken 14,142 tries. You can check any row in the visualizer above by typing the two numbers in.

The lab writes it as a `void` method that prints the answer:

```java
public static void GCD(int m, int n) {
    int r = 0;
    while (n != 0) {
        r = m % n;
        m = n;
        n = r;
    }
    System.out.println("The GCD is " + m);
}
```

Its `main` calls `GCD(45, 210)` and prints 15. Printing inside the method works for the lab, but you can't use the answer anywhere else, for example to [simplify a fraction](#where-this-shows-up-today). Returning it is more useful:

```java
static int gcd(int m, int n) {
    while (n != 0) {
        int r = m % n;
        m = n;
        n = r;
    }
    return m;
}
```

<Callout tone="orange" label="Common mistake: updating in the wrong order">
The two assignments `m = n;` and `n = r;` must happen in that order. Write `n = r;` first and the old value of `n` is gone before `m` can take it, so `m` gets the remainder instead. On gcd(60, 24) that gives $m = 12, n = 12$, then $m = 0, n = 0$, and the loop returns 0. When you trace by hand, write each new row from the **previous** row's values, never from half-updated ones.
</Callout>

Or recursively, which reads almost exactly like the equality:

```java
static int gcd(int m, int n) {
    return n == 0 ? m : gcd(n, m % n);
}
```

## Analysis

Every two steps, the remainder drops to **less than half** of what it was. (If $n \le m/2$, then $m \bmod n \lt n \le m/2$. If $n \gt m/2$, then $m \bmod n = m - n \lt m/2$.)

Halving every two steps means the number of steps is at most about $2 \log_2 n$. Euclid's algorithm is **$O(\log n)$**, the same growth as [binary search](/courses/algorithm-design-and-analysis/linear-and-binary-search#binary-search-throw-away-half). For two 10-digit numbers, that's a few dozen divisions instead of billions.

<Callout tone="sky" label="Order doesn't matter">
What if $m \lt n$, like $\gcd(45, 210)$? The first step computes $45 \bmod 210 = 45$, so the pair becomes $(210, 45)$. Euclid swaps them for you, for the price of one division.
</Callout>

Run the same divisions backwards and they also give you the numbers $x$ and $y$ with $mx + ny = \gcd(m, n)$. That's the [extended Euclidean algorithm](/courses/computational-mathematics/modular-inverses#the-extended-euclidean-algorithm), which ciphers use to undo multiplication modulo a number.

## Where this shows up today

<ApplicationsGrid>
  <PracticalApplication title="RSA encryption" tool="CRYPTOGRAPHY">
    Generating an RSA key needs numbers that are coprime, and computing the private key uses the *extended* Euclidean algorithm. That's Euclid running on numbers hundreds of digits long, which is only practical because it's $O(\log n)$.
  </PracticalApplication>
  <PracticalApplication title="Simplifying fractions" tool="MATH LIBRARIES">
    $\frac{210}{45}$ becomes $\frac{14}{3}$ by dividing both by their gcd, 15. Every exact-fraction library does this after each operation.
  </PracticalApplication>
  <PracticalApplication title="Screen aspect ratios" tool="UI">
    1920 × 1080 → divide both by $\gcd = 120$ → 16:9.
  </PracticalApplication>
  <PracticalApplication title="Java's BigInteger" tool="JDK">
    `BigInteger.gcd()` handles numbers too big for a `long`, using the same idea.
  </PracticalApplication>
</ApplicationsGrid>

<Callout tone="violet" label="LCM for free">
The least common multiple comes straight from the gcd: $\operatorname{lcm}(m, n) = \dfrac{m \cdot n}{\gcd(m, n)}$. In Java, write it as `m / gcd(m, n) * n`, dividing first so the multiplication doesn't overflow.
</Callout>
