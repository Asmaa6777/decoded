# Euclid's GCD: A 2,300-Year-Old Algorithm

Around 300 BC, the Greek mathematician Euclid documented an efficient method for finding the greatest common divisor of two integers. It remains one of the oldest numerical algorithms in active use, running inside the cryptographic routines that protect secure network connections.

## The problem

The **greatest common divisor** of two non-negative integers $m$ and $n$ (not both zero), written $\gcd(m, n)$, is the largest integer that [divides](/courses/computational-mathematics/divisibility-and-euclid#divisibility) both numbers without a remainder.

Finding small GCD values by inspection means identifying common factors directly without executing an algorithm:

- $\gcd(24, 54) = 6$
- $\gcd(18, 42) = 6$
- $\gcd(45, 210) = 15$
- $\gcd(97, 20) = 1$. Two numbers whose only common divisor is 1 are called *[coprime](/courses/computational-mathematics/divisibility-and-euclid#greatest-common-divisor)* (or relatively prime).

## Brute force approach

The direct brute force approach tests every candidate integer. Starting at $\min(m, n)$, the loop counts downward until it finds a number that divides both $m$ and $n$ without a remainder:

```java
static int gcdBruteForce(int m, int n) {
    for (int d = Math.min(m, n); d >= 1; d--)
        if (m % d == 0 && n % d == 0) return d;
    return Math.max(m, n);     // one of them is 0
}
```

This method is correct, but in the worst case (coprime inputs) it checks every integer down to 1. That requires $O(\min(m, n))$ iterations. For two 10-digit numbers, that involves billions of division operations.

## Euclid's idea

**Euclid's algorithm** computes the greatest common divisor using a single recurrence relation:

$$
\gcd(m, n) = \gcd(n,\ m \bmod n)
$$

where $m \bmod n$ denotes the remainder when dividing $m$ by $n$ (`m % n` in Java, from [modular arithmetic](/courses/computational-mathematics/modular-arithmetic#the-mod-operation)).

**Why is that true?** Express the integer division as $m = q \cdot n + r$, where $q$ is the integer quotient and $r$ is the remainder ($0 \le r < n$). Any divisor that divides both $m$ and $n$ must also divide their difference, $r = m - q \cdot n$. Likewise, any divisor that divides both $n$ and $r$ must also divide their sum, $m = q \cdot n + r$. Because $(m, n)$ and $(n, r)$ share identical sets of common divisors, they share the identical greatest common divisor.

Because $r < n$, the subproblem $(n, r)$ is strictly smaller. Repeatedly applying this reduction shrinks the numbers until the second argument reaches 0. Every non-zero integer divides 0 (since $0 = 0 \cdot m$). Thus, the common divisors of $m$ and 0 are simply the divisors of $m$, the largest of which is $m$ itself. When the second value reaches 0, the algorithm terminates with $\gcd(m, 0) = m$.

For example, tracing $\gcd(60, 24)$:

$$
\gcd(60, 24) = \gcd(24, 12) = \gcd(12, 0) = 12
$$

First, $60 \bmod 24 = 12$ because $60 = 2 \cdot 24 + 12$. Next, $24 \bmod 12 = 0$. Because the second value is now 0, the process halts and returns 12.

Geometrically, Euclid's division tiles an $m \times n$ floor with squares of size $n \times n$, then recursively tiles the remaining strip with squares of size $r \times r$. The side length of the final square that perfectly tiles the floor is $\gcd(m, n)$:

## Watch it run

<EuclidVisualizer m={210} n={45} />

The table layout reflects standard exam presentation: each row performs one division, shifting $n$ and $r$ into the next row's inputs. You can test custom inputs in the visualizer above. Consecutive [Fibonacci numbers](/courses/algorithm-design-and-analysis/dynamic-programming#the-problem-with-plain-recursion), such as 89 and 55, represent the worst-case input for Euclid's algorithm. Because dividing one Fibonacci number by the preceding Fibonacci number yields a quotient of 1, the remainder is always the next smaller Fibonacci number: $(89, 55) \to (55, 34) \to (34, 21) \to \dots$, causing the values to shrink at the slowest possible rate.

The algorithm proceeds in three steps:

1. If $n = 0$, return $m$ and terminate.
2. Divide $m$ by $n$ and let the remainder be $r$.
3. Set $m \leftarrow n$ and $n \leftarrow r$, then return to step 1.

In pseudocode, where `!=` means not equal:

```text
ALGORITHM Euclid(m, n)
// input: two non-negative, not-both-zero integers m and n
while n != 0 do
    r ← m mod n
    m ← n
    n ← r
return m
```

### Worked example: gcd(31415, 14142)

Consider finding the GCD of 31,415 and 14,142 using Euclid's algorithm. Each row performs the division $m = q \times n + r$ and shifts $n$ and $r$ one column to the left:

| m | n | m = q × n + r | r |
| --- | --- | --- | --- |
| 31415 | 14142 | 31415 = 2 × 14142 + 3131 | 3131 |
| 14142 | 3131 | 14142 = 4 × 3131 + 1618 | 1618 |
| 3131 | 1618 | 3131 = 1 × 1618 + 1513 | 1513 |
| 1618 | 1513 | 1618 = 1 × 1513 + 105 | 105 |
| 1513 | 105 | 1513 = 14 × 105 + 43 | 43 |
| 105 | 43 | 105 = 2 × 43 + 19 | 19 |
| 43 | 19 | 43 = 2 × 19 + 5 | 5 |
| 19 | 5 | 19 = 3 × 5 + 4 | 4 |
| 5 | 4 | 5 = 1 × 4 + 1 | 1 |
| 4 | 1 | 4 = 4 × 1 + 0 | 0 |
| 1 | 0 | stop | |

Because the final non-zero remainder is 1, $\gcd(31415, 14142) = 1$, confirming that 31,415 and 14,142 are coprime. Euclid's algorithm solves this in 10 division steps, whereas the linear brute force approach would require 14,142 iterations. You can verify each row in the visualizer above by entering both numbers.

In introductory programming labs, the method is often written as a `void` procedure that prints the result:

```java
public static void GCD(int m, int n) {
    int r = 0;
    while (n != 0) {
        r = m % n;
        m = n;
        n = r;
    }
    System.out.println("The GCD is " + m);
}
```

Calling `GCD(45, 210)` outputs 15. However, returning the integer value is more versatile, allowing the caller to use the result in further calculations such as [fraction simplification](#where-this-shows-up-today):

```java
static int gcd(int m, int n) {
    while (n != 0) {
        int r = m % n;
        m = n;
        n = r;
    }
    return m;
}
```

<Callout tone="orange" label="Common mistake: updating in the wrong order">
The assignments `m = n;` and `n = r;` must execute in this exact sequence. If you update `n = r;` first, the original value of `n` is overwritten before `m` can receive it, causing `m` to receive `r` instead. Tracing $\gcd(60, 24)$ with that bug produces $m = 12, n = 12$, followed by $m = 0, n = 0$, returning an incorrect result of 0. When tracing by hand, derive each row strictly from the preceding row rather than partially updated variables.
</Callout>

Euclid's algorithm can also be written recursively in a single line, mirroring the mathematical recurrence:

```java
static int gcd(int m, int n) {
    return n == 0 ? m : gcd(n, m % n);
}
```

## Analysis

Every two steps, the remainder decreases by at least half:

- If $n \le m/2$, then $m \bmod n \lt n \le m/2$.
- If $n \gt m/2$, then $m \bmod n = m - n \lt m/2$.

Because the remainder is at least halved every two iterations, the maximum number of division steps is roughly $2 \log_2 n$. Euclid's algorithm runs in **$O(\log n)$** time, exhibiting the same logarithmic complexity as [binary search](/courses/algorithm-design-and-analysis/linear-and-binary-search#binary-search-throw-away-half). For two 10-digit numbers, Euclid terminates in a few dozen divisions instead of billions.

<Callout tone="sky" label="Order does not matter">
If the smaller argument is passed first, as in $\gcd(45, 210)$, the first division computes $45 \bmod 210 = 45$. The next state becomes $(210, 45)$. The algorithm automatically swaps the values on the first step at the cost of one modulo operation.
</Callout>

Reversing the division steps computes integer coefficients $x$ and $y$ satisfying Bézout's identity, $mx + ny = \gcd(m, n)$. This is the [extended Euclidean algorithm](/courses/computational-mathematics/modular-inverses#the-extended-euclidean-algorithm), widely used in asymmetric cryptography to compute modular multiplicative inverses.

## Where this shows up today

  <PracticalApplication title="RSA encryption" tool="CRYPTOGRAPHY">
    [RSA encryption](/courses/computational-mathematics/what-is-cryptography#two-kinds-of-system) key generation requires picking coprime integers, and computing the private decryption key relies on the extended Euclidean algorithm. Euclid's algorithm operates on keys with hundreds of decimal digits, which is computationally feasible only because the algorithm runs in logarithmic time.
  </PracticalApplication>
  <PracticalApplication title="Simplifying fractions" tool="MATH LIBRARIES">
    Rational number arithmetic reduces fractions like $\frac{210}{45}$ to $\frac{14}{3}$ by dividing both numerator and denominator by $\gcd(210, 45) = 15$. Exact arithmetic libraries apply this reduction after each operation.
  </PracticalApplication>
  <PracticalApplication title="Screen aspect ratios" tool="UI">
    Display dimensions such as $1920 \times 1080$ reduce to an [aspect ratio](/courses/computer-graphics/screen-resolution#aspect-ratio) of $16:9$ by dividing width and height by $\gcd(1920, 1080) = 120$.
  </PracticalApplication>
  <PracticalApplication title="Java standard library" tool="JDK">
    `BigInteger.gcd()` handles arbitrarily large integers, providing an efficient implementation of the Euclidean algorithm for cryptographic workloads.
  </PracticalApplication>
</ApplicationsGrid>

<Callout tone="violet" label="LCM for free">
The least common multiple connects directly to the greatest common divisor through the product formula:

$$
\operatorname{lcm}(m, n) = \frac{m \cdot n}{\gcd(m, n)}
$$

In Java, compute this as `(m / gcd(m, n)) * n`, dividing first so the intermediate multiplication does not overflow integer bounds.
</Callout>

**1.** *(Lab trace: GCD(45, 210) and automatic operand swapping)* In Lab 7, Euclid's algorithm is invoked as `GCD(45, 210)`.
1. Trace the execution step by step. For each iteration of `while (n != 0)`, state the values of dividend $m$, divisor $n$, remainder $r = m \bmod n$, and the updated assignments $m = n$ and $n = r$.
2. Detail what happens during the very first division step ($45 \bmod 210$). Why does Euclid's algorithm never require an initial check or swap to ensure $m \ge n$?
3. How many total division/modulo operations are performed before the method outputs the answer?

<ModelAnswer>
The inputs are $m = 45$ and $n = 210$.

**(a) Step-by-step trace:**

| Iteration | Initial $m$ | Initial $n$ | Division $m = q \cdot n + r$ | Remainder $r$ | Updated $m \leftarrow n$ | Updated $n \leftarrow r$ |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 45 | 210 | $45 = 0 \times 210 + 45$ | 45 | 210 | 45 |
| 2 | 210 | 45 | $210 = 4 \times 45 + 30$ | 30 | 45 | 30 |
| 3 | 45 | 30 | $45 = 1 \times 30 + 15$ | 15 | 30 | 15 |
| 4 | 30 | 15 | $30 = 2 \times 15 + 0$ | 0 | 15 | 0 |

- **Termination:** In iteration 5, `n == 0` evaluates to true. The loop halts and the method outputs: `"The GCD is 15"`.

**(b) Automatic operand swap on smaller first argument:**
- When $m < n$, the integer quotient $q = \lfloor m / n \rfloor$ is 0, and the remainder is simply $r = m \bmod n = m$.
- The assignments $m \leftarrow n$ and $n \leftarrow r$ place the larger number into $m$ and the smaller number into $n$.
- Therefore, if $m < n$, the algorithm automatically swaps the two inputs on the very first step at the cost of exactly one modulo operation, without needing any `if (m < n) swap(...)` guard.

**(c) Total division count:**
- Exactly **4 division operations** are performed (1 swap division + 3 reduction divisions).
</ModelAnswer>

**3.** *(Worst-case input analysis: Lamé's Theorem and Fibonacci numbers)*
1. Trace Euclid's algorithm on the consecutive Fibonacci numbers $m = 89$ and $n = 55$. State the quotient and remainder at each step.
2. Explain why consecutive Fibonacci numbers represent the worst-case input for Euclid's algorithm.
3. State Lamé's Theorem and verify that its bound holds for $n = 55$.

<ModelAnswer>
**(a) Trace on Fibonacci numbers $(89, 55)$:**
- Step 1: $89 = 1 \times 55 + 34 \implies r = 34$
- Step 2: $55 = 1 \times 34 + 21 \implies r = 21$
- Step 3: $34 = 1 \times 21 + 13 \implies r = 13$
- Step 4: $21 = 1 \times 13 + 8 \implies r = 8$
- Step 5: $13 = 1 \times 8 + 5 \implies r = 5$
- Step 6: $8 = 1 \times 5 + 3 \implies r = 3$
- Step 7: $5 = 1 \times 3 + 2 \implies r = 2$
- Step 8: $3 = 1 \times 2 + 1 \implies r = 1$
- Step 9: $2 = 2 \times 1 + 0 \implies r = 0$
- Step 10: $n = 0$, algorithm halts and returns $m = \mathbf{1}$.
- Total division operations: **9 divisions**.

**(b) Why Fibonacci numbers are the worst case:**
- In the division $m = q \cdot n + r$, the remainder $r = m - q \cdot n$ shrinks fastest when $q$ is large.
- The smallest possible quotient for positive integers with non-zero remainder is $q = 1$.
- When $q = 1$ at every step, $r = m - n$. For consecutive Fibonacci numbers $F_{k+1}$ and $F_k$, the remainder is $F_{k+1} - F_k = F_{k-1}$, which is the immediately preceding Fibonacci number.
- Because every quotient is 1 (except the final step where $F_2 = 2 \cdot F_1 + 0$), the values shrink at the slowest possible rate, maximizing the number of iterations required to reach 0.

**(c) Lamé's Theorem:**
- **Theorem:** The number of division steps in Euclid's algorithm never exceeds 5 times the number of decimal digits in the smaller input number $n$:
  $$
  \text{steps} \le 5 \cdot \text{digits}_{10}(n)
  $$
- For $n = 55$, the number of decimal digits is 2.
- The theorem bounds the number of steps by $5 \times 2 = 10\text{ steps}$.
- The actual number of steps observed is $9$, which strictly satisfies $9 \le 10$.
</ModelAnswer>

**4.** *(Variable overwrite bug and Least Common Multiple derivation)*
1. A student implements the loop body of Euclid's algorithm in Java as:
   ```java
   r = m % n;
   n = r;
   m = n;
   ```
   Trace this faulty implementation on $m = 60$ and $n = 24$. Identify the bug and provide the corrected statements.
2. Given $\gcd(60, 24) = 12$, compute $\operatorname{lcm}(60, 24)$ using the product formula. Explain why computing `(m / gcd) * n` in Java is safer than `(m * n) / gcd`.

<ModelAnswer>
**(a) Faulty assignment order trace on $(60, 24)$:**
- **Iteration 1:**
  - $r = 60 \bmod 24 = 12$.
  - `n = r;` sets $n = 12$.
  - `m = n;` copies the newly updated $n$ into $m$, setting $m = 12$.
  - Both variables now equal 12! The original value of $n$ (24) was completely lost before $m$ could receive it.
- **Iteration 2:**
  - $r = 12 \bmod 12 = 0$.
  - `n = r;` sets $n = 0$.
  - `m = n;` sets $m = 0$.
- **Termination:**
  - The loop checks `while (n != 0)`: $0 \ne 0$ is false, so the loop terminates.
  - The method returns $m = \mathbf{0}$, which is completely incorrect ($\gcd(60, 24) = 12$).
- **The fix:** Update $m$ with $n$ *before* updating $n$ with $r$:
  ```java
  r = m % n;
  m = n;
  n = r;
  ```

**(b) Least Common Multiple calculation:**
- The relationship between GCD and LCM for any positive integers $m$ and $n$ is:
  $$
  \operatorname{lcm}(m, n) = \frac{m \cdot n}{\gcd(m, n)}
  $$
- For $m = 60$ and $n = 24$:
  $$
  \operatorname{lcm}(60, 24) = \frac{60 \times 24}{12} = \frac{1{,}440}{12} = \mathbf{120}
  $$
- **Integer overflow prevention in code:**
  - If we write `(m * n) / gcd(m, n)`, the intermediate product $m \cdot n$ can easily exceed `Integer.MAX_VALUE` ($2^{31} - 1 \approx 2.14 \times 10^9$) even when the final LCM fits comfortably within an `int`. For example, with $m = 100{,}000$ and $n = 100{,}000$ ($\gcd = 100{,}000$, $\operatorname{lcm} = 100{,}000$), $m \cdot n = 10^{10}$ overflows 32-bit signed int, producing an erroneous negative result.
  - Evaluating `(m / gcd(m, n)) * n` divides first. Because $\gcd(m, n)$ divides $m$ evenly by definition, `m / gcd(m, n)` produces an exact integer that is strictly smaller than $m$, preventing unnecessary intermediate overflow.
</ModelAnswer>
