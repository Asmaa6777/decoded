# Euclid's GCD: A 2,300-Year-Old Algorithm

Around 300 BC, the Greek mathematician Euclid documented an efficient method for finding the greatest common divisor of two integers. It remains one of the oldest numerical algorithms in active use, running inside the cryptographic routines that protect secure network connections.

## The problem

The **greatest common divisor** of two non-negative integers $m$ and $n$ (not both zero), written $\gcd(m, n)$, is the largest integer that divides both numbers without a remainder.

Finding small GCD values by inspection means identifying common factors directly without executing an algorithm:

- $\gcd(24, 54) = 6$
- $\gcd(18, 42) = 6$
- $\gcd(45, 210) = 15$
- $\gcd(97, 20) = 1$. Two numbers whose only common divisor is 1 are called *[coprime](/courses/computational-mathematics/divisibility-and-euclid#greatest-common-divisor)* (or relatively prime).

## Brute force approach

The direct brute force approach tests every candidate integer. Starting at $\min(m, n)$, the loop counts downward until it finds a number that divides both $m$ and $n$ without a remainder:

```java
static int gcdBruteForce(int m, int n) {
    for (int d = Math.min(m, n); d >= 1; d--)
        if (m % d == 0 && n % d == 0) return d;
    return Math.max(m, n);     // one of them is 0
}
```

This method is correct, but in the worst case (coprime inputs) it checks every integer down to 1. That requires $O(\min(m, n))$ iterations. For two 10-digit numbers, that involves billions of division operations.

## Euclid's idea

**Euclid's algorithm** computes the greatest common divisor using a single recurrence relation:

$$
\gcd(m, n) = \gcd(n,\ m \bmod n)
$$

where $m \bmod n$ denotes the remainder when dividing $m$ by $n$ (`m % n` in Java).

**Why is that true?** Express the integer division as $m = q \cdot n + r$, where $q$ is the integer quotient and $r$ is the remainder ($0 \le r < n$). Any divisor that divides both $m$ and $n$ must also divide their difference, $r = m - q \cdot n$. Likewise, any divisor that divides both $n$ and $r$ must also divide their sum, $m = q \cdot n + r$. Because $(m, n)$ and $(n, r)$ share identical sets of common divisors, they share the identical greatest common divisor.

Because $r < n$, the subproblem $(n, r)$ is strictly smaller. Repeatedly applying this reduction shrinks the numbers until the second argument reaches 0. Every non-zero integer divides 0 (since $0 = 0 \cdot m$). Thus, the common divisors of $m$ and 0 are simply the divisors of $m$, the largest of which is $m$ itself. When the second value reaches 0, the algorithm terminates with $\gcd(m, 0) = m$.

For example, tracing $\gcd(60, 24)$:

$$
\gcd(60, 24) = \gcd(24, 12) = \gcd(12, 0) = 12
$$

First, $60 \bmod 24 = 12$ because $60 = 2 \cdot 24 + 12$. Next, $24 \bmod 12 = 0$. Because the second value is now 0, the process halts and returns 12.

## Watch it run

The table layout reflects standard exam presentation: each row performs one division, shifting $n$ and $r$ into the next row's inputs. You can test custom inputs in the visualizer above. Consecutive Fibonacci numbers, such as 89 and 55, represent the worst-case input for Euclid's algorithm. Because dividing one Fibonacci number by the preceding Fibonacci number yields a quotient of 1, the remainder is always the next smaller Fibonacci number: $(89, 55) \to (55, 34) \to (34, 21) \to \dots$, causing the values to shrink at the slowest possible rate.

The algorithm proceeds in three steps:

1. If $n = 0$, return $m$ and terminate.
2. Divide $m$ by $n$ and let the remainder be $r$.
3. Set $m \leftarrow n$ and $n \leftarrow r$, then return to step 1.

In pseudocode, where `!=` means not equal:

```text
ALGORITHM Euclid(m, n)
// input: two non-negative, not-both-zero integers m and n
while n != 0 do
    r ← m mod n
    m ← n
    n ← r
return m
```

### Worked example: gcd(31415, 14142)

Consider finding the GCD of 31,415 and 14,142 using Euclid's algorithm. Each row performs the division $m = q \times n + r$ and shifts $n$ and $r$ one column to the left:

| m | n | m = q × n + r | r |
| --- | --- | --- | --- |
| 31415 | 14142 | 31415 = 2 × 14142 + 3131 | 3131 |
| 14142 | 3131 | 14142 = 4 × 3131 + 1618 | 1618 |
| 3131 | 1618 | 3131 = 1 × 1618 + 1513 | 1513 |
| 1618 | 1513 | 1618 = 1 × 1513 + 105 | 105 |
| 1513 | 105 | 1513 = 14 × 105 + 43 | 43 |
| 105 | 43 | 105 = 2 × 43 + 19 | 19 |
| 43 | 19 | 43 = 2 × 19 + 5 | 5 |
| 19 | 5 | 19 = 3 × 5 + 4 | 4 |
| 5 | 4 | 5 = 1 × 4 + 1 | 1 |
| 4 | 1 | 4 = 4 × 1 + 0 | 0 |
| 1 | 0 | stop | |

Because the final non-zero remainder is 1, $\gcd(31415, 14142) = 1$, confirming that 31,415 and 14,142 are coprime. Euclid's algorithm solves this in 10 division steps, whereas the linear brute force approach would require 14,142 iterations. You can verify each row in the visualizer above by entering both numbers.

In introductory programming labs, the method is often written as a `void` procedure that prints the result:

```java
public static void GCD(int m, int n) {
    int r = 0;
    while (n != 0) {
        r = m % n;
        m = n;
        n = r;
    }
    System.out.println("The GCD is " + m);
}
```

Calling `GCD(45, 210)` outputs 15. However, returning the integer value is more versatile, allowing the caller to use the result in further calculations such as [fraction simplification](#where-this-shows-up-today):

```java
static int gcd(int m, int n) {
    while (n != 0) {
        int r = m % n;
        m = n;
        n = r;
    }
    return m;
}
```

<Callout tone="orange" label="Common mistake: updating in the wrong order">
The assignments `m = n;` and `n = r;` must execute in this exact sequence. If you update `n = r;` first, the original value of `n` is overwritten before `m` can receive it, causing `m` to receive `r` instead. Tracing $\gcd(60, 24)$ with that bug produces $m = 12, n = 12$, followed by $m = 0, n = 0$, returning an incorrect result of 0. When tracing by hand, derive each row strictly from the preceding row rather than partially updated variables.
</Callout>

Euclid's algorithm can also be written recursively in a single line, mirroring the mathematical recurrence:

```java
static int gcd(int m, int n) {
    return n == 0 ? m : gcd(n, m % n);
}
```

## Analysis

Every two steps, the remainder decreases by at least half:

- If $n \le m/2$, then $m \bmod n \lt n \le m/2$.
- If $n \gt m/2$, then $m \bmod n = m - n \lt m/2$.

Because the remainder is at least halved every two iterations, the maximum number of division steps is roughly $2 \log_2 n$. Euclid's algorithm runs in **$O(\log n)$** time, exhibiting the same logarithmic complexity as [binary search](/courses/algorithm-design-and-analysis/linear-and-binary-search#binary-search-throw-away-half). For two 10-digit numbers, Euclid terminates in a few dozen divisions instead of billions.

<Callout tone="sky" label="Order does not matter">
If the smaller argument is passed first, as in $\gcd(45, 210)$, the first division computes $45 \bmod 210 = 45$. The next state becomes $(210, 45)$. The algorithm automatically swaps the values on the first step at the cost of one modulo operation.
</Callout>

Reversing the division steps computes integer coefficients $x$ and $y$ satisfying Bézout's identity, $mx + ny = \gcd(m, n)$. This is the [extended Euclidean algorithm](/courses/computational-mathematics/modular-inverses#the-extended-euclidean-algorithm), widely used in asymmetric cryptography to compute modular multiplicative inverses.

## Where this shows up today

<ApplicationsGrid>
  <PracticalApplication title="RSA encryption" tool="CRYPTOGRAPHY">
    RSA key generation requires picking coprime integers, and computing the private decryption key relies on the extended Euclidean algorithm. Euclid's algorithm operates on keys with hundreds of decimal digits, which is computationally feasible only because the algorithm runs in logarithmic time.
  </PracticalApplication>
  <PracticalApplication title="Simplifying fractions" tool="MATH LIBRARIES">
    Rational number arithmetic reduces fractions like $\frac{210}{45}$ to $\frac{14}{3}$ by dividing both numerator and denominator by $\gcd(210, 45) = 15$. Exact arithmetic libraries apply this reduction after each operation.
  </PracticalApplication>
  <PracticalApplication title="Screen aspect ratios" tool="UI">
    Display dimensions such as $1920 \times 1080$ reduce to an aspect ratio of $16:9$ by dividing width and height by $\gcd(1920, 1080) = 120$.
  </PracticalApplication>
  <PracticalApplication title="Java standard library" tool="JDK">
    `BigInteger.gcd()` handles arbitrarily large integers, providing an efficient implementation of the Euclidean algorithm for cryptographic workloads.
  </PracticalApplication>
</ApplicationsGrid>

<Callout tone="violet" label="LCM for free">
The least common multiple connects directly to the greatest common divisor through the product formula:

$$
\operatorname{lcm}(m, n) = \frac{m \cdot n}{\gcd(m, n)}
$$

In Java, compute this as `(m / gcd(m, n)) * n`, dividing first so the intermediate multiplication does not overflow integer bounds.
</Callout>
