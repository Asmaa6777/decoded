# Euclid's GCD: A 2,300-Year-Old Algorithm

Around 300 BC, Euclid wrote down a method for finding the greatest common divisor of two numbers. It's one of the oldest algorithms we know of, it's still the one everyone uses, and there's a version of it running inside the encryption that protects your phone's connections right now.

## The problem

The **greatest common divisor** of two non-negative integers $m$ and $n$ (not both zero), written $\gcd(m, n)$, is the largest integer that divides both of them **evenly** — with remainder zero.

Some examples you can check by hand:

- $\gcd(24, 54) = 6$
- $\gcd(18, 42) = 6$
- $\gcd(45, 210) = 15$
- $\gcd(97, 20) = 1$ — numbers like these, with no common divisor except 1, are called *coprime*.

## The obvious way

Try every candidate. Start at the smaller of the two numbers and count down until you find one that divides both:

```java
static int gcdBruteForce(int m, int n) {
    for (int d = Math.min(m, n); d >= 1; d--)
        if (m % d == 0 && n % d == 0) return d;
    return Math.max(m, n);     // one of them is 0
}
```

Correct, but in the worst case — coprime numbers — it tries every value down to 1. That's $O(\min(m, n))$. For two 10-digit numbers, that's billions of divisions.

## Euclid's idea

Euclid noticed one equality, and the whole algorithm falls out of it:

$$
\gcd(m, n) = \gcd(n,\ m \bmod n)
$$

where $m \bmod n$ is the remainder when you divide $m$ by $n$ (`m % n` in Java).

**Why is that true?** Write $m = q \cdot n + r$, where $r$ is the remainder. Any number that divides both $m$ and $n$ also divides $r = m - q \cdot n$. And any number that divides both $n$ and $r$ also divides $m = q \cdot n + r$. So the pairs $(m, n)$ and $(n, r)$ have exactly the same common divisors — which means the same *greatest* one.

But $(n, r)$ is a smaller problem: $r$ is always less than $n$. Keep applying the rule, and the numbers keep shrinking, until the second one becomes **0**. And $\gcd(m, 0) = m$, because every number divides 0. That's the answer.

## Watch it run

The table is exactly how you'd write it on an exam: one row per division, with $m$ and $n$ sliding one column left each time. Try your own numbers. Try two consecutive Fibonacci numbers like $89$ and $55$ — they're famous for being the slowest possible input for Euclid.

As steps:

1. If $n = 0$, return $m$ and stop.
2. Divide $m$ by $n$ and call the remainder $r$.
3. Set $m \leftarrow n$ and $n \leftarrow r$. Go back to step 1.

```java
static int gcd(int m, int n) {
    while (n != 0) {
        int r = m % n;
        m = n;
        n = r;
    }
    return m;
}
```

Or recursively, which reads almost exactly like the equality:

```java
static int gcd(int m, int n) {
    return n == 0 ? m : gcd(n, m % n);
}
```

## Analysis

Here's the surprise. Look at what happens every two steps: the remainder always drops to **less than half** of what it was. (If $n \le m/2$, then $m \bmod n \lt n \le m/2$. If $n \gt m/2$, then $m \bmod n = m - n \lt m/2$.)

Halving every two steps means the number of steps is at most about $2 \log_2 n$. Euclid's algorithm is **$O(\log n)$** — the same growth as binary search. For two 10-digit numbers, that's a few dozen divisions instead of billions.

<Callout tone="sky" label="Order doesn't matter">
What if $m \lt n$, like $\gcd(45, 210)$? The first step computes $45 \bmod 210 = 45$, so the pair becomes $(210, 45)$. Euclid swaps them for you, for the price of one division.
</Callout>

  <PracticalApplication title="RSA encryption" tool="CRYPTOGRAPHY">

  </PracticalApplication>
  <PracticalApplication title="Simplifying fractions" tool="MATH LIBRARIES">
    $\frac{210}{45}$ becomes $\frac{14}{3}$ by dividing both by their gcd, 15. Every exact-fraction library does this after each operation.
  </PracticalApplication>
  <PracticalApplication title="Screen aspect ratios" tool="UI">

  </PracticalApplication>
  <PracticalApplication title="Java's BigInteger" tool="JDK">
    `BigInteger.gcd()` exists for numbers too big for a `long` — and it's built on the same idea.
  </PracticalApplication>
</ApplicationsGrid>

<Callout tone="violet" label="LCM for free">
The least common multiple comes straight from the gcd: $\operatorname{lcm}(m, n) = \dfrac{m \cdot n}{\gcd(m, n)}$. In Java, write it as `m / gcd(m, n) * n` — divide first, so the multiplication doesn't overflow.
</Callout>
