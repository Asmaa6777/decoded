# Greedy Algorithms: Prim and Kruskal

So far you've learned specific algorithms. This module covers *strategies for inventing them*, starting with the one most people use without thinking: **always grab the best option available right now.**

## The greedy approach

A greedy algorithm builds a solution **one step at a time**. At each step it extends the partial solution it has so far, and the choice it makes must be:

1. **Feasible:** it doesn't break the problem's rules.
2. **Locally optimal:** it's the best choice available *at this step*.
3. **Irrevocable:** once made, it's never undone.

The third rule keeps greedy algorithms fast and simple, since they never go back or try alternatives. It's also why they can get the wrong answer. Greedy algorithms pick the **local optimum** (the best choice at this step) in the hope that it leads to the **global optimum** (the best answer overall).

## When greedy fails

Make change for 6 using as few coins as possible. Coins come in values 1, 3 and 4.

The greedy cashier always picks the biggest coin that fits: **4**, leaving 2. Then **1**, then **1**, for three coins: 4 + 1 + 1.

But **3 + 3** is only two coins. Grabbing the 4 looked best at that moment and turned out to be a mistake, and greedy never takes a choice back.

Try other amounts with 1, 3 and 4 (10 and 14 fail too), then switch to US money, where greedy never loses.

(With real coin systems such as 1, 5, 10, 25, greedy always gives the optimal answer, because those values were designed that way.)

The notes list the advantages: greedy algorithms are easy to describe, and they can be faster than other approaches, though not always. They're also easy to code. Their drawback, which the notes call the major one, is that they **don't always produce the optimal solution**. For each problem you have to *prove* that the local choices lead to the global best, or accept a good-enough answer.

The rest of this lesson is about a problem where greedy provably finds the best answer.

## Minimum spanning trees

You're laying cable to connect six buildings. Some pairs of buildings can be connected, each at a known cost. Every building must be connected, directly or indirectly, and you want to spend as little as possible.

In graph terms, this is a connected, weighted, undirected graph. A **spanning tree** is a subset of edges that connects **every** vertex with **no cycles** (a cycle would mean paying for a cable you don't need). With $n$ vertices, every spanning tree has exactly $n - 1$ edges. The **minimum spanning tree (MST)** is the spanning tree with the smallest total weight.

There are two classic greedy algorithms for it. Both always find the true minimum.

Both run on the notes' example: six vertices, a to f, and ten weighted edges, ab = 3, bc = 1, bf = 4, cf = 4, af = 5, df = 5, ae = 6, cd = 6, ef = 2 and de = 8.

## Prim's algorithm: grow one tree

1. Start the tree with any single vertex. (The notes say "chosen at random": any vertex works.)
2. Look at every edge that connects a vertex **in** the tree to a vertex **not yet** in it.
3. Add the **cheapest** of those edges (and its new vertex) to the tree.
4. Repeat until every vertex is in.

The dotted neon edges are the candidates at each step: the edges that cross from the tree to the outside. Prim always takes the cheapest crossing edge, so the tree grows outward from its starting vertex.

The notes trace it as a table. Each vertex outside the tree carries a label (nearest tree vertex, weight of that edge), and $(-, \infty)$ means no edge reaches the tree yet. Each row adds the vertex with the smallest weight:

| Tree vertex added | Remaining vertices |
| --- | --- |
| a(−, −) | **b(a, 3)**, c(−, ∞), d(−, ∞), e(a, 6), f(a, 5) |
| b(a, 3) | **c(b, 1)**, d(−, ∞), e(a, 6), f(b, 4) |
| c(b, 1) | d(c, 6), e(a, 6), **f(b, 4)** |
| f(b, 4) | d(f, 5), **e(f, 2)** |
| e(f, 2) | **d(f, 5)** |
| d(f, 5) | |

When b joins, f's label improves from (a, 5) to (b, 4), because b is closer. When f joins, e improves from (a, 6) to (f, 2) and d from (c, 6) to (f, 5). The tree is ab, bc, bf, fe and fd, with total weight $3 + 1 + 4 + 2 + 5 = 15$.

The notes' pseudocode, where $V_T$ is the set of tree vertices and $E_T$ the set of tree edges:

```text
ALGORITHM Prim(G)
V_T ← {v0}          // any vertex can start the tree
E_T ← ∅
for i ← 1 to |V| − 1 do
    find a minimum-weight edge e* = (v*, u*) among all edges (v, u)
        such that v is in V_T and u is in V − V_T
    V_T ← V_T ∪ {u*}
    E_T ← E_T ∪ {e*}
return E_T
```

The loop runs $|V| - 1$ times, once per tree edge.

## Kruskal's algorithm: join the forest

Kruskal works differently. Instead of growing one tree, it starts with every vertex as its own tiny tree (a forest) and joins them up.

1. **Sort** all edges from lowest weight to highest.
2. Take the cheapest remaining edge. If it connects two **different** trees, add it. If both ends are **already in the same tree**, adding it would create a cycle, so **reject** it.
3. Repeat until you have $n - 1$ edges.

<MstVisualizer algorithm="kruskal" nodes={[{ id: 0, x: 50, y: 120, label: "a" }, { id: 1, x: 170, y: 40, label: "b" }, { id: 2, x: 330, y: 40, label: "c" }, { id: 3, x: 450, y: 120, label: "d" }, { id: 4, x: 250, y: 200, label: "e" }, { id: 5, x: 250, y: 120, label: "f" }]} edges={[{ from: 0, to: 1, weight: 3 }, { from: 1, to: 2, weight: 1 }, { from: 1, to: 5, weight: 4 }, { from: 2, to: 5, weight: 4 }, { from: 0, to: 5, weight: 5 }, { from: 5, to: 3, weight: 5 }, { from: 0, to: 4, weight: 6 }, { from: 2, to: 3, weight: 6 }, { from: 5, to: 4, weight: 2 }, { from: 4, to: 3, weight: 8 }]} />

The orange dashed edges were cheap, but their two ends were already connected, so they would only have closed a loop. Kruskal skips them.

On the notes' graph, the sorted list is bc 1, ef 2, ab 3, bf 4, cf 4, af 5, df 5, ae 6, cd 6, de 8:

| Edge | Weight | Result |
| --- | --- | --- |
| bc | 1 | accept |
| ef | 2 | accept |
| ab | 3 | accept |
| bf | 4 | accept: joins the a, b, c piece to the e, f piece |
| cf | 4 | reject: c and f are already connected |
| af | 5 | reject: a and f are already connected |
| df | 5 | accept: the 5th edge, so the tree is done |

Kruskal stops as soon as it has $|V| - 1 = 5$ edges and never looks at ae, cd or de. It finds the same tree as Prim here, total **15**. When there are ties the two can pick different edges, but the minimum total weight is always the same.

The notes' pseudocode keeps a count of tree edges, `ecounter`, and an index `k` into the sorted edge list:

```text
ALGORITHM Kruskal(G)
sort E so that w(e_i1) ≤ … ≤ w(e_i|E|)
E_T ← ∅; ecounter ← 0
k ← 0
while ecounter < |V| − 1 do
    k ← k + 1
    if E_T ∪ {e_ik} is acyclic
        E_T ← E_T ∪ {e_ik}; ecounter ← ecounter + 1
return E_T
```

"Is acyclic" is the cycle check: adding the edge must not close a loop.

Total weight $2 + 2 + 3 + 3 + 4 = 14$. Every tie gives a different tree, but each one weighs 14. On an exam, say how you broke ties (here, alphabetically).

**Kruskal.** Edges: AB = 1, DE = 2, BC = 3, CD = 4, AE = 5, AC = 7, AD = 10. Sorted, accept AB 1, DE 2, BC 3 and CD 4. That's $5 - 1 = 4$ edges, so the tree is done: A–B–C–D–E with total weight $1 + 2 + 3 + 4 = 10$. The heavier edges AE, AC and AD would each close a cycle.

## Why does greedy work here?

The reason is the **cut property**. Split the vertices into any two groups. The cheapest edge crossing between the groups is always safe to include in some minimum spanning tree. Prim applies this to "tree vs. everything else." Kruskal applies it to "this edge's tree vs. everything else." So every greedy choice is one that some optimal solution also makes, and that's what greedy needs to be correct.

## Analysis

- **Prim**, simple version (matrix, scan for the cheapest crossing edge each time): $O(V^2)$. With a [priority queue](/courses/data-structures/heaps#the-interface): $O(E \log V)$.
- **Kruskal**: sorting the edges dominates, $O(E \log E)$. The "same tree?" check uses a **union–find** structure, which is nearly $O(1)$ per check with the standard optimizations.

Rule of thumb: Prim for dense graphs (lots of edges), Kruskal for sparse ones.

Advanced Algorithms proves these results, in [greedy algorithms](/courses/advanced-algorithms/greedy-algorithms#optimization-problems) and [minimum spanning trees](/courses/advanced-algorithms/minimum-spanning-trees#optimal-substructure).

## The Java

The visualizer shows the simple matrix version of Prim. Here's Kruskal in full, with a minimal union–find:

```java
import java.util.Arrays;

public class Kruskal {

    static int find(int[] parent, int x) {
        while (parent[x] != x) x = parent[x];
        return x;
    }

    static int kruskal(int n, int[][] edges) {        // each edge: {u, v, weight}
        Arrays.sort(edges, (a, b) -> a[2] - b[2]);    // greedy order: cheapest first
        int[] parent = new int[n];
        for (int i = 0; i < n; i++) parent[i] = i;

        int total = 0, used = 0;
        for (int[] e : edges) {
            int ru = find(parent, e[0]), rv = find(parent, e[1]);
            if (ru == rv) continue;                   // same tree: would make a cycle
            parent[ru] = rv;                          // join the two trees
            total += e[2];
            if (++used == n - 1) break;               // tree complete
        }
        return total;
    }

    public static void main(String[] args) {
        // the notes' graph, with a = 0, b = 1, c = 2, d = 3, e = 4, f = 5
        int[][] edges = {
            {0,1,3}, {1,2,1}, {1,5,4}, {2,5,4}, {0,5,5},
            {5,3,5}, {0,4,6}, {2,3,6}, {5,4,2}, {4,3,8}
        };
        System.out.println(kruskal(6, edges));        // 15
    }
}
```
