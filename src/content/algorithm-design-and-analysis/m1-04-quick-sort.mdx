# Quick Sort: Pick a Pivot

[Merge sort](/courses/algorithm-design-and-analysis/merge-sort#merge-sort-in-one-paragraph) executes its simplest phase first (splitting arrays down the middle) and its complex phase last (merging sorted subarrays). Quick sort reverses that order. It performs the sorting work **up front** during partitioning, leaving no combination work at the end.

## The idea

**Quick sort** is a divide-and-conquer sorting algorithm that organizes elements around a chosen value called the **pivot**:

1. Select a **pivot** element from the array.
2. **Partition** the array: rearrange elements so that all values smaller than the pivot move to its left, and all values greater move to its right. The pivot is now in its **final position** and will never move again.
3. Recursively apply quick sort to the left subarray and the right subarray.

There is no combine step. Once both partitions are sorted, the entire array is in order because all elements on the left are smaller than the pivot and all elements on the right are larger. All sorting logic occurs during partitioning.

This structure follows [divide and conquer](/courses/algorithm-design-and-analysis/merge-sort#divide-and-conquer): divide corresponds to partitioning, conquer corresponds to recursion, and the combine step requires no additional work.

## Partitioning with two pointers

There are multiple ways to partition an array. The lab uses the **first element as the pivot** and converges two pointers from opposite ends:

- `right` begins at the end and moves leftward while pointing to an element greater than or equal to the pivot.
- `left` begins at the start and moves rightward while pointing to an element less than or equal to the pivot. Its initial step advances past the pivot itself.
- When both pointers stop, `right` marks a value smaller than the pivot and `left` marks a value larger than the pivot. **Swapping them** places both elements into their proper partitions, and the traversal continues.
- When the pointers meet, swapping the pivot with the element at the meeting point places the pivot into its final location.

### Why `right` has to move first

When the two pointers meet, the algorithm swaps the pivot with the value at that meeting point. Because that value moves to index 0 (the left partition), it must be **no larger than the pivot**. Advancing the `right` pointer first guarantees this condition: `right` only halts on values smaller than the pivot, or meets `left` at an already validated location.

If `left` moves first, it can halt on a value larger than the pivot when `right` cannot advance. Swapping the pivot into that position would place a larger value at index 0, corrupting the partition. For example, on the array `[25, 10, 30]`, advancing `left` first passes 25 and 10 to halt at 30, where it meets `right`. Swapping produces `[30, 10, 25]`, placing 30 to the left of 25. (When choosing the **last** element as the pivot, the order reverses: `left` must advance first.)

### The notes' version: loc, left and right

The course notes illustrate a variation using pointers `loc`, `left`, and `right` on the sequence 25, 10, 30, 15, 20, 28. In this scheme, the pivot does not remain stationary at index 0. It **moves with each swap**, and `loc` continuously tracks its position. Whichever pointer is not pointing at the pivot performs the traversal:

- When `loc = left`, advance `right` leftward while `a[loc] < a[right]`. When `a[loc] > a[right]`, swap them, updating `loc` to `right`.
- When `loc = right`, advance `left` rightward while `a[left] < a[loc]`. When `a[left] > a[loc]`, swap them, updating `loc` to `left`.
- Terminate when `loc`, `left`, and `right` all point to the same index.

| Step | What happens | Array | loc, left, right |
| --- | --- | --- | --- |
| start | pivot 25 is at the front | **25** 10 30 15 20 28 | 0, 0, 5 |
| 1 | 25 < 28, move `right` | **25** 10 30 15 20 28 | 0, 0, 4 |
| 2 | 25 > 20, swap; pivot goes right | 20 10 30 15 **25** 28 | 4, 0, 4 |
| 3 | 20 < 25, move `left` | 20 10 30 15 **25** 28 | 4, 1, 4 |
| 4 | 10 < 25, move `left` | 20 10 30 15 **25** 28 | 4, 2, 4 |
| 5 | 30 > 25, swap; pivot goes left | 20 10 **25** 15 30 28 | 2, 2, 4 |
| 6 | 25 < 30, move `right` | 20 10 **25** 15 30 28 | 2, 2, 3 |
| 7 | 25 > 15, swap; pivot goes right | 20 10 15 **25** 30 28 | 3, 2, 3 |
| 8 | 15 < 25, move `left` | 20 10 15 **25** 30 28 | 3, 3, 3 |

All three pointers meet at index 3, establishing 25 in its final position with smaller values to its left and larger values to its right. The visualizer method also places 25 at index 3, leaving the left partition ordered as 15, 10, 20. Both outcomes are correct: partitioning guarantees only which **partition** each element enters, not its internal order.

The notes also provide the classic pseudocode for this partition, named **Hoare partition** after Tony Hoare, who invented quick sort. It expresses this two-pointer scan using `repeat … until` loops. Here is the high-level recursion where `s` denotes the **split position** (the pivot's final index):

```text
ALGORITHM Quicksort(A[l..r])
if l < r
    s ← Partition(A[l..r])     // s is a split position
    Quicksort(A[l..s − 1])
    Quicksort(A[s + 1..r])
```

## Analysis: it depends on the pivot

Partitioning a subarray of size $n$ requires $O(n)$ time because the two pointers traverse the subarray once. Overall performance depends on how evenly the pivot splits the array into subarrays.

- **Balanced partitions (average case):** when the pivot divides subarrays roughly in half, the recursion tree reaches a depth of approximately $\log_2 n$ levels. Each level performs $O(n)$ partitioning work, yielding **$O(n \log n)$** total time. Even uneven splits, such as a 25/75 ratio, still reduce subproblem sizes exponentially, preserving $O(n \log n)$ asymptotic growth. On randomly ordered inputs, quick sort achieves $O(n \log n)$ on average. Advanced Algorithms provides a rigorous mathematical proof in [randomized quicksort](/courses/advanced-algorithms/quicksort#randomized-quicksort).

- **Unbalanced partitions (worst case):** if the pivot is consistently the smallest or largest element, one partition remains empty while the other contains $n - 1$ elements. Partitioning shrinks the problem by only one element at a cost of $O(n)$ operations:

$$
n + (n-1) + (n-2) + \dots + 1 = O(n^2)
$$

When using the first element as the pivot, this worst case occurs on inputs that are **already sorted in ascending or descending order**. Every chosen pivot is either the minimum or maximum remaining element, producing $n$ recursive levels. Test this in the visualizer with `1, 2, 3, 4, 5, 6, 7, 8` to observe each partition strip away only a single element.

The notes represent the worst case as $f(n) = n \times (n-1)$, and the best case as $f(n) = n \times \log_2 n$. Both formulations correspond asymptotically to $O(n^2)$ and $O(n \log n)$.

<Callout tone="orange" label="Common mistake: thinking one partition sorts the sides">
A partition step separates elements into lower and higher groups, but does not sort those groups internally. For instance, partitioning `25, 10, 30, 15, 20, 28` around 25 yields `15, 10, 20, 25, 30, 28`. The subarray `15, 10, 20` remains unsorted; only 25 has reached its final sorted index. Quick sort must recursively sort both partitions.
</Callout>

Consequently, input that represents the best case for [insertion sort](/courses/algorithm-design-and-analysis/insertion-sort#the-idea) represents the worst case for naive quick sort.

### Picking a better pivot

Selecting pivots deliberately mitigates unbalanced partitioning. Standard strategies include:

- **First** or **last** element: straightforward to implement, but quadratic on pre-sorted arrays.
- **Middle** element: handles pre-sorted data efficiently.
- **Random** element: makes worst-case inputs virtually impossible regardless of input ordering.
- **Median of three**: uses the median of the first, middle, and last elements to avoid extreme values.

<Callout tone="violet" label="Quick sort vs merge sort">
Merge sort guarantees $O(n \log n)$ worst-case time and provides [stability](/courses/algorithm-design-and-analysis/selection-and-bubble-sort#stability), but requires $O(n)$ auxiliary memory. Quick sort requires $O(n \log n)$ average time and $O(n^2)$ worst-case time, and is unstable. However, quick sort operates **in place** and typically executes faster in practice because it minimizes data movement and exhibits strong CPU cache locality. The **CPU cache** is high-speed memory within the processor, and sequential array access keeps data readily available without repeated fetches from main memory.
</Callout>

## Strengths and weaknesses

Quick sort is frequently the fastest general-purpose sorting algorithm in practical applications. It operates in place without allocating a second array, though it consumes $O(\log n)$ auxiliary space on average on the [call stack](/courses/algorithm-design-and-analysis/counting-steps#space-is-a-cost-too). It also parallelizes readily because partitions can be sorted independently.

Its primary limitations are its quadratic worst-case time on poorly chosen pivots and its lack of stability due to long-range swaps.

## The lab version

```java
public static void quickSort(int[] array, int lowIndex, int highIndex) {
    if (lowIndex >= highIndex) return;

    int pivot = array[lowIndex];
    int pivotIndex = partition(array, lowIndex, highIndex, pivot);
    quickSort(array, lowIndex, pivotIndex - 1);
    quickSort(array, pivotIndex + 1, highIndex);
}

public static int partition(int[] array, int lowIndex, int highIndex, int pivot) {
    int leftPointer = lowIndex;
    int rightPointer = highIndex;

    while (leftPointer < rightPointer) {
        while (array[rightPointer] >= pivot && leftPointer < rightPointer)
            rightPointer--;
        while (array[leftPointer] <= pivot && leftPointer < rightPointer)
            leftPointer++;
        swap(array, leftPointer, rightPointer);
    }
    swap(array, lowIndex, rightPointer);
    return rightPointer;  // pivot's final index
}
```

Invoke the method using `quickSort(array, 0, array.length - 1)`. To observe worst-case behavior, benchmark execution on 50,000 random integers and then on 50,000 pre-sorted integers. When run on sorted inputs, a first-element pivot triggers $n$ levels of nested recursion instead of $\log_2 n$, which may cause a `StackOverflowError`.
