# Quick Sort: Pick a Pivot

Merge sort does the easy part first (split blindly down the middle) and the hard part last (merge carefully). Quick sort reverses that order. It does the careful work **up front**, so afterwards there's nothing left to combine.

## The idea

1. Pick one element, the **pivot**.
2. **Partition** the array: move everything smaller than the pivot to its left and everything bigger to its right. The pivot is now in its **final position** and will never move again.
3. Quick sort the left part, then quick sort the right part.

There's no combine step. Once both sides are sorted the whole array is sorted, because everything on the left is smaller than the pivot and everything on the right is bigger. All the work happens in partitioning.

It's still divide and conquer: divide is "partition," conquer is "recurse," and combine is empty.

## Partitioning with two pointers

There are several ways to partition. This one uses the **last element as the pivot** and two pointers walking towards each other:

- `left` starts at the beginning and moves right **while** its element is ≤ the pivot (that element is already on the correct side).
- `right` starts at the end and moves left **while** its element is ≥ the pivot.
- When both have stopped, `left` is on something too big for the left side and `right` is on something too small for the right side. **Swap them**, which puts both on the correct side, and keep going.
- When the pointers meet, swap the pivot into the meeting point.

## Analysis: it depends on the pivot

Partitioning a piece of size $n$ takes $O(n)$: each pointer step does one comparison, and together the pointers cross the piece once. The running time depends on *how evenly* the pivot splits the array.

**Good case: the pivot lands near the middle.** Each partition cuts the problem roughly in half. As with merge sort, that gives about $\log_2 n$ levels of $O(n)$ work each, so **$O(n \log n)$**. This is what usually happens on random data, so the **average case is $O(n \log n)$**.

**Bad case: the pivot is always the smallest or biggest element.** Then one side is empty and the other has $n - 1$ elements, so $O(n)$ work has made the problem only one element smaller. Do that $n$ times:

$$
n + (n-1) + (n-2) + \dots + 1 = O(n^2)
$$

With a last-element pivot, this happens on data that's **already sorted** (or reverse sorted), because every pivot is the largest remaining element. Try `1, 2, 3, 4, 5, 6, 7, 8` in the visualizer and watch every partition peel off just one element.

So the input that's best for insertion sort is the worst for naive quick sort.

### Picking a better pivot

The fix is to choose the pivot more carefully. Common choices:

- **First** or **last** element: simple, but bad on sorted input.
- **Middle** element: handles sorted input well.
- **Random** element: makes the worst case extremely unlikely on *any* input.
- **Median of three**: the median of the first, middle and last elements. A cheap way to avoid bad pivots.

<Callout tone="violet" label="Quick sort vs merge sort">
Merge sort is always $O(n \log n)$ and stable, but needs $O(n)$ extra memory. Quick sort is $O(n \log n)$ on average and $O(n^2)$ in the worst case, and it isn't stable. It sorts **in place**, though, and is usually faster in practice because it moves less data around and uses the CPU cache well.
</Callout>

## Strengths and weaknesses

Quick sort is often the fastest general-purpose sort in practice. It sorts in place, using only $O(\log n)$ extra space on average for the recursion stack. It's also easy to parallelize, since after partitioning the two sides are completely independent.

Against that, its worst case is $O(n^2)$, and it isn't stable: the long-distance swaps can reorder equal elements.

## The lab version

```java
public static void quickSort(int[] array, int lowIndex, int highIndex) {
    if (lowIndex >= highIndex) return;

    int pivotIndex = partition(array, lowIndex, highIndex);
    quickSort(array, lowIndex, pivotIndex - 1);
    quickSort(array, pivotIndex + 1, highIndex);
}

private static int partition(int[] array, int lowIndex, int highIndex) {
    int pivot = array[highIndex];
    int leftPointer = lowIndex;
    int rightPointer = highIndex;

    while (leftPointer < rightPointer) {
        while (array[leftPointer] <= pivot && leftPointer < rightPointer)
            leftPointer++;
        while (array[rightPointer] >= pivot && leftPointer < rightPointer)
            rightPointer--;
        swap(array, leftPointer, rightPointer);
    }
    swap(array, leftPointer, highIndex);
    return leftPointer;
}
```

Call it as `quickSort(array, 0, array.length - 1)`. Then run the experiment that shows the worst case: time it on 50,000 random numbers, then on 50,000 numbers that are already sorted. If the sorted run crashes with a `StackOverflowError`, you've hit the worst case: $n$ levels of recursion instead of $\log n$.
