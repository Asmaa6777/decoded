# Counting Steps: Big-O, Omega and Theta

Two programs can produce the exact same answer, yet one finishes in milliseconds while the other runs for hours. Neither program has a bug. The difference lies in the *algorithm*, and **analysis** allows you to identify that difference before running any code.

The goal of analysis is to **compare algorithms**, primarily by running time, but also by memory usage and implementation complexity. *Running time analysis* answers one specific question: how does execution time grow as the input size increases?

## Why not just time it?

You could time both programs with a stopwatch, as you will in the next lesson. However, a wall-clock timer reflects hardware specifications, JVM warm-up, background operating system processes, and the specific test input. On a faster computer the measured times decrease even though the underlying *algorithm* has not changed.

So instead of seconds, we count **steps**:

- **Input size, $n$.** How big is the problem? It depends on the problem:
  - for an array, the number of elements;
  - for a polynomial, its degree;
  - for a matrix, the number of elements in it;
  - for a graph, the number of vertices and edges;
  - for a single number, such as when testing whether it is prime, the number of bits in its binary representation. The cost depends on the number of bits needed to store the value, not the value alone: 1,000,000 takes 20 bits in binary, while a 40-bit number is over a trillion.
- **The basic operation** (also called the **key operation**). The operation that contributes most to the running time: the step that does the real work and runs most often. In a sorting algorithm it's usually a comparison (`a[j] < a[min]`); otherwise it's often an assignment inside the innermost loop.
- **Count how many times the basic operation runs, as a function of $n$.**

That function is the algorithm's **time complexity**. This course writes it as $T(n)$. Many course notes write $f(n)$ and call it the **complexity of the algorithm**, measuring the running time or memory required for an input of size $n$. Because it does not depend on specific hardware or programming languages, it characterizes the algorithm itself.

## Space is a cost too

**Space complexity** is how much memory the algorithm needs, also as a function of $n$. It has two parts:

- A **fixed part** independent of input size: program instructions and simple variables like `i`, `max`, and `temp`.
- A **variable part** that scales with input size: memory dynamically allocated for additional data structures, along with the **recursion stack**. Every recursive call awaiting completion occupies stack memory.

Written as a formula, the space needed by an algorithm $X$ is

$$
S(X) = C + S(I)
$$

where $C$ is the fixed part and $S(I)$ is the variable part, which depends on $I$, the *instance characteristics* (the size and attributes of this particular input). For `findMax` from the previous lesson, $S(I)$ is zero: it only uses `max` and `i`, regardless of array length. A recursive version making one recursive call per element maintains $n$ stack frames simultaneously, so its $S(I)$ grows proportionally to $n$.

Although this course focuses primarily on execution time, memory usage remains an important constraint. For example, [merge sort](/courses/algorithm-design-and-analysis/merge-sort#merge-sort-in-one-paragraph) achieves fast running time by allocating auxiliary memory.

## Best, worst and average case

Take linear search, which walks through an array looking for a value `x`.

```java
static int linearSearch(int[] a, int x) {
    for (int i = 0; i < a.length; i++) {
        if (a[i] == x) return i;
    }
    return -1;
}
```

How many comparisons does it make? Even for a fixed size $n$, *it depends on the input*:

- **Best case:** `x` is the very first element. **1** comparison.
- **Worst case:** `x` is last, or not there at all. **$n$** comparisons.
- **Average case:** the expected number of comparisons, averaged over all possible inputs of size $n$. It needs a calculation, worked out below.

The worst case provides an **upper bound** on running time, while the best case provides a **lower bound**. Identifying either requires determining which input triggers the maximum or minimum number of operations. For linear search, the best case requires a constant number of comparisons regardless of $n$, written $\Omega(1)$, while the worst case requires $n$ comparisons, written $O(n)$.

### Working out the average case

Assume every case is equally likely: `x` is at position 1, or position 2, …, or position $n$, or not in the array at all. That's $n + 1$ cases. Count the comparisons in each, add them up, and divide by $n + 1$:

- Finding `x` at index $i$ requires $i$ comparisons. Searching all positions 1 through $n$ totals $1 + 2 + \cdots + n = \frac{n(n+1)}{2}$ comparisons. To verify the formula, pair the first term with the last ($1 + n$), the second with the second-to-last ($2 + n - 1$), and so on. Each of the $n/2$ pairs sums to $n + 1$.
- `x` missing takes $n$ comparisons.

Add them and divide by the $n + 1$ cases. Split the fraction into its two parts, and the first part's $(n + 1)$ cancels:

$$
\text{average} = \frac{\frac{n(n+1)}{2} + n}{n + 1} = \frac{\frac{n(n+1)}{2}}{n+1} + \frac{n}{n+1} = \frac{n}{2} + \frac{n}{n+1}
$$

The second term remains less than 1 for all $n \ge 1$, so the average stays slightly below $\frac{n}{2} + 1$. For the 9-element array shown above, the calculation gives $\frac{45 + 9}{10} = 5.4$ comparisons. Because this value grows proportionally with $n$, the average case has linear complexity.

A common mistake is dividing by $n$ and forgetting the case where the target value is not in the array. The average must account for all possible outcomes, including the "not found" case as the $(n+1)$-th possibility.

Engineers usually report the **worst case** because it guarantees that the algorithm will never take longer than this upper bound. The best case is helpful context but rare in practice. The average case is often realistic, but it requires assumptions about the input distribution, such as assuming every position is equally likely.

## Growth is what matters

Suppose one algorithm does $T(n) = 3n + 10$ steps and another does $T(n) = n^2$. For $n = 5$, both do 25. For $n = 1000$, it's 3,010 against 1,000,000.

When $n$ is small, everything is fast and the details don't matter. When $n$ is large, **only the fastest-growing term matters**, and constants and smaller terms become noise. Drag the slider to see it:

## The three notations

> **Asymptotic notations** are mathematical tools for describing how efficient an algorithm is, in time or in space, as the input size grows. The three most common are **Big-O**, **Omega** and **Theta** notation.

"Asymptotic" means "as $n$ gets very large". These notations ignore what happens for small inputs and describe the trend. Exams ask for all three.

**Big-O is an upper bound.** $T(n) = O(g(n))$ means that, for large enough $n$, $T(n)$ is at most some constant times $g(n)$:

$$
T(n) \le c \cdot g(n) \quad \text{for all } n \ge n_0
$$

Read it as *"it grows no faster than $g$."* People use Big-O for the **worst case**.

The definition uses two constants. The multiplier $c$ absorbs constant factors, while $n_0$ establishes the threshold where asymptotic behavior begins. To prove $3n + 10 = O(n)$, choose constants $c$ and $n_0$ satisfying the inequality. Setting $c = 4$ gives $3n + 10 \le 4n$. Subtracting $3n$ from both sides yields $10 \le n$. The condition holds for all $n \ge 10$, so $c = 4$ and $n_0 = 10$ confirm that $3n + 10 = O(n)$. At $n = 5$ the inequality fails ($25 \gt 20$), which is allowed because the definition only requires the bound to hold for $n \ge n_0$.

The same approach fails for $n^2 = O(n)$: the condition requires $n^2 \le c \cdot n$, which simplifies to $n \le c$. That inequality fails for any input larger than the chosen constant $c$. Because no fixed constant $c$ bounds $n$ for all values, $n^2$ is **not** $O(n)$.

Big-O is the most widely used notation. It allows you to **compare algorithms** across different machines and classify them into standard growth rates.

**Omega (Ω) is a lower bound.** $T(n) = \Omega(g(n))$ means $T(n)$ is at least $c \cdot g(n)$ for large $n$: *"it grows at least as fast as $g$."* It's often used for the **best case**.

**Theta (Θ) is a tight bound.** $T(n) = \Theta(g(n))$ means both at once: $T(n)$ sits between two constant multiples of $g(n)$.

$$
c_1 \cdot g(n) \le T(n) \le c_2 \cdot g(n) \quad \text{for all } n \ge n_0
$$

*"It grows at the same rate as $g$."* For example, $3n + 10 = \Theta(n)$: the value is at least $3n$ for all $n \ge 1$ (setting $c_1 = 3$) and at most $4n$ for all $n \ge 10$ (setting $c_2 = 4$ and $n_0 = 10$).

<Callout tone="violet" label="The everyday version">
In practice, people say "Big-O" for everything and mean "how it grows in the worst case." That's fine in conversation. On an exam, be precise: O is ≤, Ω is ≥, Θ is both.
</Callout>

<Callout tone="orange" label="Notations are not cases">
Many notes define the three by pairing each with a case: Big-O "provides the worst case", Omega "provides the best case", and Theta "is used for the average case". If an exam asks for those definitions, that is the expected answer. But the pairing is a habit, not the meaning. Each notation is a bound on a function, and you can bound any case with any of them. Linear search's worst case is $n$ comparisons, which is $O(n)$, $\Omega(n)$ and $\Theta(n)$ all at once. Its best case is $\Theta(1)$. Theta just says the bound is tight from both sides; it has nothing to do with averages.
</Callout>

## Getting the Big-O without the algebra

You rarely need the formal definition to find the answer. Three rules cover almost everything:

1. **Drop the constants.** $5n$ and $n/2$ are both $O(n)$.
2. **Keep only the biggest term.** $n^2 + 100n + 7$ is $O(n^2)$.
3. **Loops multiply, sequences add.** A loop of $n$ inside a loop of $n$ is $n \times n = O(n^2)$. One loop of $n$ followed by another loop of $n$ is $n + n = O(n)$.

To see the rules at work, write the cost of each line next to it. Statements that run once cost a constant, written $c_0, c_1, \ldots$; a constant is $O(1)$, so $O(c) = O(1)$. A loop header runs about $n$ times.

```java
int sum = 0;                  // c0     runs once
for (int i = 0; i < n; i++)   // n      loop runs n times
    sum += i;                 // c1     runs n times
```

$T(n) = c_0 + c_1 n$. Drop the constant and the smaller term: **$O(n)$**.

```java
int count = 0;                    // c0
for (int i = 0; i < n; i++)       // n
    for (int j = 0; j < n; j++)   // n, for each i
        count++;                  // c1, runs n × n times
```

$T(n) = c_0 + c_1 n^2$, so **$O(n^2)$**.

Two complexity rates deserve specific explanation:

**Logarithmic.** $\log_2 n$ counts how many times you can halve $n$ before reaching 1. For example, $\log_2 8 = 3$ because $8 \to 4 \to 2 \to 1$ takes three halvings. Similarly, $\log_2 1024 = 10$, and $\log_2(1{,}000{,}000) \approx 20$. Logarithmic functions grow very slowly, explaining why divide-and-conquer algorithms like binary search run quickly. In asymptotic notation the base is omitted because changing logarithmic bases only multiplies by a constant factor, written simply as $\log n$.

**Exponential and factorial.** An exponential term $2^n$ doubles with each unit increase in $n$, representing counts such as the number of possible subsets for $n$ items. A factorial $n! = n \times (n-1) \times \cdots \times 1$ represents the number of orderings for $n$ items. Both grow extremely rapidly: $2^{30}$ exceeds one billion, while $20!$ exceeds $2 \times 10^{18}$.

The common classes, from fastest to slowest:

| Class | Name | Typical example |
| --- | --- | --- |
| $O(1)$ | constant | read `a[i]`, swap two elements |
| $O(\log n)$ | logarithmic | binary search |
| $O(n)$ | linear | linear search, find the max |
| $O(n \log n)$ | linearithmic | merge sort, quick sort (average) |
| $O(n^2)$ | quadratic | selection sort, bubble sort |
| $O(n^3)$ | cubic | three nested loops, such as multiplying two $n \times n$ matrices the schoolbook way |
| $O(2^n)$ | exponential | trying every subset (brute-force knapsack) |
| $O(n!)$ | factorial | trying every order (brute-force Traveling Salesman) |

"Linear" means running time scales **in direct proportion** to input size. Doubling the input doubles the execution time.

<Callout tone="orange" label="Common mistake: leaving extra terms in">
Answers like $O(3n)$, $O(n^2 + n)$ or $O(\frac{n}{2})$ aren't wrong as bounds, but they aren't simplified, and exams expect the simplest form: $O(n)$, $O(n^2)$, $O(n)$. The point of Big-O is to name the class from the table, so apply the two rules above until only one term is left, with no constant in front.
</Callout>

## A worked example

Exams frequently present algorithms as numbered steps. Consider this example: what does it output, what is its Big-O, and which complexity class does it belong to?

```text
Step 1: Declare N and F as integers.
Step 2: Set F = 1. Read N.
Step 3: If N > 0 is false, F stays 1.
Step 4: If N > 0, repeat: F = F * N, then N = N - 1, until N = 0.
Step 5: Print F.
```

Trace it with $N = 4$: F becomes $1 \cdot 4 = 4$, then $4 \cdot 3 = 12$, then $12 \cdot 2 = 24$, then $24 \cdot 1 = 24$. It prints **24**, which is $4!$, so the algorithm computes the **factorial**.

If $N$ is 0 (or negative), the loop never runs and it prints **1**, which matches $0! = 1$.

The loop body runs once for each value of N from N down to 1. That's $N$ multiplications, so it's **$O(n)$**, and its type is **linear time complexity**.

In Java:

```java
static long factorial(int n) {
    long f = 1;
    while (n > 0) {
        f = f * n;   // basic operation: runs n times
        n--;
    }
    return f;
}
```

## A loop that depends on the outer loop

A common exam problem asks for the Big-O of dependent nested loops:

```java
int x = 1;
for (int i = 1; i <= n; i++) {
    sum = 1;
    for (int j = 1; j <= i; j++) {
        x = i + j;     // basic operation
        y = x + 3;
    }
}
```

The inner loop does not run $n$ times during every pass. It runs $i$ times, and $i$ changes. Make a table for $n = 4$:

| $i$ | inner loop runs |
| --- | --- |
| 1 | 1 |
| 2 | 2 |
| 3 | 3 |
| 4 | 4 |
| **total** | **10** |

In general the total is

$$
1 + 2 + 3 + \cdots + n = \frac{n(n+1)}{2} = \frac{n^2}{2} + \frac{n}{2}
$$

For $n = 4$, the formula yields $\frac{4 \cdot 5}{2} = 10$, matching the count in the table. Each inner loop pass runs two assignments, contributing $n(n+1)$ total operations, alongside $n$ evaluations of `sum = 1` and the initial assignment `x = 1`. Dropping constant factors and lower-order terms leaves **$O(n^2)$** (quadratic time). Even though the inner loop performs half the iterations of a full $n \times n$ grid, $\frac{1}{2} n^2$ still scales quadratically.

<Callout tone="orange" label="A classic mistake">
Nested loops are not automatically $O(n^2)$. If the inner loop runs a fixed number of times (such as exactly 3 iterations), the total cost is $3n = O(n)$. Conversely, an inner loop running up to $i$ remains $O(n^2)$, as shown above. Always count how many times the inner operations execute instead of assuming each nesting level adds a factor of $n$.
</Callout>
