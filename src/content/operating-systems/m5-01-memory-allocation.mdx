# Main Memory: Addresses, Swapping and Allocation

Every running program needs memory, and they all share the same RAM. How does the OS give each one its own space, stop them from scribbling on each other, and pack them in without wasting room? This lesson covers addresses, the hardware that checks and translates them, swapping, and the first two ways to divide memory up: contiguous allocation and segmentation.

## Background

- A program must be brought (from disk) **into memory** and placed within a process for it to run.
- **Main memory and registers** are the **only storage the CPU can access directly**.
  - The memory unit only sees a **stream of addresses + read requests**, or **address + data + write requests**. It doesn't know what they're for.
  - A **register** access takes one CPU clock (or less).
  - **Main memory** can take **many cycles**, causing a **stall**: the CPU waits.
  - A **cache** sits between main memory and the CPU registers to hide that delay.
- **Protecting memory** is required for correct operation: a process must not touch memory that isn't its own.

### Base and limit registers

A pair of **base** (relocation) and **limit** registers define a process's **logical address space**:

- **base** holds the smallest legal physical address,
- **limit** holds the size of the range.

The CPU must check **every memory access made in user mode** to make sure it lies between base and base + limit. If not, it **traps** to the OS (addressing error). Only the OS, in kernel mode, can load these registers.

## Address binding

Programs on disk, ready to be brought into memory to run, form an **input queue**.

- Without support, a program would have to be loaded at address **0000**. That's inconvenient: why should the first user process always sit at physical address 0000?
- Also, addresses are represented in **different ways** at different stages of a program's life:
  - in **source code**, addresses are usually **symbolic** (a variable named `count`),
  - the **compiler** binds them to **relocatable** addresses ("14 bytes from the beginning of this module"),
  - the **linker or loader** binds relocatable addresses to **absolute** addresses (like 74014).
- Each binding **maps one address space to another**.

### When does binding happen?

| Stage | How |
| --- | --- |
| **Compile time** | if the memory location is **known in advance**, **absolute code** can be generated. You must **recompile** if the starting location changes |
| **Load time** | if the location isn't known at compile time, the compiler generates **relocatable code**, and binding happens when the program is loaded |
| **Execution time** | binding is **delayed until run time**, so the process can be **moved** in memory while it runs. This needs **hardware support** for address maps (like base and limit registers) |

A user program goes through several steps: **source program → compiler/assembler → object module → linkage editor (with other object modules) → load module → loader (with system libraries) → in-memory binary image**, possibly with dynamically loaded system libraries joining at run time.

## Logical vs. physical addresses

The idea of a **logical address space** bound to a separate **physical address space** is central to memory management.

- **Logical address**: generated by the **CPU**. Also called a **virtual address**.
- **Physical address**: the address seen by the **memory unit**.

Logical and physical addresses are the **same** with compile-time and load-time binding. They **differ** with **execution-time** binding.

- The **logical address space** is the set of all logical addresses a program generates.
- The **physical address space** is the set of all physical addresses that correspond to them.

### The memory-management unit (MMU)

The **MMU** is the **hardware** that maps logical (virtual) addresses to physical ones **at run time**. There are many ways to do it; the rest of this chapter covers them.

The simplest: the value in a **relocation register** is **added to every address** a user process generates, at the moment it's sent to memory.

- The base register is now called the **relocation register**.
- (MS-DOS on the Intel 80x86 used **4** relocation registers.)
- The user program deals only with **logical** addresses. It **never sees** the real physical addresses.
- Execution-time binding happens when a reference is made to a location in memory.

Switch the MMU demo above to **Relocation register**: with relocation = 14000, logical address 346 becomes physical address 14346.

### Dynamic loading

With **dynamic loading**, a routine **isn't loaded until it's called**.

- **Better memory-space use**: a routine that's never used is never loaded.
- All routines are kept on disk in a **relocatable load format**.
- Useful when **large amounts of code** handle **rare cases** (like error handling).
- **No special support from the OS** is needed. It's done through **program design**, although the OS can help by providing libraries for it.

### Dynamic linking

- **Static linking**: system libraries are combined by the loader into the **binary program image**. Every program carries its own copy.
- **Dynamic linking**: linking is **postponed until execution time**.
  - A small piece of code, a **stub**, locates the right **memory-resident** library routine.
  - The stub **replaces itself** with the address of the routine, and runs it.
  - The OS checks whether the routine is in the process's memory address space; if not, it **adds** it.
- Dynamic linking is especially useful for **libraries**. Such libraries are also called **shared libraries**.
- It also helps with **library updates** (like bug fixes): replace the library with a new version, and every program that uses it gets the fix.

## Swapping

A process can be **swapped** temporarily **out of memory** to a **backing store**, then brought **back** into memory to continue.

- So the total physical memory of all processes can **exceed** physical memory.
- **Backing store**: a fast disk, large enough to hold copies of all memory images for all users, with **direct access** to them.
- **Roll out, roll in**: a swapping variant for **priority-based** scheduling. A lower-priority process is swapped out so a higher-priority one can be loaded and run.
- The **major part of swap time is transfer time**: it's directly proportional to the **amount of memory swapped**.
- The system keeps a **ready queue** of all ready-to-run processes whose memory images are on the backing store or in memory.
- Does a swapped-out process need to come back to the **same physical addresses**? It **depends on the address-binding method**. With execution-time binding, it can go anywhere.
- **Modified versions** of swapping are found on many systems (UNIX, Linux, Windows): swapping is normally **disabled**, starts only when more than a **threshold** of memory is allocated, and stops again when demand drops below it.

### Context-switch time with swapping

If the next process to run isn't in memory, we must swap a process **out** and swap the target process **in**. The context switch can then take a **very** long time:

- a **100 MB** process swapping to a hard disk with a transfer rate of **50 MB/sec**,
- swap out time: **2000 ms**,
- plus swapping in a same-sized process,
- total context-switch swapping time: **4000 ms**.

<SwapTimeCalc />

We can reduce this by swapping only the memory that's **really being used**. Processes can tell the OS with system calls like `request_memory()` and `release_memory()`.

**Other constraints:**

- **Pending I/O**: a process **can't be swapped out** while I/O is happening into its memory, or the I/O would land in the wrong process's memory. Or the I/O can go into **kernel buffers** first, then to the process. That's **double buffering**, which adds overhead.
- **Standard swapping isn't used in modern OSs**, but a modified version is common: swap only when free memory is **extremely low**.
- **Mobile systems don't support swapping.** Instead, when memory is low:
  - **Android terminates apps**,
  - **iOS asks apps to voluntarily release** memory.

## Contiguous allocation

Main memory must hold **both the OS and the user processes**, and it must be shared **efficiently**. **Contiguous allocation** is one early method.

- Main memory is usually divided into **two partitions**:
  - the **resident OS**, usually in **low memory** with the interrupt vector,
  - **user processes** in **high memory**.
- **Each process** is contained in a **single contiguous section** of memory.

### Protection with relocation registers

**Relocation registers** protect user processes from **each other**, and from changing OS code and data:

- the **base (relocation) register** holds the value of the **smallest physical address**,
- the **limit register** holds the **range of logical addresses**: each logical address must be **less than** the limit,
- the MMU maps logical addresses **dynamically** by **adding** the base,
- on each **context switch**, the dispatcher loads the base and limit registers for the process about to run.

This scheme also lets the **OS's own size change dynamically**: useful for OS services that aren't used often. Their code, loaded and unloaded as needed, is called **transient code**.

### Multiple partitions

Memory is divided into **several partitions** (the **multiple-partition method**):

- The **degree of multiprogramming** is limited by the number of partitions.
- **Variable-partition sizes** are used for efficiency: each sized to a process's needs.
- A **hole** is a block of **available** memory. Holes of various sizes are **scattered** throughout memory.
- When a process **arrives**, it's given memory from a hole **large enough** for it.
- When a process **exits**, its partition is freed, and **adjacent free partitions are combined**.
- The OS keeps track of **(a) allocated partitions** and **(b) free partitions (holes)**.

### The dynamic storage-allocation problem

How do we satisfy a request of size $n$ from a list of free holes?

| Strategy | Rule | Notes |
| --- | --- | --- |
| **First fit** | allocate the **first** hole that's big enough | fast: stop searching as soon as one fits |
| **Best fit** | allocate the **smallest** hole that's big enough | must search the whole list (unless it's sorted by size). Leaves the **smallest** leftover hole |
| **Worst fit** | allocate the **largest** hole | must also search the whole list. Leaves the **largest** leftover hole |

**First fit and best fit are better than worst fit** in both speed and storage use.

Try the classic exercise: holes of **100K, 500K, 200K, 300K and 600K**, and requests of **212K, 417K, 112K and 426K**, in that order. Which strategy places all four?

### Fragmentation

- **External fragmentation**: there's **enough total memory** to satisfy a request, but it's **not contiguous**. Memory is broken into lots of small holes.
  - First fit and best fit both suffer from it.
  - Analysis of first fit shows that, with $N$ blocks allocated, another **½ N blocks are lost** to fragmentation. So **one third** of memory may be unusable: the **50-percent rule**.
- **Internal fragmentation**: the allocated memory may be **slightly larger** than what was requested. The difference is memory **inside** a partition that isn't being used.

**Compaction** reduces external fragmentation:

- **shuffle** the memory contents to put **all free memory together** in one large block,
- only possible if relocation is **dynamic**, done at **execution time**: move the process, then change its base register,
- **I/O problem**: don't move a process while it's doing I/O. Either **latch** the job in memory during I/O, or do I/O only into **OS buffers**.

The **backing store** has the same fragmentation problems.

## Segmentation

**Segmentation** is a memory-management scheme that matches **the programmer's view of memory**.

A program is a **collection of segments**. Each segment is a **logical unit**, such as: the main program, a procedure, a function, a method, an object, local and global variables, a common block, the stack, the symbol table, arrays.

Segments are placed separately in physical memory: segment 1 of the logical address space might sit near the top of physical memory, segment 2 near the bottom.

### Segmentation architecture

- A logical address is a **two-tuple**: **⟨segment-number, offset⟩**.
- A **segment table** maps these two-dimensional addresses into one-dimensional physical addresses. Each entry has:
  - **base**: the **starting physical address** of the segment,
  - **limit**: the **length** of the segment.
- **Hardware support:**
  - the **segment-table base register (STBR)** points to the segment table's location in memory,
  - the **segment-table length register (STLR)** says how many segments the process uses. Segment number $s$ is **legal if $s <$ STLR**.

The hardware checks **offset < limit**. If yes, the physical address is **base + offset**; if not, it **traps** (addressing error).

<SegmentTranslator />

**Protection:** each segment-table entry has a **validation bit** (0 means an illegal segment) and **read/write/execute** privileges. Protection bits belong to segments, so **code sharing happens at the segment level**.

Since segments **vary in length**, memory allocation is again a **dynamic storage-allocation problem**: first fit, best fit, external fragmentation and all.
