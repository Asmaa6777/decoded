# Processes: The Program in Motion

Double-click an app and, a moment later, it's running. Something changed between those two moments: a file on your disk became a **process**. A process is the basis of all computation on a computer, and this lesson covers what one is made of, the states it moves through, how the OS juggles many of them, and how processes are born and die.

## The process concept

An OS runs many kinds of programs:

- a **batch system** runs **jobs**,
- a **time-shared system** runs **user programs** or **tasks**.

The words **job** and **process** are used almost interchangeably.

<Callout tone="mint" label="Program vs. process">
A **program** is a **passive** entity stored on disk (an executable file). A **process** is an **active** entity. A program **becomes** a process when its executable file is **loaded into memory**, whether you start it with a mouse click or by typing its name.
</Callout>

- **One program can be several processes.** Think of several users running the same program, or you opening three browser windows.
- A **process** is a **program in execution**. Its execution must progress in a **sequential** fashion.

### A process in memory

A process is made of several parts:

| Part | Holds |
| --- | --- |
| **Text section** | the **program code** |
| **Current activity** | the **program counter** and the **processor registers** |
| **[Stack](/courses/data-structures/stacks#the-call-stack)** | temporary data: **function parameters**, **return addresses**, **local variables** |
| **Data section** | **global variables** |
| **Heap** | memory **dynamically allocated** while the process runs |

## Process state

As a process runs, it **changes state**:

| State | Meaning |
| --- | --- |
| **new** | the process is being **created** |
| **running** | its instructions are being **executed** |
| **waiting** | it's waiting for some **event** to occur |
| **ready** | it's waiting to be **assigned to a processor** |
| **terminated** | it has **finished** execution |

<Callout tone="orange" label="Waiting vs. ready">
Both are "not running", but for different reasons. A **waiting** process *couldn't* use the CPU even if offered it (it needs its I/O first). A **ready** process could run *right now*, if only the CPU were free.
</Callout>

## The Process Control Block (PCB)

The OS keeps all the information about each process in its **Process Control Block (PCB)**:

- **Process state**: running, waiting, etc.
- **[Program counter](/courses/computer-organization/inside-the-cpu#the-registers-that-matter-most)**: the location of the next instruction to execute.
- **CPU registers**: the contents of all the process-centric registers.
- **CPU-scheduling information**: priorities, pointers to scheduling queues.
- **Memory-management information**: the memory allocated to the process.
- **Accounting information**: CPU time used, clock time since it started, time limits.
- **I/O status information**: I/O devices allocated to the process, its list of open files.

## Process scheduling

The goal: **maximize CPU use**, and quickly switch processes onto the CPU for **time sharing**.

The **process scheduler** selects which available process runs next on the CPU. It keeps **scheduling queues** of processes:

| Queue | Contains |
| --- | --- |
| **Job queue** | **all** processes in the system |
| **Ready queue** | the processes in **main memory**, **ready** and waiting to run |
| **Device queues** | the processes **waiting for an I/O device** (one queue per device) |

Processes **migrate** among the queues. The one that matters most is the **ready queue**: the processes in main memory that are ready and waiting for the CPU. A **queuing diagram** shows this: a process sits in the ready queue until it's dispatched to the CPU. Then one of these happens:

- it issues an **I/O request** and goes into an I/O queue,
- its **time slice expires** and it goes back to the ready queue,
- it **forks a child** and waits for it,
- it **waits for an interrupt**.

Each path eventually leads back to the ready queue, until the process terminates.

### Schedulers

| Scheduler | Chooses | Runs | Speed |
| --- | --- | --- | --- |
| **Long-term** (job scheduler) | which processes are brought **into the ready queue** | very **infrequently** (seconds, minutes) | may be slow |
| **Short-term** (CPU scheduler) | which process **runs next** on the CPU | very **frequently** (milliseconds) | must be fast |

- The **short-term scheduler** (CPU scheduler) picks which process in the ready queue runs next. It runs every few milliseconds, so it must be fast, and it's sometimes the **only** scheduler in a system.
- The **long-term** scheduler controls the **degree of [multiprogramming](/courses/operating-systems/os-architecture-and-operations#multiprogramming)**: how many processes are in memory.

Processes can be described as either:

- **I/O-bound**: spends more time doing I/O than computing. **Many short CPU bursts.**
- **CPU-bound**: spends more time computing. **Few, very long CPU bursts.**

The long-term scheduler aims for a **good mix** of the two. All I/O-bound and the CPU sits idle; all CPU-bound and the devices sit idle. You saw why in this multiprogramming demo from the first module:

### Medium-term scheduling

A **medium-term scheduler** can be added when the degree of multiprogramming needs to **decrease**. It removes a process from memory, stores it on disk, then brings it back from disk later to continue running. This is **[swapping](/courses/operating-systems/memory-allocation#swapping)**.

### Context switch

When the CPU switches to another process, the system must **save the state of the old process** and **load the saved state of the new one**. This is a **context switch**.

- The **context** of a process is stored in its **PCB**.
- Context-switch time is **pure overhead**: the system does no useful work while switching.
- The more complex the OS and the PCB, the **longer** the context switch.
- The time also depends on **hardware support** (some CPUs have several sets of registers, so a switch is just changing a pointer).

## Operations on processes

The OS must provide mechanisms for **creating** and **terminating** processes.

### Process creation

A **parent** process creates **child** processes, which can create their own, forming a **tree of processes**. Each process is identified and managed by its **process identifier (pid)**.

<LinuxProcessTree />

**Resource-sharing options:**

- parent and children share **all** resources,
- children share a **subset** of the parent's resources,
- parent and child share **no** resources.

**Execution options:**

- parent and children run **concurrently**,
- the parent **waits** until some or all children terminate.

**Address-space options:**

- the child is a **duplicate** of the parent (same program and data),
- the child has a **new program** loaded into it.

### fork() and exec() in UNIX

- The **`fork()`** [system call](/courses/operating-systems/services-and-system-calls) creates a new process. The child is a copy of the parent.
- The **`exec()`** system call is used **after** `fork()` to **replace the process's memory** with a new program.

```c
#include <sys/types.h>
#include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid;
    pid = fork();              /* fork a child process */

    if (pid < 0) {             /* error occurred */
        fprintf(stderr, "Fork Failed");
        return 1;
    }
    else if (pid == 0) {       /* child process */
        execlp("/bin/ls", "ls", NULL);
    }
    else {                     /* parent process */
        wait(NULL);            /* parent waits for the child to complete */
        printf("Child Complete");
    }
    return 0;
}
```

The trick: `fork()` returns **twice**, once in each process. In the **child** it returns **0**; in the **parent** it returns the **child's pid**. That's how the same code knows which copy it's running in.

### Process termination

- A process runs its last statement, then asks the OS to delete it with **`exit()`**.
  - The child can return a **status** to its parent (collected with **`wait()`**).
  - The OS **deallocates** the process's resources.
- A parent may **terminate** its children with **`abort()`**, for example when:
  - the child has **exceeded** its allocated resources,
  - the task given to the child is **no longer needed**,
  - the **parent is exiting**. Some OSs don't let a child continue if its parent terminates. Then **all its children must also be terminated**: this is **cascading termination**.

<ModelAnswer>
**(Midterm 2014, Q3) Describe the differences among short-term, medium-term, and long-term scheduling.**

- **Long-term (job) scheduler:** decides which jobs are brought into memory. It runs rarely and controls the degree of multiprogramming.
- **Short-term (CPU) scheduler:** picks, from the ready processes in memory, the one that runs next, and gives it the CPU. It runs very often.
- **Medium-term scheduler:** swaps partly run programs out of memory and brings them back later. It is used mainly in time-sharing systems.

The 2014 key gives the same three roles.
</ModelAnswer>

<ModelAnswer>
**(Midterm 2017, Q3) What is a process? What is a process state and mention the various states of a process? What is a PCB?**

A **process** is a program in execution: an active entity with a program counter and its own resources (stack, data and registers).

A process **state** is its current situation. The states are **new**, **ready**, **running**, **waiting** and **terminated**.

The **PCB** (process control block) is the record the OS keeps for each process. It holds the process state, program counter, CPU registers, CPU-scheduling information, memory-management information, accounting information and I/O status.
</ModelAnswer>

<ModelAnswer>
**(Midterm 2019 second version, Q6) What is the difference between zombie and orphan processes?**

- A **zombie** is a child that has finished, but its parent has not yet called `wait()`, so its exit status is still held.
- An **orphan** is a child whose parent has terminated without calling `wait()`. The orphan is adopted by the init process.

The printed key gives the same two definitions.
</ModelAnswer>

<ModelAnswer>
**(Midterm 2019 second version, Q8) Including the initial parent process, how many processes are created by the program shown in the code below? Illustrate your answer using a tree.**

The code has three `fork()` calls, one after another, in `main`.

Each `fork()` doubles the number of processes, because every process that exists at that point forks a copy of itself:

- Before any `fork()`: 1 process (the parent).
- After the first `fork()`: 2.
- After the second: 4.
- After the third: 8.

**Answer: 8 processes, including the initial parent.** The tree has the parent at the root, with a child added at each `fork()` for every process that already exists. The printed key says 8 as well.
</ModelAnswer>

<ModelAnswer>
**(Midterm 2018, Q4) Describe the actions taken by a kernel to context-switch between processes.**

The kernel saves the state of the running process into its PCB: the CPU registers, the program counter and the memory information. It then loads the state of the next process from that process's PCB into the CPU, so the new process resumes where it stopped. Some architectures also flush caches or the TLB at this point. The switch is pure overhead, because no useful work runs during it.
</ModelAnswer>

<ModelAnswer>
**(Midterm 2018 second version, Q4) What is a PCB? Describe the actions taken by a kernel to context-switch between processes.**

The **PCB** is the process control block, the kernel's record for one process (see the 2017 answer above). To context-switch, the kernel saves the running process's registers and program counter into its PCB, then restores the same fields from the next process's PCB and hands over the CPU.
</ModelAnswer>

**(Final 2019 spring, Q4) Describe the actions taken by a kernel to context-switch between processes.**

The OS saves the state of the running process (the CPU registers, plus its memory information) and restores the state of the process to run next. On many architectures it also flushes caches. The midterm answer above gives the same steps.
</ModelAnswer>

<ModelAnswer>
**(Final 2019 fall, Q4) During the course of execution, a process may create several new processes. What are the possible options of execution and of resource sharing between the parent and the children? What are the reasons a parent may terminate its child? What are the possible options for process termination?**

- **Execution:** the parent continues to run concurrently with its children, or it waits until some or all of them have terminated.
- **Resource sharing:** the parent and children share all resources; the children share a subset of the parent's resources; or they share none.
- **Reasons a parent terminates a child:** the child has exceeded its resources, the task given to the child is no longer needed, or the parent is exiting.
- **Termination options:** some systems don't let a child continue after its parent terminates, and in cascading termination all children are terminated when the parent is.
</ModelAnswer>
