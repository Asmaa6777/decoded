# Semaphores and the Classic Synchronization Problems

A mutex lets one process in at a time. Often you need more: "let up to 3 in", "don't start step 2 until step 1 is done", "wait until there's something to consume". The **semaphore** handles all of these. This lesson builds semaphores, shows how they can go wrong, and uses them on three classic problems that every new synchronization tool is tested against.

## Semaphores

A **semaphore** is a synchronization tool that can be built **without [busy waiting](/courses/operating-systems/critical-section-problem#mutex-locks)**.

- A semaphore **S** is an **integer variable**.
- It's changed by two standard operations, **`wait()`** and **`signal()`**. They were originally called **P()** and **V()** (from the Dutch words *proberen*, "to test", and *verhogen*, "to increment").
- It's **less complicated** to use than the hardware instructions.
- It can **only** be accessed through these two **indivisible (atomic)** operations:

```c
wait(S) {
    while (S <= 0)
        ;   // busy wait
    S--;
}

signal(S) {
    S++;
}
```

### Semaphore usage

- A **counting semaphore**'s value can range over an **unrestricted** domain. Use it to control access to a resource with **several instances**: initialize S to the number available.
- A **binary semaphore**'s value can only be **0 or 1**. That's the **same as a [mutex lock](/courses/operating-systems/critical-section-problem#mutex-locks)**.
- A counting semaphore can be **implemented** using binary semaphores.

Semaphores solve many synchronization problems. For example: two concurrent processes, $P_1$ with a statement $S_1$, and $P_2$ with a statement $S_2$. We need $S_2$ to run **only after** $S_1$ has finished. Use a semaphore `synch` initialized to **0**:

```c
/* P1 */                  /* P2 */
S1;                       wait(synch);
signal(synch);            S2;
```

If $P_2$ gets there first, `wait(synch)` stops it until $P_1$ signals.

### Implementing semaphores

The implementation must guarantee that **no two processes** can run `wait()` and `signal()` on the **same semaphore at the same time**.

- So the implementation **itself** becomes a [critical-section problem](/courses/operating-systems/critical-section-problem#the-critical-section-problem), with the wait and signal code inside the critical section.
- We could now have **busy waiting** in the implementation. But that code is **short**, so there's **little busy waiting** if the critical section is rarely occupied.
- But **applications** may spend a long time in their critical sections, so busy waiting there is **not a good solution**.

### Implementation with no busy waiting

Give each semaphore its own **waiting queue**:

```c
typedef struct {
    int value;
    struct process *list;
} semaphore;
```

Two operations help:

- **`block()`**: put the process that called it on the right **waiting queue**, and stop running it.
- **`wakeup(P)`**: take process P off the waiting queue and put it in the **[ready queue](/courses/operating-systems/processes#process-scheduling)**.

```c
wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        add this process to S->list;
        block();
    }
}

signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        remove a process P from S->list;
        wakeup(P);
    }
}
```

A blocked process sleeps instead of spinning, so it uses **no CPU** while waiting.

## Deadlock and starvation

**Deadlock**: two or more processes are **waiting forever** for an event that only one of the **waiting** processes could cause.

Let **S** and **Q** be two semaphores initialized to **1**:

```c
/* P0 */          /* P1 */
wait(S);          wait(Q);
wait(Q);          wait(S);
  ...               ...
signal(S);        signal(Q);
signal(Q);        signal(S);
```

Each process asks for the two semaphores in a **different order**. That's fine most of the time, until the scheduler switches at exactly the wrong moment:

Two related problems:

- **Starvation** (indefinite blocking): a process may **never be removed** from the semaphore queue it's waiting in. For example, if the queue is served in LIFO order.
- **Priority inversion**: a **scheduling** problem where a **lower-priority** process holds a lock that a **higher-priority** process needs. The important process ends up waiting on the unimportant one.

## Classic problems of synchronization

These are the standard tests for any new synchronization scheme:

1. the **bounded-buffer** problem,
2. the **readers-writers** problem,
3. the **dining-philosophers** problem.

### 1. The bounded-buffer problem

- **n** buffers, each holding one item.
- Semaphore **`mutex`** initialized to **1**: protects the buffer itself.
- Semaphore **`full`** initialized to **0**: counts the **full** slots.
- Semaphore **`empty`** initialized to **n**: counts the **empty** slots.

**Producer:**

```c
do {
    ...
    /* produce an item in next_produced */
    ...
    wait(empty);
    wait(mutex);
    ...
    /* add next_produced to the buffer */
    ...
    signal(mutex);
    signal(full);
} while (true);
```

**Consumer:**

```c
do {
    wait(full);
    wait(mutex);
    ...
    /* remove an item from buffer to next_consumed */
    ...
    signal(mutex);
    signal(empty);
    ...
    /* consume the item in next_consumed */
    ...
} while (true);
```

<SemaphoreBuffer />

<Callout tone="orange" label="Order matters">
What if the producer did `wait(mutex)` **before** `wait(empty)`? With a full buffer, it would grab the mutex and then block on `empty`, while holding the mutex. The consumer could never get in to free a slot: deadlock.
</Callout>

### 2. The readers-writers problem

A **data set** is shared among several concurrent processes:

- **Readers** only **read** the data set. They never update it.
- **Writers** can both **read and write**.

The problem:

- allow **multiple readers** to read **at the same time**,
- but only **one writer** may access the shared data at a time (with no readers).

**Shared data:**

- the data set,
- semaphore **`rw_mutex`** initialized to **1** (writers' lock, also taken by the first reader),
- semaphore **`mutex`** initialized to **1** (protects `read_count`),
- integer **`read_count`** initialized to **0** (how many are reading now).

**Writer:**

```c
do {
    wait(rw_mutex);
    ...
    /* writing is performed */
    ...
    signal(rw_mutex);
} while (true);
```

**Reader:**

```c
do {
    wait(mutex);
    read_count++;
    if (read_count == 1)      /* first reader in locks out writers */
        wait(rw_mutex);
    signal(mutex);
    ...
    /* reading is performed */
    ...
    wait(mutex);
    read_count--;
    if (read_count == 0)      /* last reader out lets writers in */
        signal(rw_mutex);
    signal(mutex);
} while (true);
```

<ReadersWriters />

**Variations.** There are several ways to treat readers and writers, and they all involve **priorities**:

- **First variation:** no reader is kept waiting unless a writer **already has permission** to use the shared object. (That's the code above.)
- **Second variation:** once a writer is **ready**, it writes **as soon as possible**.
- Both may lead to **starvation** (of writers in the first, of readers in the second), which leads to even more variations.

On some systems the **[kernel](/courses/operating-systems/what-an-os-does#so-what-exactly-counts-as-the-os) provides reader-writer locks** that solve this for you.

### 3. The dining-philosophers problem

- Philosophers spend their lives **thinking** and **eating**.
- They don't talk to their neighbours. Now and then a philosopher tries to pick up **2 chopsticks** (one at a time) to eat from the bowl.
- They need **both** to eat, and put both down when finished.

**Shared data** (for 5 philosophers): the bowl of rice (the data set), and semaphores **`chopstick[5]`**, each initialized to **1**.

**The structure of philosopher i:**

```c
do {
    wait(chopstick[i]);
    wait(chopstick[(i + 1) % 5]);

        // eat

    signal(chopstick[i]);
    signal(chopstick[(i + 1) % 5]);

        // think
} while (true);
```

**What's the problem with this algorithm?** No two neighbours eat at once, so it's safe. But if **all five** get hungry at the same time and each picks up their **left** chopstick, every `chopstick` semaphore is now 0, and everyone waits forever for their right one. **Deadlock.**

<DiningPhilosophers />

Some ways to fix it:

- allow **at most 4** philosophers at the table at once,
- let a philosopher pick up chopsticks **only if both** are free (do it inside a critical section),
- use an **asymmetric** solution: odd-numbered philosophers pick up their **right** chopstick first, even-numbered ones their **left** first (the fix in the demo above).

## Problems with semaphores

Semaphores are powerful but easy to misuse, and one mistake anywhere breaks everything:

- **`signal(mutex) … wait(mutex)`**: the order is swapped. Several processes may be in their critical sections at once, so [mutual exclusion](/courses/operating-systems/critical-section-problem#what-a-solution-must-guarantee) is gone.
- **`wait(mutex) … wait(mutex)`**: `signal` was replaced by `wait`. The process blocks itself forever: deadlock.
- **Omitting** `wait(mutex)` or `signal(mutex)` (or both): either mutual exclusion is broken, or a deadlock happens.

All of these lead to **deadlock** and **starvation**, and they're hard to find, because they only show up in particular interleavings.

## Where you meet this every day

  <PracticalApplication title="Limiting database connections" tool="COUNTING SEMAPHORE">
    A server with 10 database connections uses a semaphore initialized to 10. The 11th request waits until someone signals that a connection is free.
  </PracticalApplication>
  <PracticalApplication title="Many readers, one editor" tool="READER-WRITER LOCKS">
    Caches and config stores are read constantly and changed rarely. Reader-writer locks (like Java's ReentrantReadWriteLock) let all the reads run in parallel.
  </PracticalApplication>
  <PracticalApplication title="Two bank transfers in opposite directions" tool="DEADLOCK">
    Transfer A→B locks A then B; transfer B→A locks B then A. That's the S and Q example. Real systems fix it by always locking accounts in the same order, the same trick as the asymmetric philosophers.
  </PracticalApplication>
  <PracticalApplication title="The Mars Pathfinder reset bug" tool="PRIORITY INVERSION">
    In 1997 the Pathfinder lander kept rebooting because a low-priority task held a lock a high-priority task needed. Engineers fixed it from Earth by enabling priority inheritance.
  </PracticalApplication>

<ModelAnswer>
**(Midterm 2015, Q5; Midterm 2021, Q4; Midterm 2019, Q4) A semaphore does not suffer busy waiting. Explain how its implementation avoids this drawback and describe how it is used to solve the readers-writers problem.** *(The 2019 version asks for the code of the semaphore and the readers-writers solution.)*

**Avoiding busy waiting.** A semaphore has a value and a queue of waiting processes. `wait(S)` decrements the value. If the value is then negative, the process is put in the queue and **blocked**, so it stops using the CPU. `signal(S)` increments the value. If a process is waiting, it removes one from the queue and **wakes** it, so it becomes ready again. A waiting process never loops on the CPU.

```c
typedef struct { int value; struct process *list; } semaphore;

wait(S)   { S.value--; if (S.value < 0) { add this process to S.list; block(); } }
signal(S) { S.value++; if (S.value <= 0) { remove a process P from S.list; wakeup(P); } }
```

**Readers-writers.** Three shared variables: `rw_mutex = 1` (lets a writer, or the first reader, lock out everyone else), `mutex = 1` (protects `read_count`), and `read_count = 0`.

- A **writer** does `wait(rw_mutex)`, writes, then `signal(rw_mutex)`.
- A **reader** does `wait(mutex)`, increments `read_count`, and if it is the **first** reader it does `wait(rw_mutex)`. It then does `signal(mutex)`, reads, does `wait(mutex)` again, decrements `read_count`, and if it is the **last** reader it does `signal(rw_mutex)`.

Many readers can read together, but a writer can only write when no reader is inside.
</ModelAnswer>

<ModelAnswer>
**(Midterm 2017, Q4) A semaphore does not suffer busy waiting. What is the meaning of the term busy waiting? Explain how the semaphore implementation can avoid busy waiting, and describe how it is used to solve the bounded buffer problem.**

**Busy waiting** means a process keeps looping and testing a condition on the CPU while it waits for another process to leave its critical section. The CPU does nothing useful during that time.

A semaphore avoids it by blocking: a process that finds the value not positive joins the semaphore's queue and sleeps. Another process's `signal()` wakes it up.

**Bounded buffer** (n buffers, each holding one item): `mutex = 1`, `full = 0`, `empty = n`.

- **Producer:** `wait(empty)`, `wait(mutex)`, add the item, `signal(mutex)`, `signal(full)`.
- **Consumer:** `wait(full)`, `wait(mutex)`, remove the item, `signal(mutex)`, `signal(empty)`.

`empty` counts free slots and `full` counts filled slots, so neither side writes into a full buffer or reads an empty one. `mutex` keeps the two from changing the buffer at the same time. The printed key uses the same three semaphores.
</ModelAnswer>

<ModelAnswer>
**(Midterm 2022, Q5) Regarding the readers-writers problem, with the shared variables `int readCount`, `FILE *sharedFile` and `semaphore mutex, writeBlock`.** *(The 2022 answer key is a scan that has not been checked yet; the answers below are ours.)*

1. **Initial values:** `readCount = 0`, `mutex = 1`, `writeBlock = 1`. `mutex` protects `readCount`, and `writeBlock` is the lock that writers, and the first reader, take.
2. **Three new readers while a writer is updating:** the first reader takes `mutex` and then blocks on `wait(writeBlock)`, because the writer holds it. It keeps `mutex` while it waits. The second and third readers block at `wait(mutex)`, which the first reader holds.
3. **A new writer while some readers are reading:** the readers hold `writeBlock` (the first reader took it). The writer blocks at `wait(writeBlock)` until the last reader signals `writeBlock` on its way out.
4. **Writer starvation:** **yes.** As long as new readers keep arriving before the last reader leaves, `read_count` never drops to 0, so `writeBlock` is never released and a writer can wait forever.
</ModelAnswer>

**(Final 2019 spring, Q5) Explain the problems of using semaphores as a synchronization tool. Describe how the Dining Philosophers problem is solved using semaphores.**

**Problems with semaphores:**

- **Wrong use:** `signal(mutex) ... wait(mutex)`, `wait(mutex) ... wait(mutex)`, or leaving out a `wait` or a `signal` (or both).
- **Deadlock:** two or more processes wait forever for events only the waiting processes can cause. For example, P0 does `wait(S); wait(Q)` while P1 does `wait(Q); wait(S)`.
- **Starvation:** a process can be blocked on the semaphore's queue forever.
- **Priority inversion:** a low-priority process holds a lock that a high-priority process needs.

**Dining philosophers:** five philosophers share five chopsticks, each represented by a semaphore `chopstick[i] = 1`. Philosopher *i* does `wait(chopstick[i])`, then `wait(chopstick[(i+1) % 5])`, eats, and signals both. This solution can **deadlock**: if all five pick up their left chopstick at once, each waits for the right one forever. The printed key gives only the basic solution; the deadlock risk is our note.
</ModelAnswer>
