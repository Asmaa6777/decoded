# Paging

Contiguous allocation and segmentation both suffer from **external fragmentation**: free memory chopped into holes too small to use. Paging solves it with a simple idea: cut **everything** into equal-sized pieces. Any free piece fits any page. Almost every modern computer, including your phone, uses paging.

## The idea

The **physical address space** of a process can be **noncontiguous**: the process gets physical memory **wherever it's available**.

- This **avoids external fragmentation**.
- It avoids the problem of **variable-sized** memory chunks.

How it works:

- Divide **physical memory** into fixed-sized blocks called **frames**. The size is a **power of 2**, normally between **512 bytes and 16 MB**.
- Divide **logical memory** into blocks of the **same size**, called **pages**.
- Keep track of **all free frames**.
- To run a program of **N pages**, find **N free frames** (anywhere!) and load the program.
- Set up a **page table** to translate logical addresses to physical ones: it maps each logical **page** to its physical **frame**.
- The **backing store** is split into pages too.
- There's still **internal fragmentation**: the last frame a process gets may not be completely full.

## Address translation

An address generated by the CPU is divided into:

- **page number (p)**: used as an **index** into the page table, which holds the **base address** of each page in physical memory (its frame),
- **page offset (d)**: combined with that base address to give the **physical address** sent to the memory unit.

For a logical address space of $2^m$ and a page size of $2^n$:

| page number $p$ | page offset $d$ |
| --- | --- |
| $m - n$ bits | $n$ bits |

The paging hardware: **CPU** produces $(p, d)$ → the **page table** turns $p$ into a frame number $f$ → **physical address** is $(f, d)$, meaning $f \times \text{page size} + d$.

### A paging example

A **32-byte** physical memory with **4-byte pages**: $n = 2$, and a 16-byte logical address space so $m = 4$. The process's page table maps page 0 → frame 5, page 1 → frame 6, page 2 → frame 1, page 3 → frame 2.

Logical address 0 is page 0, offset 0. Page 0 is in frame 5, so it maps to physical address $5 \times 4 + 0 = 20$. Logical address 13 is page 3, offset 1, so it maps to $2 \times 4 + 1 = 9$.

- The **process's view** and **physical memory** are now **very different**: the process sees one tidy block, while its pages are scattered.
- By construction, a process can **only access its own memory**: there's no page-table entry pointing anywhere else.

### Calculating internal fragmentation

- Page size = **2,048** bytes
- Process size = **72,766** bytes
- That's **35 pages + 1,086 bytes**, so it needs **36 frames**
- Internal fragmentation = 2,048 − 1,086 = **962 bytes**

The **worst case** is 1 frame − 1 byte; **on average**, half a frame. So should frames be small? But **each page-table entry takes memory** to track, so smaller pages mean bigger page tables. In practice, **page sizes have been growing over time**.

### Free frames

The OS keeps a **free-frame list**. When a new process of $N$ pages arrives, it takes $N$ frames from the list, puts each page into one, and records the frame numbers in the new process's page table.

## Implementing the page table

- If the page table is **reasonably small**, it can be kept in **dedicated registers**. For example, the DEC PDP-11 had 16-bit addresses and 8 KB pages, so its page table had just **eight entries**, all in fast registers.
- Most computers allow **very large** page tables, so the page table is kept in **main memory**:
  - the **page-table base register (PTBR)** points to the page table,
  - the **page-table length register (PTLR)** gives its size.

The problem: now **every** data or instruction access needs **two memory accesses**: one for the page-table entry, and one for the data itself. That would make every program twice as slow.

### The TLB

The fix is a special, fast lookup cache called the **translation look-aside buffer (TLB)**, built from **associative memory**:

- Each TLB entry has two parts: a **page number** (the key) and the matching **frame number**.
- An item is compared with **all keys at the same time** (a parallel search).
- Address translation for $(p, d)$:
  - if $p$ is in the TLB (a **hit**), take the frame number from it,
  - otherwise (a **miss**), get the frame number from the page table in memory, and **add it to the TLB** for faster access next time. When the TLB is full, a **replacement policy** decides which entry to throw out.

### Effective access time

- **Associative lookup** = $\varepsilon$ time units. It can be under **10%** of the memory access time.
- **Hit ratio** = $\alpha$: the percentage of times a page number is found in the TLB. It depends on the **number of TLB entries**.
- Memory access time = $m$ nanoseconds.

$$
\text{EAT} = (m + \varepsilon)\,\alpha + (2m + \varepsilon)(1 - \alpha) = 2m + \varepsilon - m\alpha
$$

- With $\alpha = 80\%$, $\varepsilon = 20$ ns and $m = 100$ ns: $\text{EAT} = 0.80 \times 120 + 0.20 \times 220 = $ **140 ns**.
- With a more realistic $\alpha = 99\%$: $\text{EAT} = 0.99 \times 120 + 0.01 \times 220 = $ **121 ns**.

So with a good TLB, paging costs only about **21%** extra instead of 100%.

## Memory protection

- Protection is done with a **protection bit** for each frame, saying whether **read-only** or **read-write** access is allowed. More bits can mark pages as **execute-only**, and so on.
- A **valid-invalid bit** is attached to each page-table entry:
  - **"valid"**: the page is in the process's logical address space, so it's a **legal** page,
  - **"invalid"**: the page is **not** in the process's logical address space.
  - Or use the **PTLR** to reject page numbers beyond the table's length.
- Any **violation** causes a **trap** to the kernel.

## Shared pages

**Shared code:**

- **One copy** of read-only (**reentrant**) code is shared among processes: text editors, compilers, window systems.
- It's like several threads sharing the same process space.
- Sharing **read-write** pages also works for **interprocess communication**.

**Private code and data:** each process keeps a **separate copy** of its own code and data. The pages for private code and data can appear **anywhere** in the logical address space.

For example, three users running the same editor: each process's page table points the editor's pages to the **same three frames** in memory, while each has its own private data page.

## Structure of the page table

Memory for paging structures can get **huge** with the straightforward approach:

- a **32-bit** logical address space, as on many computers,
- a page size of **4 KB** ($2^{12}$),
- the page table would have **1 million entries** ($2^{32} / 2^{12}$),
- if each entry is **4 bytes**, that's **4 MB** of memory for the page table **alone**, per process. And we don't want to allocate that **contiguously** in main memory.

Alternatives:

1. **Hierarchical paging**
2. **Hashed page tables**
3. **Inverted page tables**

### Hierarchical page tables

**Break up the logical address space into multiple page tables.** A simple technique is a **two-level page table**: we **page the page table** itself.

**Two-level example** (32-bit machine, **1 KB** pages):

- A logical address is divided into a **22-bit page number** and a **10-bit page offset**.
- Since the page table is paged, the page number is further divided into a **12-bit** page number $p_1$ and a **10-bit** offset $p_2$.

| $p_1$ | $p_2$ | $d$ |
| --- | --- | --- |
| 12 bits | 10 bits | 10 bits |

$p_1$ is an index into the **outer page table**, and $p_2$ is the displacement within the page of the **inner page table**.

### 64-bit logical address spaces

Even two-level paging isn't enough for 64 bits:

- with **4 KB** pages ($2^{12}$), the page table has $2^{52}$ entries,
- with a two-level scheme, inner page tables could hold $2^{10}$ 4-byte entries, so an address looks like: outer page **42 bits**, inner page **10 bits**, offset **12 bits**,
- the outer page table then has $2^{42}$ entries!
- One solution is a **second outer page table** (three-level paging). But even then, the second outer table is still $2^{32}$ bytes, and it could take **4 memory accesses** to reach one physical location.

### Hashed page tables

Common in address spaces **larger than 32 bits**.

- The **virtual page number is hashed** into a page table.
- Each table slot holds a **chain** of elements that hash to the same location.
- Each element contains: **(1)** the virtual page number, **(2)** the mapped page frame, **(3)** a pointer to the next element.
- Virtual page numbers in the chain are **compared** until a match is found; then its **physical frame** is used.

### Inverted page tables

Instead of **each process** having a page table that tracks all its possible logical pages, keep **one table** that tracks **all physical frames**:

- **one entry per real page (frame)** of memory,
- each entry holds the **virtual address** of the page stored in that frame, plus information about the **process** that owns it.

This **decreases the memory** needed for page tables, but **increases the time** to search the table on each reference. A **hash table** limits the search to one (or a few) entries, and the **TLB** speeds up access.

But how do we implement **shared memory**? With only one virtual address per frame, a frame can't easily be mapped into two processes at once.
